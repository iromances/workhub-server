# 运维 Job 管理 + Function Call 统一 SQL 访问 实施计划

## Context

业务监测目前存在三个痛点：① 9 个定时任务全部是静态 `@Scheduled`，改调度时间要改代码/配置并重启，也没有执行历史可查；② XXL-JOB 看板缺少「上次状态/启用状态」筛选；③ XXL-JOB 与 MQ 巡检访问业务库的 SQL 散落在 `XxlJobMonitorCollector`/`MqMonitorCollector` 代码里拼接，无统一登记与复用机制。

本需求按 SDD 流程执行：先在 `docs/业务线/BL000012-工作台/需求迭代/` 下建档起草规格（Proposal/Design/Tasks），**用户确认规格后再实施**。

**需求编码**：`REQ-9f3c2a84-6d1e-4b7a-b5c2-8e4a71d0f39b`（名称：运维Job管理与FunctionCall统一SQL访问），涉及 workhub-server 与 workhub-web 两仓库。

用户已确认的决策：9 个任务全部纳入且均可操作；调度修改**即时生效**；Function Call SQL 登记+维护均页面化（代码拼 SQL 下线）；两个菜单都放「运维」组。XXL-JOB 与 MQ 巡检 cron 默认均从 10 分钟改为 30 分钟（design 中注明，规格确认时可调整）。

## 现状关键事实（探索结论）

- 定时任务：`workhub-job/.../job/` 下 9 个类，5 个 cron 型（`XxlJobFailureMonitorJob:16` cron `0 */10 * * * *`、`MqFailureMonitorJob`、`ElkSystemAlertJob`、`AccountingReconcileJob`、`WorkItemDueReminderJob`）+ 4 个 Agent fixedDelay 轮询（5000ms）。无动态调度基础设施。
- 业务库访问已统一：两个 Collector 都走 `XxlJobDatabaseQueryClient` 接口 → `McpXxlJobDatabaseQueryClient`（按业务线+环境解析 MCP 数据库目标）→ `DatabaseDiagnosticService.runReadonlyQueries` + `SqlPolicyGuard`（仅 SELECT/WITH/SHOW/DESC/EXPLAIN、单条、强制 LIMIT）。`runVerifiedBatch` 提供证据链（targetHash/起止时间），**必须保留**。
- SQL 拼接点：`XxlJobMonitorCollector` 10 个 `private String *Sql()` 方法、`MqMonitorCollector` 3 个（statsSql/messageStatisticsSql/messagePageSql）+ 辅助片段（detailFilter、inList、abnormalPredicate）。
- 建表走 Flyway：`workhub-bootstrap/src/main/resources/db/schema/mysql/V*.sql`；权限种子参照 `V16__align_permission_tree_with_current_menu.sql`（`sys_permission` INSERT + parent 关联）。
- 前端菜单硬编码：`workhub-web/src/constants/menu.ts` + `src/router/index.ts`（permission 元信息）；业务监测页 `src/views/ops/OpsMonitorView.vue` + `src/api/ops.ts`。

## 实施步骤

### 0. SDD 建档与规格确认（前置门）
- 建 `docs/业务线/BL000012-工作台/需求迭代/REQ-9f3c2a84-6d1e-4b7a-b5c2-8e4a71d0f39b-运维Job管理与FunctionCall统一SQL访问/`，按共用模板起草 proposal.md / design.md / tasks.md（接口契约、表结构、cron 口径、安全边界都落到 design）。
- **停下来请用户确认规格**，确认后才进入编码。

### 1. 数据库迁移（workhub-bootstrap，2 个迁移文件）
- `V20261114_100000__add_job_admin.sql`：
  - `sys_job_config`：job_code(唯一)、job_name、schedule_type(CRON/FIXED_DELAY)、schedule_value、default_schedule_value、enabled、allow_manual_trigger、param_desc、remark、时间戳。
  - `sys_job_execution_log`：job_code、trigger_type(SCHEDULED/MANUAL)、params、status(RUNNING/SUCCESS/ERROR)、started_at、finished_at、duration_ms、error_message、hostname；索引 (job_code, started_at)。
  - 9 个任务的种子（幂等 INSERT），XXL-JOB 与 MQ 巡检 cron 默认 `0 */30 * * * *`。
  - 权限种子：`ops:job:view` / `ops:job:manage`（挂 `ops:view` 下，路径 /ops/jobs）。
- `V20261114_110000__add_function_call.sql`：
  - `func_call_sql`：sql_code(唯一)、scenario_code(唯一可空)、name、description、sql_template(MEDIUMTEXT，命名参数 `:name`)、param_desc、enabled、remark、时间戳。
  - 种子：把两个 Collector 现有 SQL 主体登记为模板（场景编码如 `OPS-XXL-HEALTH-STATS`、`OPS-XXL-FAILED-PAGE`、`OPS-XXL-SILENT-JOBS`、`OPS-MQ-STATS`、`OPS-MQ-MESSAGE-PAGE` 等约 13 条），动态片段（executor 过滤、日期、in 列表）作为命名参数。
  - 权限种子：`ops:function-call:view` / `ops:function-call:manage`。

### 2. 后端：动态调度框架 + 9 任务改造（workhub-job、workhub-service、workhub-dao）
- 新增 `WorkhubJob` 接口（code/name/defaultSchedule/run(String params)）+ `DynamicJobScheduler`：自建 `ThreadPoolTaskScheduler`，启动时从 `sys_job_config` 加载（无记录用默认值并回写种子），按 CRON(CronTrigger)/FIXED_DELAY 调度；改配置后取消 `ScheduledFuture` 立即重调度；同任务并发保护（运行中：调度跳过+日志、手动触发拒绝）；执行包装器写 `sys_job_execution_log`；内部每日清理 90 天前历史（不在管理页展示）。
- 9 个 Job 类去掉 `@Scheduled`，实现 `WorkhubJob`；Agent 轮询类 manual trigger 即调一次 tick（幂等）。cron 校验用 `CronExpression.isValidExpression`。
- 新增 `JobAdminService` + `JobAdminController`（`/api/ops/jobs`）：列表（配置+运行中标记+最近一次执行摘要）、改调度（PUT `/{code}/schedule`）、启停（PUT `/{code}/enabled`）、手动触发（POST `/{code}/trigger`，body 传 params 字符串）、执行历史分页（GET `/{code}/executions`）。DAO 参照 `OpsMonitorMapper` 注解风格。

### 3. 后端：XXL-JOB 看板筛选（改 3 处）
- `OpsMonitorMapper.findAll` 增加 `lastStatus`、`enabled` 精确条件（`<if>` 拼接，`last_status` 兼容 NULL=未检查口径）。
- `OpsMonitorService.dashboard` / `OpsMonitorController.xxlJobDashboard` 透传新参数。

### 4. 后端：FunctionCallService + Collector 改造
- 新增 `FunctionCallService`（workhub-service）：
  - `run(codeOrScenario, params, businessLineCode, environmentCode)`：按 sql_code 或 scenario_code 查启用的模板 → 命名参数替换（模板有参未传值即报错；值仍由调用方经现有白名单校验/转义，注入防护继续依赖 SqlPolicyGuard）→ 走 `McpXxlJobDatabaseQueryClient`。
  - `runBatch(...)` 走 `runVerifiedBatch` 保持证据链（`XxlJobQueryEvidence` 依赖 targetHash 不变）。
  - 模板每次调用直查 DB（巡检频率低，无缓存失效问题），页面修改即时生效。
- 两个 Collector 的 `*Sql()` 构建方法替换为：模板来自 `func_call_sql`，动态片段（detailFilterSql/inListSql/quoteDatabaseName 等现有校验函数）构建后作为参数值传入；单测同步改造。
- 新增 `FunctionCallController`（`/api/ops/function-call`）：SQL 定义 CRUD（manage 权限）、试运行接口（传 code+参数 JSON+业务线/环境，返回限行结果）。

### 5. 前端（workhub-web）
- `constants/menu.ts` + `router/index.ts`：运维组加「Job 管理」(`/ops/jobs`, ops:job:view) 与「Function Call」(`/ops/function-call`, ops:function-call:view)。
- 新增 `views/ops/JobManagementView.vue`：任务列表（调度类型/当前值/状态/最近执行）、改调度对话框（cron 校验提示）、启停、手动触发（参数输入框）、执行历史抽屉（时间/触发方式/参数/状态/耗时/失败原因）。新增 `api/job.ts`。
- 新增 `views/ops/FunctionCallView.vue`：SQL 定义列表（code/场景/名称/启用）+ 编辑对话框（模板 textarea、参数说明）+ 试运行面板。新增 `api/functionCall.ts`。
- `views/ops/OpsMonitorView.vue` + `api/ops.ts`：XXL-JOB 看板筛选栏增加「上次状态」「启用状态」下拉。

### 6. 规范固化（需求 4）
- `AGENTS.md` 研发节新增条目：访问业务数据库必须先在 Function Call 登记场景 SQL 并经 `FunctionCallService` 调用，禁止代码内拼业务库 SQL。
- 新增 `docs/研发/FunctionCall数据库访问规范.md`（登记流程、模板参数写法、安全边界、试运行要求），AGENTS.md 引用。

## 关键风险与对策
- Agent 轮询任务误停会导致数字员工停摆：页面停用操作需二次确认；`sys_job_config` 记录 default 值便于恢复。
- 模板化后 SQL 行为漂移：种子模板直接取自现网在用 SQL 文本，单测断言渲染结果与旧拼接输出一致。
- `@Scheduled` 移除后配置属性（`workhub.agent.dispatch-interval-ms` 等）不再生效：design 中明确「DB 为唯一调度事实源」，行为变更点写入规格请用户确认。

## 验证方式
`mvn -q test`（后端全量单测）→ `npm run build`（前端）→ 本地起服验证上述集成项 → 用 MCP `run_readonly_query` 核对 `sys_job_config`/`sys_job_execution_log`/`func_call_sql` 种子与运行数据。
