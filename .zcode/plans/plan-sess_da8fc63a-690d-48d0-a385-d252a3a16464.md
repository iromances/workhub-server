# 需求任务评估 SDD 化与 AI 开发提测流程升级

## Context：现状结论与目标

**现状**（已核实）：
- "AI任务评估"与"任务评估"是同一份数据（`pm_intake_development_analysis.draft_json`）的两个页签：前者只读展示 AI 参考，后者可编辑（任务项/改动点/工时/涉及系统/负责人）并"评估完成"确认 → 创建 `pm_work_item` + 阶段推进待排期 + 归档研发评估.md。禅道同步仅 RESERVED。
- 澄清完成（`ACTION_CONFIRM_CLARIFICATION`）已自动触发 AI 研发评估（`IntakeService.schedulePostStageAutomation`）。
- AI 评估经 `AiGatewayClient.executeStructured`（场景配置存 DB），输入含知识库上下文——但只是关键词检索（`ProjectKnowledgeBaseService.buildContext`，最多5文件/6000字符），不定向读 SDD 流程。
- 该分支已有完整 Agent 基础设施：`AgentWorkbenchService`（任务/运行）、`AgentCodeGit`（分支 prepare/revise/publish）、`AgentJenkinsClient`（真实 HTTP）、GitLab 客户端、构建/部署/验证/发布计划等。禅道无任何客户端。

**目标流程**（用户 2026-11-05 描述 + 四项决策已确认）：
录入时选研发规范（默认 SDD）→ 澄清时选审核员（选中则任务负责人默认全是他，支持按任务指派）→ 澄清完成后按 SDD 规范评估（读知识库 SDD 流程做设计评估，任务拆解从 SDD tasks 摘要：任务项/改动点/工时/改动系统，负责人默认不填）→ 两个评估页签合并 → 评估确认后发布 SDD 三件套 → **设计完成后** AI 在研发分支启动开发 → 提交测试先 AI 审核（有缺陷→不通过，人工确认可强制提测）→ 确认提测：**真实禅道 API** 建测试单 + **Jenkins 发布测试环境**（人选环境）→ 后续流程照旧。

## 实施内容

### 0. SDD 建档
新需求目录 `docs/业务线/BL000012-工作台/需求迭代/REQ-{uuidgen}-需求任务评估SDD化与AI开发提测流程升级/`（proposal/design/tasks 三件套，记录用户原话与四项决策），完成后更新迭代日志与现状.md。

### 1. 数据与配置（后端 workhub-server，分支 codex/development-20261102）
- 迁移脚本（V 编号顺延，H2 验证）：
  - `pm_intake_record` 加 `development_standard VARCHAR(32)`（SDD/STANDARD，NULL 视为 STANDARD 兼容旧数据）、`review_user_name VARCHAR(64)`。
  - 新表 `pm_intake_submit_test_review`（intake_id、review_status、findings_json、human_confirmed_by/at、zentao 单号/URL、jenkins 构建信息、created/updated）。
- `IntakeStructuredData` 兼容式扩展 `developmentStandard`、`reviewUserName`（沿用现有 record 重载构造器模式）。
- 禅道配置：系统配置组 `zentao.*`（baseUrl、token、productId），参照现有 `SysConfigService` 分组模式；Jenkins 复用 Agent Jenkins 既有配置结构，测试环境候选取业务线环境配置（REQ-95321398 已有环境编码）。

### 2. 录入与澄清（前后端）
- 录入弹窗加"研发规范"下拉（SDD 默认/常规），走 `IntakeUploadRequest` → 入库链路；结构化识别不动该字段。
- 澄清页签工具栏加"审核员"选择（活跃账号，复用 `developmentDeveloperSelectOptions` 模式），新端点保存 `reviewUserName`；评估页签可改。

### 3. 评估合并与 SDD 模式（前后端核心）
- 前端：删"AI任务评估"页签；"任务评估"页签顶部并入 AI 状态 alert + AI 摘要/需求点只读区，下方保留可编辑表格；列表"去评估"弹窗（`isDevelopmentTaskEvaluationDialog`）同步同一结构。
- 后端 `DevelopmentAnalysisService.analyze`：SDD 模式下先定向读取知识库 SDD 流程与模板（`ProjectKnowledgeBaseService` 新增按配置路径读取 `schema/研发/SDD/流程.md` 等，超限截断规则沿用），经新 AI 场景（如 `SDD_DESIGN_EVALUATION`，种子提示词初版可改）产出：SDD proposal/design/tasks 内容（存 draft 扩展字段）+ tasks 任务摘要进 `workItems`（title/description/changePoints/systemTags/estimatedEffort，**ownerUserName 置空**）；非 SDD 走现有逻辑不变。
- 确认（评估完成）：SDD 模式发布 proposal.md/design.md/tasks.md 到需求迭代目录（复用 `publishConfirmedAnalysis`/`KnowledgeArchiveFiles` 模式）；负责人规则：任务有指派→用指派；无指派有审核员→默认审核员；无审核员→校验拦截提示指派（替代现有 developerPool/admin 兜底，仅 SDD 模式）。

### 4. AI 分支开发（设计完成后）
- `CONFIRM_DESIGN` 动作 afterCommit 自动创建 Agent 开发任务并运行（复用 `AgentWorkbenchService.createTask/run`，指令含研发分支 `developmentBranchName`、需求材料路径、SDD tasks；代码发布走 `AgentCodeGit.publish`）；执行失败记录并可在需求详情重试。
- 前端：详情展示 AI 开发执行状态（运行中/完成/失败+重试入口）。

### 5. 提测审核 + 禅道 + Jenkins
- `SUBMIT_TESTING` 改造：先触发 AI 审核（新场景，输入=分支 diff/验证证据，复用 Agent 验证/巡检产物）→ 有缺陷：写 `pm_intake_submit_test_review`（FAILED+findings），阶段停留开发中，前端弹窗展示缺陷清单；人工勾选"确认强制提测"（记录确认人）→ 执行提测：新 `ZentaoClient`（真实 API 建测试单，失败明确报错不伪装成功）+ `AgentJenkinsClient` 触发所选测试环境 Job 构建，回执写入审核表并展示。
- 审核通过（无缺陷）路径同样落审核记录后直接提测；测试环境由人在弹窗中选择（业务线测试环境）。
- 测试通过及以后流程不变。

### 6. 测试与验证
- 后端：新增/扩展 Service 测试（SDD 评估生成与负责人规则、确认发布三件套、提测审核状态机与人工确认、禅道/Jenkins 失败处理、迁移 H2）+ Controller 测试，`mvn test` 定向跑通；禅道/Jenkins 用本地桩测协议。
- 前端：`npm run build`；页面联调由用户在部署后执行。
- 真实禅道/Jenkins 联调：需用户提供禅道地址+Token、测试环境 Jenkins Job 配置后执行（列为交付后待办，不阻塞代码与测试交付）。

## 关键文件
- 后端：`IntakeController`、`IntakeService`、`DevelopmentAnalysisService`、`IntakeClarificationAnalysisService`、`ProjectKnowledgeBaseService`、新 `ZentaoClient`/`SubmitTestReviewService`、`IntakeDemandStatusRules`、V 迁移脚本、AI 场景种子。
- 前端：`IntakeListView.vue`（录入/澄清/合并页签/提测弹窗/AI开发状态）、`api/intake.ts`。
- 文档：需求迭代三件套、迭代日志、现状.md、需求清单测试用例文档追加。

## 边界
- 不改测试通过之后的阶段流转；非 SDD 模式评估行为保持现状；旧数据无研发规范按常规处理。
- 不安装软件；真实外部调用（禅道/Jenkins/GitLab 发布）仅在用户配置就绪并授权后联调。
