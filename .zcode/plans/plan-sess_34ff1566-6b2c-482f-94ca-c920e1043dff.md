# 澄清与任务评估运行记录改造

## Context

3 个在澄清需求的后台 AI 分析提交后静默丢失（PENDING 永挂，从未 RUNNING），且同类"僵尸 PENDING"自 5 月以来累计 20+ 条。根因三层：

1. **静默丢失**：`executeAnalysis` 只在首次 DB 写之后的 try 块里 `catch Exception`；`Error` 级异常、executor 拒绝、任务启动前失败都不留痕，线程静默死亡。
2. **单行覆盖**：澄清/研发拆解分析表按 intake upsert 同一行，历次运行不留存；卡死的 PENDING 无恢复路径（研发拆解更糟：in-progress 直接返回旧记录，连 stale 重试都没有）。
3. **前后端不一致**：后端澄清有 30 分钟 stale 重发通道，前端 `isClarificationInProgress` 只要 PENDING/RUNNING 就禁用按钮 → 永久灰。

改造方向（用户已确认）：**每次开始/重试澄清、每次生成/重试任务评估都插入一条运行记录，按本次运行结果更新该条状态；后端计算 retryable 下发，前端只认返回值**；澄清增加历史轮次列表 UI；两个服务一起改；Flyway 数据修复存量卡死记录。

## 后端 workhub-server

### 1. IntakeClarificationAnalysisService（核心改造）
`workhub-service/.../intake/IntakeClarificationAnalysisService.java`

- **generate()**：
  - 保留防重：最新记录 PENDING/RUNNING 且未超 30 分钟 → 直接返回，不新起（现有测试语义不变）；
  - 否则：沿用"重评前保留澄清记录"归档 → **新 mapper 方法把该 intake 所有 PENDING/RUNNING 旧行置 FAILED**（message="超时未完成，已被新分析取代"）→ **insert 新行**（PENDING）→ 提交 executor；
  - **catch `RejectedExecutionException`**：新行置 FAILED + history"需求澄清分析失败" + 抛出（对齐 `IntakeEnrichmentService:162` 既有模式）。
- **executeAnalysis()**：加 SLF4J 日志（开始/结束+耗时/失败）；现有 `catch Exception` 后**增加 `catch (Throwable)` 兜底** → 该行置 FAILED + log.error + history，任何错误不再静默。
- **toResponse()**：新增 `retryable` 字段：无记录→true；PENDING/RUNNING→`isStaleExecution`（>30 分钟）；DRAFT/CONFIRMED/FAILED→true。
- 新增 `history(intakeId)`：`listByIntakeId`（id DESC 全部轮次），控制器加 `GET /intake/{id}/clarification-analysis/history`。
- reply/confirm/detail 继续走 `findLatestByIntakeId`（最新一轮即当前活跃轮次），语义不变。

### 2. DevelopmentAnalysisService（同法改造）
`workhub-service/.../intake/DevelopmentAnalysisService.java`

- `analyze()`：同 generate() 改法（当前 [L256](workhub-service/src/main/java/cn/aslight/workhub/service/intake/DevelopmentAnalysisService.java#L256) in-progress 永远返回旧行 → 改为 stale 可废弃重起）；`executeAnalysis()`（[L628](workhub-service/src/main/java/cn/aslight/workhub/service/intake/DevelopmentAnalysisService.java#L628)）同样加 Throwable 兜底 + 日志 + 提交拒绝兜底；`toResponse()` 加 `retryable`。
- chat/updateDraft/updateOwners/confirm/retryKnowledgeArchive 保持操作最新一行，无需改语义；内部 `NoopIntakeClarificationAnalysisMapper`（L165-187）与新 mapper 方法同步补实现。

### 3. Mapper 新增
- `IntakeClarificationAnalysisMapper`：`failInFlightByIntakeId(intakeId, message, updatedBy)`、`listByIntakeId(intakeId)`（ORDER BY id DESC）。
- `DevelopmentAnalysisMapper`：`failInFlightByIntakeId(...)`。

### 4. DTO
`IntakeClarificationAnalysisResponse`、`DevelopmentAnalysisResponse` 加 `retryable`；同步所有构造点（两处 toResponse 等）。

### 5. Flyway 存量数据修复
新迁移 `workhub-bootstrap/src/main/resources/db/schema/mysql/V20261112_120000__fail_stale_intake_analysis_runs.sql`：两张表 `UPDATE ... SET analysis_status='FAILED', analysis_message='后台执行中断（历史遗留），可重新分析', updated_by='migration' WHERE analysis_status IN ('PENDING','RUNNING') AND updated_at < NOW() - INTERVAL 30 MINUTE`。重启后自动解锁当前 3 条 + 历史 20+ 条（替代手工 SQL）。

## 前端 workhub-web

### 6. 重试规则只认后端
- `src/types/work-item.ts`：两个 Response 接口加 `retryable: boolean`，新增历史记录类型。
- `src/views/intake/IntakeListView.vue`：`isClarificationInProgress`（L1976）/`isDevelopmentAnalysisInProgress`（L2803）改为 `retryable === false`（字段缺失时回退旧 status 判断，兼容旧后端）；对应按钮 `:disabled` 联动。

### 7. 历史澄清记录列表
- `src/api/intake.ts`：`fetchClarificationAnalysisHistory(id)`。
- 需求澄清 tab（L4229 起）增加折叠式"历史澄清记录"区：每轮显示序号/状态标签/时间/澄清项数，可展开只读查看该轮澄清项与回复；当前轮保持现有交互不变。

## 验证
1. **单测**：更新 `IntakeClarificationAnalysisServiceTest`（stale 重试→废弃旧行+insert 新行；fresh PENDING 不重复执行；提交拒绝→FAILED+history；Throwable→FAILED+history；retryable 计算），新增 DevelopmentAnalysisService 同类用例；`mvn -pl workhub-service test`。
2. **编译/构建**：`mvn -q compile`；前端 `npm run build`。
3. **端到端**（需重启服务，建议普通 Run 模式）：Flyway 应用迁移 → 3 条需求澄清状态变"失败"、按钮可用 → 点"重新分析澄清项" → 几分钟内 排队中→分析中→待处理，新插入一行运行记录；回复一项澄清项；历史列表能看到上一轮 FAILED 轮次；点"澄清完成"后任务评估同样走新链路；DB 复查两表按轮次留痕。
