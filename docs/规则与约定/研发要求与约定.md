# 研发要求与约定

本文档维护 WorkHub 仓库的研发要求、工程约定、安全边界、AI 协作规则和项目专项业务规则。

## 1. AI 协作和文档要求

- 使用中文沟通和维护仓库文档。
- AI、Superpowers 或其他工具生成的仓库文档也必须遵守中文文档要求。
- 代码标识、命令、API 路径、第三方产品名和既有工具固定目录可保留英文。

## 2. 开发前置要求

- 涉及新功能、页面改造、接口改造、数据库结构变更、数据修复、定时任务、批处理或外部接口改造时，先按 `docs/规则与约定/研发设计规范.md` 输出方案。
- 方案审核通过前，不修改代码，不执行会改变项目状态的命令。
- 实现过程中发现方案不准确时，先更新方案并重新等待确认。
- 禁止把未执行的验证命令写成已验证。
- 禁止把敏感配置、token、数据库密码复制进方案、文档或回答。
- 所有关键写操作必须产生日志或留痕记录，尤其是工作项状态流转、需求阶段动作、支付配置变更和跟踪记录。

## 3. 数据库和接口变更要求

工程结构、模块职责边界和业务域归档方式见 `docs/事实/系统架构与设计.md`。

- 前端职责以交互、呈现、表单状态、用户操作触发和轻量格式化为主；业务统计、数据聚合、状态口径、权限判定、跨页分页合并、业务线归并、金额/数量汇总等业务逻辑必须由后端接口统一输出。
- 工作台、看板、列表汇总、报表截图和其他统计类页面不得由前端拉取大分页或全量列表后自行聚合；必须提供面向页面场景的后端查询接口，保证分页、历史数据兼容、业务线编码和状态口径一致。
- 前端可以保留纯展示层计算，例如空值显示、颜色样式选择、下载文件名生成和用户选择项切换；一旦计算结果会影响业务数量、分组、筛选、排序或权限，就必须后移到后端。
- 表结构变更必须同步更新初始化 SQL、模型、DAO、服务逻辑和相关文档。
- 新增或变更接口时，同步更新 `docs/事实/控制器接口说明.md`。
- 接口文档表格必须包含 `系统路径`，用于标注前端功能入口或调用来源。
- 涉及数据库结构变更时，方案必须说明 DDL、DML、默认值、历史数据兼容、索引影响和回滚方式。
- 纯刷数据需求必须说明数据范围、筛选 SQL、影响记录数、备份、幂等、试跑、回滚和前后校验；禁止直接执行正式刷数。
- 禁止在 Java 启动代码、`ApplicationRunner`、`CommandLineRunner`、Bean 初始化或定时任务中硬编码 DDL/DML 自动补表、补字段或刷历史数据。
- 数据库结构和数据变更必须以 Flyway 版本脚本交付，统一放在 `workhub-bootstrap/src/main/resources/db/schema/mysql/`；`V1__init.sql` 是当前完整建库基线，后续新增变更从下一个版本号递增，不再维护 `dbscript/DDL/` 或 `dbscript/DML/` 分目录。
- 数据库脚本执行记录以 Flyway 的 `flyway_schema_history` 为准；失败脚本必须修复后重新验证，不允许用 Java 启动逻辑绕过脚本管理。
- 可观测性基础设施只能作为旁路能力接入，采集失败不得影响核心台账 API 可用性。

## 4. 测试用例验证

- 涉及代码、接口、页面、数据库脚本、定时任务、批处理或外部接口改造的需求，必须按 `docs/模版/自动化测试用例模板.md` 单独输出测试用例文件。
- 测试用例必须覆盖核心场景、边界场景和异常场景；不适合自动化覆盖的场景必须说明原因和替代验证方式。
- 测试用例文件在方案阶段填写计划覆盖范围和计划执行命令；开发完成后必须回填真实执行结果、执行时间、执行人或执行代理、失败原因和剩余风险。
- 交付前应执行与变更风险匹配的验证命令或手工验证。
- 后端较大改动提交前，至少执行 `mvn -q -DskipTests compile`。
- 受影响接口应完成基本手工验证；涉及前端调用时，同时验证前端入口路径和接口响应字段。
- 当前仓库未形成成体系测试代码时，不得用“无测试可跑”替代编译、接口验证和必要手工验证。
- 如验证命令因环境、依赖或外部服务不可用而失败，应说明失败原因、影响范围和后续处理建议。
- 最终交付只能声明实际执行成功的命令或手工验证结果，不得把未执行的测试写成“已验证”。

## 5. MCP 和生产资源安全要求

- MCP 不向 AI 返回数据库密码、GitLab Access Token、SSH 密码、私钥或堡垒机凭据。
- 需要凭据时，由 WorkHub 服务端从已加密配置中加载并在服务端内部使用。
- 数据库能力只允许受控只读查询，禁止写入、DDL、多语句、导出、高风险函数和无边界全表扫描。
- 服务器能力只允许服务状态、服务日志和日志路径读取；配置服务或日志路径白名单时必须限制在白名单内，白名单为空表示对应维度不限制。
- MCP runtime 不暴露任意 SSH 命令。
- 需求管理 MCP 能力只允许读取和搜索，不提供写入、阶段推进、状态变更或附件文件正文读取。
- 知识库 MCP 定位能力只返回 MCP 项目配置中的知识库根地址 `projectVaultPath` 和路径结构；如新增知识库文件正文读取能力，必须限制在该根目录下，并限制文件类型、文件大小和路径穿越。
- 对生产问题，默认只做诊断和只读核查；任何修复、重启、数据修正、DDL/DML、配置变更都必须等用户明确确认。

## 6. 运维要求

- 业务线定位必须以 WorkHub 配置为准，不以本地代码目录或仓库名反推。
- 如果用户没有明确业务线，先反问；涉及数据、服务状态、日志或生产现象时，还必须明确环境。
- 检索知识库时必须先用业务线中文名圈定范围，再用项目名、系统名、审批编号、需求名称、业务关键词收敛范围。
- 回答业务线问题时，区分代码证据、知识库证据、数据库结果、服务器日志和个人推断。
- 没有证据时使用“推测”“需要确认”等表述，不要把 AI 生成内容包装成已确认事实。
- 详细定位与排查方法见 `docs/事实/业务运维分析方法.md`。
- 运维排查默认只做诊断和只读核查；涉及修复、重启、数据修正、DDL/DML 或配置变更时，必须等待用户明确确认。
- 服务器状态和日志排查只使用 MCP 受控能力，不绕过 WorkHub 直接执行任意 shell 命令。

## 7. 支付配置边界

- 支付配置域只负责“渠道/商户/参数/敏感凭据/秘钥/项目绑定”的管理，不直接承担真实支付交易编排。
- 商户号按渠道和环境维度管理，生产与测试配置不得混用在同一条商户记录中。
- 项目与商户是多对多关系，通过多用途绑定表达“某项目在该商户支持用途的子集下使用哪个商户”。
- 支付敏感参数、敏感凭据和秘钥采用应用层加密落库，接口只返回脱敏值、指纹和版本摘要。
- 秘钥采用版本化保存，新增秘钥默认视为轮换行为，需要保留历史版本和审计日志。

## 8. 文档维护触发

优先保持根目录 `AGENTS.md` 简短稳定；详细说明写入 `docs/`，再从入口文档链接过去。

当做以下变更时，应同步更新对应文档：

- 新增或移除核心 API 分组。
- 改变业务范围、对象模型或生命周期。
- 引入新的全局交互规则或集成方式。
- 调整业务范围、验收基线或开发顺序。
- 新增、修改或删除 MCP 工具。
- 调整业务运维分析方法、知识库路径规则或生产资源访问边界。
- 新增或修改专题能力。
