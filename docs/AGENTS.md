# docs 文档指引

本文件是 `docs/` 下的 AI 文档指引，统一维护文档组织、职责划分、归档与协作规则。

## 1. 文档分层与命名

本仓库维护 WorkHub 及已归档业务线的系统设计、迭代日志与需求研发文档，以及配套研发规范。新业务线需求先按下方跨仓库规则确定归属。以下为本仓库标准目录结构，相关目录和文档按实际需要创建：

```text
docs/
├── AGENTS.md                  # 文档组织、用途与协作指引
├── WorkHub/
│   ├── 系统设计.md
│   ├── 迭代日志.md
│   └── 需求/
│       └── {需求编码}-{需求名称}/
│           ├── proposal.md
│           ├── design.md
│           └── tasks.md
├── 业务线/
│   └── {业务线编码}-{业务线名称}/
│       ├── 系统设计.md
│       ├── 迭代日志.md
│       └── 需求/
│           └── {需求编码}-{需求名称}/
│               ├── proposal.md
│               ├── design.md
│               └── tasks.md
└── 研发规范/
    ├── 业务运维分析方法.md
    ├── 代码风格.md              # AI 编码强制指引
    ├── SDD/                     # SDD 文档模板
    └── 参考资料/                 # 方法论与分享材料
```

### 跨仓库需求归属

- 先按需求编码和名称检查本仓库与 [agents-playbook](../../agents-playbook/docs/AGENTS.md#需求归属与建档) 的已有目录。已有正式需求目录继续维护，采用归属仓库的流程和模板；其他仓库只维护索引，不复制正式规格或因当前工作目录变化重复建档。
- 无已有目录时，WorkHub 自身需求归档本仓库；业务线需求默认归档 agents-playbook，用户明确指定其他归属时遵从指定。
- 两处均有正式产物时，先核对用户指定、审批和版本来源；仍无法判断才询问归属，期间不迁移或覆盖文件。业务代码始终遵守实际代码仓库的操作约束和编码规范。

## 2. 文档职责与内容边界

文档按职责分层组织，以下规范统一适用于 WorkHub 和各业务线。具体目录遵循第 1 节的结构，本指引不逐一登记业务线或需求文件。

| 文档类型 | 职责与内容边界 | 维护时机 |
| --- | --- | --- |
| 系统设计 | 维护所属系统的整体设计与当前事实，包括系统范围、架构、模块职责、业务规则、关键流程、接口、数据模型、运行方式，以及仓库区分和跨系统关联等特定约束。单次需求的待实施方案放在需求目录。 | 首次梳理时建立；系统变化经核实后更新，注明来源和适用范围，区分现状与计划。 |
| 需求研发文档 | 描述一次需求要解决的问题、方案及执行任务。采用 SDD：Proposal 说明背景、目标、范围与验收标准，Design 说明技术方案，Tasks 承接实施与验证；接口契约、ADR 和附件按需补充。 | 随需求分析、设计和实施维护在唯一需求目录中，记录实际状态及相关版本。 |
| 迭代日志 | 按时间记录所属系统哪个需求发生了什么变化，关联需求编码和研发文档；作为变更摘要，不重复完整方案。 | 需求建档及实际进展、变更发生时追加，区分设计、开发、验证和发布等状态。 |
| 研发规范 | 在 `研发规范/` 下维护可复用的编码约定、工程边界及业务运维分析方法。具体业务线的事实和特殊规则放入其系统设计。 | 通用研发要求或分析方法变化时更新。 |
| 文档模板 | 在 `研发规范/SDD/模板/` 下提供需求文档的结构和填写提示，不承载某个具体需求的事实、进度或审批结论。 | 文档结构或填写要求变化时更新；生成需求文档时填写实际内容。 |
| 外部参考资料 | 为业务理解、设计分析或历史追溯提供参考；业务线产品文档、设计方案、系统现状和历史需求可按需只读查询 [agents-playbook 资料](../../agents-playbook/docs/)。参考内容不直接等同于当前系统事实。 | 按任务需要查询，引用时注明来源及适用范围。 |

AI 根据当前任务和文档职责自行选择阅读范围与顺序；适用的操作约束、编码要求和规格确认条件仍须遵守。历史方案用于理解当时的需求和决策，当前实现结论应结合目标代码及环境核实。

## 3. 文档维护

以下目录路径均以仓库根目录为基准。

- 文档组织、职责划分和文档协作规则统一维护在本文件。新增文档按现有类型归档；目录规则、文档类型或职责变化时更新本文件，文件新增、删除或移动时修正相关引用。
- WorkHub 系统设计维护在 `docs/WorkHub/系统设计.md`，业务线系统设计维护在 `docs/业务线/{业务线编码}-{业务线名称}/系统设计.md`。
- WorkHub 和各业务线的迭代日志分别维护在其系统设计同级的 `迭代日志.md`。需求首次建档及后续实际进展、变更发生时按时间追加，使用“时间、需求编码、需求名称、变更内容、状态、研发文档”列；复用需求固定编码，研发文档链接到对应需求目录或设计文件，不将计划写成已完成。
- 长期研发规则或设计要求变化时，更新 `docs/研发规范/` 下对应的规范文档。
- 项目定位、职责边界或仓库操作约束变化时更新[根目录指引](../AGENTS.md)；文档组织、用途或 AI 文档协作规则变化时更新本文件；具体业务事实和研发细则仍维护在对应文档中。
