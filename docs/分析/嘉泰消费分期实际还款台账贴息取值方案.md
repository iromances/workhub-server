# 嘉泰消费分期实际还款台账贴息取值方案

## 1. 结论

嘉泰消费分期“实际还款台账”对应接口为：

```http
GET /jiatai-amp-saps/manage/report/paytable/page
```

下载接口为：

```http
POST /jiatai-amp-saps/manage/report/paytable/page/download
```

当前 `master` 中，页面查询和下载均调用 `pageQueryThreeTable`，实际使用的表为：

- `repayment_plan`
- `bill_fee_detail`
- `loan_order`，仅用于合同编号、放款申请单号、资产标签等展示或查询条件

当前接口已经不使用：

- `repayment_plan_pay_subject_detail`
- `statement_charge_resource`

按照张华君上一版逻辑，贴息模式下本金 P0001 必须扣除资方服务费 P0003 的原始金额；P0003 再作为资方服务费单独展示。当前 `pageQueryThreeTable` 的 P0001 没有执行该扣减，因此存在本金和资方服务费重复计算风险。

本次只需要修改实际还款台账的查询展示逻辑，不修改真实账单、支付、退款、回购或核销金额。

| 项目 | 内容 |

| 业务线 | 嘉泰消费分期 `BL000003` |

| 目标环境 | 生产环境 |

消费分期 `BL000004 / asset-plateform` 是部分再保理项目的业务侧，但实际还款台账金额拆分发生在嘉泰资方侧。本方案不修改消费分期侧的退费、回购接口或数据。

## 3. 接口调用链

```text
GET /jiatai-amp-saps/manage/report/paytable/page
  -> PayTableReportController.pageIndex()
  -> RepaymentReportService.page()
  -> RepaymentPlanPaySubjectDetailMapper.pageQueryThreeTable()
```

页面和下载使用同一个 Mapper 查询：

```text
POST /jiatai-amp-saps/manage/report/paytable/page/download
  -> RepaymentReportService.submitDownload()
  -> RepaymentReportService.executeDownload()
  -> RepaymentPlanPaySubjectDetailMapper.pageQueryThreeTable()
```

因此，修正 `pageQueryThreeTable` 后，页面和下载会同时生效。

## 4. 当前生产项目范围

生产配置中目前仍有业务活动的四个项目为：

| 项目 | 项目编号 | 产品及付息模式 |
| --- | --- | --- |
| 国民 | `JT_XXT-PRJ-GM-C` | C001，客户付息 |
| 即科 | `JT_XXT-PRJ-JK-E` | E001 贴息；E002 客户付息 |
| 乐易享 | `JT_XXT-PRJ-LYX-A` | A001/A002，客户付息 |
| 众美优选 | `JT_XXT-PRJ-ZMY-A` | A001/A002，客户付息 |

当前生产环境实际存在的贴息产品只有即科 E001。因此：

- 当前生产数据的直接影响范围只有即科 E001。
- 查询逻辑应按 `repayment_plan.interest_subsidy_mode = 1` 编写，不应把项目编号硬编码成即科；以后其他项目启用贴息产品时可以直接复用。
- 客户付息模式 `interest_subsidy_mode = 2` 的现有逻辑不在本次公式调整范围内。

## 5. 字段定义

以下字段均取当前有效的 `bill_fee_detail` 记录，即：

```sql
is_delete = 0
AND is_cancel = 0
```

定义：

| 变量 | 数据来源 | 含义 |
| --- | --- | --- |
| `P1_paid` | P0001 的 `paid_amount` | P1 已付总额 |
| `P1_total` | P0001 的 `total_amount` | P1 应付总额 |
| `F0` | P0003 的 `original_amount` | 原始资方服务费 |
| `F_paid` | P0003 的 `paid_amount` | 资方服务费实付或冲回金额 |

## 6. 四类场景取值公式

### 6.1 提前结清，账单状态 201

```text
实际资方本金 = P1_paid - F0
实际资方服务费 = F0
```

对应取值：

```sql
P0001.pay_amount = P0001.paid_amount - P0003.original_amount
P0003.pay_amount = P0003.original_amount
```

### 6.2 退费，账单状态 400

```text
实际资方本金 = P1_paid - F0
```

实际资方服务费沿用上一版 Java 后处理逻辑：

```text
如果 F_paid < 0，实际资方服务费 = 0
如果 F_paid = 0，实际资方服务费 = F0
如果 F_paid > 0，实际资方服务费 = F_paid
```

即：

```sql
P0001.pay_amount = P0001.paid_amount - P0003.original_amount

P0003.pay_amount = CASE
    WHEN P0003.paid_amount < 0 THEN 0
    WHEN P0003.paid_amount = 0 THEN P0003.original_amount
    ELSE P0003.paid_amount
END
```

如需计算资方服务费冲回金额：

```text
资方服务费冲回金额 = F0 - 实际资方服务费
```

### 6.3 七天无理由退费，账单状态 401

取值公式与普通退费一致：

```text
实际资方本金 = P1_paid - F0
```

```text
如果 F_paid < 0，实际资方服务费 = 0
如果 F_paid = 0，实际资方服务费 = F0
如果 F_paid > 0，实际资方服务费 = F_paid
```

对应 SQL 与状态 400 相同。

### 6.4 回购，账单状态 600/601

张华君上一版使用 `statement_charge_resource` 中 P0001 的 `fee_amount` 作为回购 P1 总额，再扣减 P0003 原始资方服务费：

```text
实际资方本金 = 回购P1总额 - F0
实际资方服务费 = F0
```

回购清单生成时，P0001 的 `statement_charge_resource.fee_amount` 来源于当时 P0001 的未付金额。经生产数据核对，在本次无部分支付、已结算的贴息回购账单范围内：

```text
statement_charge_resource(P0001).fee_amount
= bill_fee_detail(P0001).total_amount
```

所以实际还款台账可改为：

```sql
P0001.pay_amount = P0001.total_amount - P0003.original_amount
P0003.pay_amount = P0003.original_amount
```

生产环境目前有状态 601 的数据，没有状态 600 的样本。状态 600 的逻辑应保持与 601 一致，但上线前需要补充测试数据验证。

## 7. 推荐 SQL

以下 SQL 只表达贴息模式下四类场景的本金和资方服务费取值，不是整个实际还款台账所有结算模式的完整替换 SQL。

```sql
SELECT
    rp.project_no,
    rp.project_name,
    rp.product_code,
    rp.application_no,
    rp.bill_no,
    rp.period,
    rp.bill_status,
    CASE
        WHEN rp.bill_status = 201 THEN 201
        WHEN rp.bill_status = 400 THEN 400
        WHEN rp.bill_status = 401 THEN 401
        WHEN rp.bill_status IN (600, 601) THEN 600
    END AS settlement_mode,
    rp.settlement_time AS operate_time,
    CASE
        WHEN rp.bill_status IN (600, 601) THEN 20
        ELSE rp.payment_mode
    END AS payment_mode,
    bfd.subject_no,
    bfd.subject_name,
    CASE
        WHEN bfd.subject_no = 'P0001' THEN
            (
                CASE
                    WHEN rp.bill_status IN (600, 601)
                        THEN IFNULL(bfd.total_amount, 0)
                    ELSE IFNULL(bfd.paid_amount, 0)
                END
            ) - IFNULL(p3.original_amount, 0)
        WHEN bfd.subject_no = 'P0003'
             AND rp.bill_status IN (201, 600, 601)
            THEN IFNULL(p3.original_amount, 0)
        WHEN bfd.subject_no = 'P0003'
             AND rp.bill_status IN (400, 401)
            THEN
                CASE
                    WHEN IFNULL(p3.paid_amount, 0) < 0 THEN 0
                    WHEN IFNULL(p3.paid_amount, 0) = 0
                        THEN IFNULL(p3.original_amount, 0)
                    ELSE p3.paid_amount
                END
        ELSE 0
    END AS pay_amount,
    IFNULL(p3.original_amount, 0) AS original_service_fee
FROM repayment_plan rp
JOIN bill_fee_detail bfd
  ON bfd.bill_no = rp.bill_no
 AND bfd.subject_no IN ('P0001', 'P0003')
 AND bfd.is_delete = 0
 AND bfd.is_cancel = 0
LEFT JOIN bill_fee_detail p3
  ON p3.bill_no = rp.bill_no
 AND p3.subject_no = 'P0003'
 AND p3.is_delete = 0
 AND p3.is_cancel = 0
WHERE rp.interest_subsidy_mode = 1
  AND rp.bill_status IN (201, 400, 401, 600, 601)
  AND rp.settlement_status = 1
  AND rp.is_delete = 0
  AND rp.is_cancel = 0;
```

## 8. 与当前 `pageQueryThreeTable` 的合并方式

不能使用上一节 SQL 直接替换当前整个 `pageQueryThreeTable`，因为当前接口还包含正常还款、代偿、客户付息产品、其他费用科目及页面查询条件。

实际修改应当：

1. 保留当前 `repayment_plan rp`、`bill_fee_detail bfd` 和 `loan_order lo` 查询结构。
2. 增加一次当前有效 P0003 的自连接：

   ```sql
   LEFT JOIN bill_fee_detail p3
     ON p3.bill_no = rp.bill_no
    AND p3.subject_no = 'P0003'
    AND p3.is_delete = 0
    AND p3.is_cancel = 0
   ```

3. 仅在以下条件同时成立时应用本方案的 P0001/P0003 公式：

   ```text
   rp.interest_subsidy_mode = 1
   rp.bill_status IN (201, 400, 401, 600, 601)
   bfd.subject_no IN ('P0001', 'P0003')
   ```

4. 其他结算模式、客户付息产品和其他费用科目保持当前逻辑。
5. 页面接口和下载接口共用该 Mapper，不需要分别维护两套金额公式。

## 9. 表是否可以省略

### 9.1 `repayment_plan_pay_subject_detail`

在本次范围内可以省略。

理由：

- 账单不涉及部分支付。
- 实际还款台账查询的是已结算账单的最终金额，不要求还原每一笔支付流水。
- 生产数据核对中，201、400、401 场景 P0001 的 `bill_fee_detail.paid_amount` 与上一版支付科目明细金额一致。
- 400、401 场景 P0003 的 `bill_fee_detail.paid_amount` 与上一版支付科目明细金额一致。

以下需求不能省略：

- 需要展示单笔支付流水或支付序列号。
- 需要精确到事件级支付时间。
- 未来支持部分支付或同一账单多次支付。
- 需要审计每次还款、退款操作过程，而不是最终账单状态。

### 9.2 `statement_charge_resource`

在本次贴息四场景的实际还款台账最终金额查询中可以省略。

理由：

- 当前 `pageQueryThreeTable` 本身已经不查询该表。
- 回购状态 601 的生产数据中，P0001 的 `statement_charge_resource.fee_amount` 与当前有效 P0001 的 `bill_fee_detail.total_amount` 全部一致。
- 当前范围不涉及部分支付。
- 查询目标是结算后的最终台账金额，而不是回购清单生成时的历史快照。

但以下场景不能省略：

- 回购清单生成逻辑。
- 需要审计回购清单生成当时的金额快照。
- 同一账单可能存在多次回购资源生成记录。
- 需要使用回购批次、账务日期、资源状态等字段。
- 未来支持部分支付，导致当前账单金额与回购生成时金额不一致。

### 9.3 `loan_order`

金额计算不依赖 `loan_order`，但当前完整页面不能直接省略，因为以下字段和查询条件来自该表：

- 再保理合同编号 `refactoring_contract_no`
- 放款申请单号 `loan_id`
- 资产标签 `assets_tag`

如果只执行本金和资方服务费的后台汇总 SQL，可以省略 `loan_order`；如果修改完整页面接口，应保留。

| --- | ---: | ---: | ---: | ---: |

| 退费 400 | 336 | 31 | 180,198.43 | 1,081.74 |
| 七天无理由退费 401 | 126 | 9 | 87,679.36 | 0.00 |
| 回购 601 | 111 | 10 | 89,991.05 | 3,748.71 |

数据质量检查结果：

- 622 个目标账单均只有一条当前有效 P0001 和一条当前有效 P0003。
- 201、400、401 的 P0001 金额与上一版支付科目明细逐账单一致。
- 400、401 的 P0003 金额与上一版支付科目明细逐账单一致。
- 601 的 P0001 `bill_fee_detail.total_amount` 与 `statement_charge_resource.fee_amount` 逐账单一致。
- 201、400、401 的 `repayment_plan.settlement_time` 与上一版操作时间日期一致；当前页面只展示日期，因此不影响现有展示口径。
- 状态 600 当前无生产样本，尚不能用生产数据完成等价性验证。

## 11. 改动影响范围

本方案只影响：

- 实际还款台账分页接口。
- 实际还款台账下载接口。
- 贴息模式下 201、400、401、600、601 场景的 P0001/P0003 展示金额。

本方案不影响：

- 真实账单金额。
- 还款、退费、七天无理由退费或回购业务处理。
- 支付和退款流水。
- 回购清单生成。
- 客户付息产品的既有取值逻辑。
- 消费分期业务侧到嘉泰资方侧的接口契约。

## 12. 上线前验证项

至少覆盖以下用例：

1. 贴息提前结清 201：P1 等于 `paid_amount - P3.original_amount`，P3 等于 `original_amount`。
2. 贴息退费 400，P3 `paid_amount < 0`：P3 展示 0。
3. 贴息退费 400，P3 `paid_amount = 0`：P3 展示原始服务费。
4. 贴息退费 400，P3 `paid_amount > 0`：P3 展示 `paid_amount`。
5. 七天无理由退费 401：覆盖与 400 相同的三个 P3 分支。
6. 贴息回购 601：P1 等于 `total_amount - P3.original_amount`，P3 等于 `original_amount`。
7. 补充构造状态 600 测试数据，验证与 601 公式一致。
8. 客户付息模式下 201、400、401、600、601 金额保持不变。
9. 正常还款和代偿等非本次场景金额保持不变。
10. 页面查询结果与下载文件金额一致。
11. 按合同编号、放款申请单号和资产标签查询仍正常，确认 `loan_order` 关联未受影响。

## 13. 最终建议

采用 `repayment_plan + bill_fee_detail` 计算贴息四场景的本金和资方服务费；完整页面继续保留 `loan_order` 以支持展示字段和查询条件。

不恢复 `repayment_plan_pay_subject_detail`，也不为实际还款台账重新引入 `statement_charge_resource`。在当前无部分支付、查询最终结算结果的业务前提下，两张表都不是金额计算必需表。

实现时只修改 `pageQueryThreeTable` 中贴息 P0001/P0003 的金额分支，保留其他场景原逻辑，并完成页面与下载的一致性回归。
