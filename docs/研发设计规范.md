# 研发设计规范

## 目标

在人工智能代理启动开发前，先输出一份可供审核的完整设计开发方案，提前暴露需求边界、影响面、数据风险、兼容策略、验证方式和回滚路径。

本规范适用于：

- 新系统 / 新模块开发
- 老系统功能迭代
- 页面改造
- 后台接口改造
- 数据库结构变更
- 一次性刷数据 / 数据修复
- 定时任务、批处理、外部接口改造
- 前后端、数据库、数据修复混合需求

## 基本原则

- 先方案，后开发。
- 审核通过前，不修改代码、不执行改变项目状态的命令。
- 方案必须足够具体，不能只写“修改相关接口”“调整页面逻辑”这类模糊描述。
- 方案要说明“不做什么”，避免需求蔓延。
- 涉及数据、金额、交易、外部供应商、批处理、定时任务时，必须说明幂等性、回滚和验证方式。
- 如果实现过程中发现方案不准确，必须先更新方案并重新等待确认。

## 关键不可省略项

每份方案必须按“标准输出结构”输出。以下内容按触发条件强制提供；确实不涉及的项，要明确写“不涉及”。

| 触发条件 | 必须提供 |
|---|---|
| 涉及页面 | 页面方案，说明入口、布局、操作路径、表单 / 按钮 / 弹窗 / 筛选 / 分页 / 排序、加载态、空态、错误态、前后端字段对应关系；复杂页面变更必须提供可交互页面 demo，低风险页面变更可说明不提供 demo 的原因和替代验证方式 |
| 涉及新增表、改表、表关系或关键字段 | 表结构 ER 图，说明表、主键、外键、唯一约束、索引、关系、核心字段、历史数据兼容方式 |
| 任何开发需求 | 功能清单、验收标准、研发任务禅道标题；研发任务标题建议格式为 `【模块】动作 + 对象 + 目的` |
| 涉及新功能或处理流程变化 | 原程序处理流程图、新程序处理流程图；新流程图必须高亮新增、修改、删除或改道的节点和链路 |
| 涉及数据、金额、交易、外部供应商、批处理、定时任务 | 幂等性、重试 / 重复执行行为、回滚、验证方式 |
| 任何开发需求 | 前置条件和风险评估，风险必须说明触发条件、影响范围、规避方式、验证方式 |

## 标准输出结构

### 1. 需求理解

说明人工智能代理对本需求理解的概述，必须包含：

- 业务目标
- 本次要交付的功能或结果
- 用户使用场景
- 明确不包含的范围
- 需求类型判断：新系统 / 新模块、老系统迭代、只改页面、只改后台、只刷数据、数据库结构变更、定时任务 / 批处理、混合需求

### 2. 功能清单和研发任务

将该需求拆解成功能清单和研发任务，必须包含：

- 功能清单
- 每个功能点的交付内容
- 每个功能点的验收标准
- 建议研发任务禅道标题
- 每个研发任务对应的内聚改动点
- 每个研发任务涉及的模块、页面、接口、表或脚本

本节下必须继续拆出以下子项；如不涉及，要明确写“不涉及”。

#### 2.1 涉及系统

说明本次需求影响哪些系统、模块或上下游，必须包含：

- 前端系统
- 后端系统
- 数据库
- 外部系统或供应商
- 定时任务、批处理或数据脚本
- 上线系统清单初步判断

#### 2.2 现状分析

说明当前系统已有内容，必须包含：

- 当前相关模块、页面、接口、服务、表、脚本位置
- 现有业务流程
- 现有数据结构
- 现有权限、菜单、配置、枚举
- 旧逻辑、旧数据、旧接口是否存在兼容要求
- 当前实现中的明显风险或限制

#### 2.3 数据库与数据方案

只要涉及数据库，就必须写。

必须包含：

- 表结构 ER 图
- 是否需要 DDL
- 是否需要 DML
- 是否需要刷历史数据
- 涉及哪些表
- 新增字段默认值
- 历史数据如何兼容
- 索引是否需要调整
- 数据脚本执行顺序
- 是否可重复执行
- 如何防止重复数据
- 如何备份
- 如何回滚
- 执行前后校验 SQL

如果是纯刷数据需求，必须额外包含：

- 数据范围
- 筛选条件
- 影响记录数预估
- 试跑方式
- 正式执行方式
- 失败中断后的恢复方式

#### 2.4 页面方案

只要涉及前端页面，就必须写。

必须包含：

- 页面方案概述
- 页面入口
- 交互变化
- 表单字段
- 列表字段
- 按钮、弹窗、筛选、分页、排序
- 权限控制
- 加载、空态、错误态
- 与后端接口的对应关系
- 浏览器验证路径

以下场景必须提供可交互页面 demo：

- 新增页面
- 页面主流程变化
- 复杂表单
- 弹窗、抽屉或批量操作
- 状态切换
- 筛选、分页或排序
- 权限差异
- 加载态、空态或错误态需要体验确认

以下低风险页面变更可以不提供可交互页面 demo：

- 文案微调
- 字段名调整
- 样式微调
- 展示顺序调整
- 不改变交互路径的小范围展示变更

不提供可交互页面 demo 时，必须说明原因和替代验证方式，例如截图、浏览器验证路径或明确验收点。

#### 2.5 接口方案

只要涉及接口，就必须写。

必须包含：

- 新增 / 修改 / 废弃的接口
- 请求参数
- 返回字段
- 字段含义
- 默认值和空值处理
- 错误码或异常处理
- 是否兼容旧前端
- 是否影响已有调用方
- 接口验证方式

#### 2.6 业务逻辑方案

说明核心规则，必须包含：

- 方案概述
- 核心设计思路
- 为什么采用该方案
- 是否有备选方案
- 备选方案为什么不采用
- 本方案对现有系统的侵入程度
- 如涉及新功能或原功能程序处理流程变化，提供原程序处理流程图、新程序处理流程图，并在新程序处理流程图中高亮标记改动部分
- 主流程
- 分支流程
- 边界条件
- 异常处理
- 幂等性设计
- 重复执行行为
- 金额、比例、价格、日期等关键字段处理方式
- 是否影响已有统计、复盘、分析结果

#### 2.7 模块与文件计划

列出预计修改或新增的位置。

格式建议：

```text
- asset-app
  - Controller：...
  - 定时任务：...
- asset-domain-xxx
  - Service：...
  - DTO：...
- asset-infra-persistence
  - Mapper：...
  - XML：...
- dbscript
  - DDL：...
  - DML：...
```

要求：

- 能定位到模块或目录
- 能说明每个文件的职责
- 不允许只写“相关文件”

#### 2.8 影响面清单

按层列出影响范围。如不涉及某一项，要明确写“不涉及”。

必须覆盖：

- 前端页面
- 后端 Controller / API
- DTO / Request / Response
- Service / Domain 逻辑
- Mapper / SQL / XML
- 数据库表、字段、索引
- 权限、菜单、字典、枚举
- 定时任务、批处理
- 外部系统调用
- 缓存、配置、消息、文件
- 数据导入、数据修复、历史数据兼容
- 日志、监控、异常处理

### 3. 兼容性方案

老系统迭代和混合需求必须写。

必须包含：

- 老接口是否保留
- 老字段是否保留
- 老数据是否可读
- 新旧逻辑是否并存
- 前后端不同步上线是否会出问题
- 历史枚举、空值、脏数据如何处理
- 是否需要灰度或开关

### 4. 前置条件

必须包含：

- 业务前置条件
- 技术前置条件
- 数据前置条件
- 环境前置条件
- 联调和上线前置条件

### 5. 风险评估

必须包含：

- 业务风险
- 数据风险
- 性能风险
- 兼容风险
- 权限风险
- 外部依赖风险
- 上线风险
- 回滚风险

每个风险要说明：

- 触发条件
- 影响范围
- 规避方式
- 验证方式

### 6. 实施步骤

必须按顺序列出。

示例：

```text
1. 只读确认现有代码和表结构
2. 新增 DDL 脚本
3. 新增 DTO 和接口定义
4. 实现 Service 逻辑
5. 补 Mapper / XML
6. 前端接入
7. 编译和接口验证
8. 数据脚本试跑
9. 最终回归
```

要求：

- 步骤之间有依赖关系
- 每一步有明确产出
- 涉及数据库时，必须说明脚本顺序
- 涉及前后端时，必须说明联调顺序

### 7. 自动化测试

必须包含计划设计或实际执行的自动化测试安排。自动化测试用例必须单独形成测试用例文件，不再只写在开发方案正文中。测试用例文件可参考 `docs/自动化测试用例模板.md`，并且必须覆盖本次需求涉及的核心场景、边界场景和异常场景。

方案阶段必须写：

- 计划新增或调整的单元测试
- 计划新增或调整的集成测试
- 自动化测试用例文件路径
- 计划覆盖的核心场景、边界场景和异常场景
- 不适合自动化测试覆盖的原因

最终交付阶段必须写：

- 测试用例文件中的测试结果是否已更新
- 实际执行的自动化测试命令
- 每条测试命令的执行结果
- 未执行自动化测试的原因
- 自动化测试未覆盖的剩余风险

要求：

- 方案阶段写“计划执行”
- 最终交付时只能声明实际执行成功的命令
- 不能把未执行的测试写成“已验证”
- 开发完成后，必须在自动化测试用例文件中回填测试结果、执行时间、执行人或执行代理、失败原因和剩余风险

### 8. 上线步骤

必须包含：

- 上线系统清单
- 上线前检查项
- 数据库脚本执行顺序
- 后端、前端、定时任务、批处理、配置的上线顺序
- 是否需要停机、灰度或开关
- 上线后检查点
- 上线负责人或协作方，如已明确
- 上线失败时的中止条件

### 9. 回滚方案

必须包含：

- 代码回滚方式
- 配置回滚方式
- DDL 是否可逆
- DML 如何反向修复
- 刷数据是否有备份
- 失败后如何恢复
- 如果不能完全回滚，必须明确说明

### 10. 验证方案

必须包含计划执行的最小校验。

按情况选择：

- `./mvnw -q -DskipTests compile`
- 指定模块编译
- 单元测试
- 接口请求验证
- SQL 查询验证
- 页面浏览器验证
- 数据修复前后对账
- 定时任务手动触发验证
- 日志检查

要求：

- 方案阶段写“计划执行”
- 最终交付时只能声明实际执行成功的命令
- 不能把未执行的命令写成“已验证”

### 11. 待确认问题

列出需要人类确认的内容。

常见包括：

- 业务口径
- 字段含义
- 数据范围
- 权限范围
- 页面交互
- 上线顺序
- 是否接受兼容成本
- 是否接受不可逆数据变更

如果没有待确认问题，写：

```text
暂无阻塞性待确认问题，可以按本方案进入开发。
```

## 按需求类型的必填项

按需求类型在标准模板基础上强化重点项；未涉及的章节仍要写“不涉及”。

| 需求类型 | 必须重点说明 | 可简化项 / 特别要求 |
|---|---|---|
| 只改页面 | 页面方案、页面入口、组件和交互、接口依赖、权限点、空态 / 错误态、浏览器验证方式；复杂页面变更必须提供可交互页面 demo，低风险页面变更必须说明不提供 demo 的原因和替代验证方式 | 可简化数据库方案和刷数据方案 |
| 只改后台 | API、DTO、Service、Mapper / SQL、权限、接口兼容、编译和接口验证 | 可简化页面方案 |
| 只刷数据 | 数据范围、筛选 SQL、影响记录数、备份、幂等、试跑、回滚、前后校验 | 不允许直接执行正式刷数 |
| 数据库结构变更 | 表结构 ER 图、DDL、DML、默认值、历史数据兼容、索引影响、回滚方式、全仓编译 | 新增脚本必须走 `dbscript/ddl` 或 `dbscript/dml` |
| 老系统迭代 | 旧逻辑、旧接口、旧字段、旧数据、新旧兼容、是否灰度、前后端上线顺序 | 流程变化时必须提供新旧流程图和改动高亮 |
| 新系统 / 新模块 | 模块边界、目录位置、表设计、权限模型、菜单入口、首版范围、后续扩展点 | 如涉及页面、数据库或流程变化，按触发条件补页面演示、ER 图、流程图 |
| 混合需求 | 拆分前端、后端、数据库、数据修复、上线顺序、回滚方案 | 不允许把无关页面、接口、脚本、数据修复混成一个研发任务 |

## 禁止事项

- 禁止未经审核直接修改代码。
- 禁止用一句“修改相关逻辑”代替影响面分析。
- 禁止缺少功能清单和研发任务禅道标题。
- 禁止在涉及页面时省略页面方案；复杂页面变更禁止省略可交互页面 demo，低风险页面变更禁止省略不提供 demo 的原因和替代验证方式。
- 禁止在涉及表结构时省略 ER 图。
- 禁止在新增功能或处理流程变化时省略原程序处理流程图、新程序处理流程图和改动高亮标记。
- 禁止省略前置条件。
- 禁止省略数据风险。
- 禁止没有回滚方案就执行刷数据。
- 禁止把未执行的验证命令写成已验证。
- 禁止在方案未覆盖前后端上线顺序时处理混合需求。
- 禁止把敏感配置、token、数据库密码复制进方案。
