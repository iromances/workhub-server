# 需求管理日期列拆分技术方案

## 1. 需求理解

需求管理列表当前把测试阶段日期压缩为“提测日期”，把发布阶段日期压缩为“上线日期”。本次需要把列表口径调整为：

- “提测日期”列改为“测试日期”，同列区分实际提测日期和测试完成日期。
- “上线日期”相关展示拆分为“验收日期”和“上线日期”。

本需求属于老系统低风险页面展示迭代。只调整需求管理列表展示口径，不改变需求生命周期，不新增阶段动作，不修改数据库表结构，不修改后端接口。

## 2. 功能清单和研发任务

| 功能点 | 交付内容 | 验收标准 | 建议研发任务禅道标题 | 内聚改动点 |
|---|---|---|---|---|
| 测试日期列口径调整 | 列名从“提测日期”改为“测试日期”，展示“提测”和“完成”两行 | 列表能同时看到实际提测日期和实际测试完成日期；无实际提测时仍可展示预估提测并标记“预估” | `【需求管理】调整测试日期列区分提测和完成日期` | 前端列表列配置、日期展示辅助函数 |
| 验收与上线日期拆分 | 原“上线日期”拆为“验收日期”和“上线日期” | 列表能分别看到实际验收日期和实际上线日期；无实际上线时仍可展示预估上线并标记“预估” | `【需求管理】拆分验收日期和上线日期列表展示` | 前端列表列配置、延期/预约标签展示 |

### 2.1 涉及系统

- 前端系统：`workhub-web`
- 后端系统：不涉及接口改造，沿用 `GET /api/intake`
- 数据库：不涉及 DDL/DML
- 外部系统或供应商：不涉及
- 定时任务、批处理或数据脚本：不涉及
- 上线系统清单初步判断：仅 `workhub-web`

### 2.2 现状分析

- 当前页面：`../workhub-web/src/views/intake/IntakeListView.vue`
- 当前类型：`../workhub-web/src/types/work-item.ts`
- 当前列表返回字段已包含：
  - `plannedTestingStartDate`：预估提测日期
  - `testingStartedDate`：实际提测日期
  - `actualTestingCompletedDate`：实际测试完成日期
  - `scheduledAcceptanceDate`：预约验收日期
  - `acceptanceTime`：实际验收日期
  - `plannedReleaseDate`：预估上线日期
  - `releasedTime`：实际上线日期
- 当前问题：
  - 列表“提测日期”只展示 `testingStartedDate || plannedTestingStartDate`，没有直观看到测试完成日期。
  - 列表“上线日期”只展示 `releasedTime || plannedReleaseDate`，没有直观看到验收日期。

### 2.3 数据库与数据方案

不涉及数据库改造。

- 表结构 ER 图：不涉及
- 是否需要 DDL：否
- 是否需要 DML：否
- 是否需要刷历史数据：否
- 历史数据兼容方式：历史记录已有字段为空时按 `-` 展示；预估字段按原逻辑继续展示预估标签。

### 2.4 页面方案

- 页面入口：需求管理列表。
- 交互变化：不新增按钮、弹窗、筛选、分页或排序。
- 列表字段：
  - `测试日期`：展示两行。
    - `提测：实际提测日期`；无实际提测但有预估提测时展示预估提测并标记 `预估`。
    - `完成：实际测试完成日期`；为空展示 `-`。
    - 实际提测晚于预估提测时标记 `延期`。
  - `验收日期`：展示实际验收日期；若暂无实际验收但有预约验收日期，展示预约验收并标记 `预约`。
  - `上线日期`：展示实际上线日期；若暂无实际上线但有预估上线日期，展示预估上线并标记 `预估`。实际上线晚于预估上线时标记 `延期`。
- 可交互 demo：不提供。原因是本次是低风险列表字段拆分，不改变交互路径；替代验证为单元测试、构建验证和需求列表页面浏览器检查。
- 浏览器验证路径：登录后进入需求管理列表，检查列名和日期行展示。

### 2.5 接口方案

不修改接口。

- `GET /api/intake` 已返回本次需要的字段。
- 空值处理由前端展示层完成。
- 旧前端兼容：不涉及后端字段变更。

### 2.6 业务逻辑方案

核心规则：

- 测试阶段不再用单个“有效测试日期”代表整段测试，而是同时展示提测日期和测试完成日期。
- 发布阶段不再把验收和上线混成“上线日期”，而是把验收日期与上线日期分列。
- 预估、预约、延期标签仅用于辅助识别日期来源，不改变需求状态。

备选方案：

- 方案 A：增加 4 个独立列。优点是最清晰，缺点是列表横向空间占用过大。
- 方案 B：测试日期保留一列内两行，验收和上线拆成两列。推荐采用，信息完整且列表宽度可控。
- 方案 C：只改列名不拆展示。不能满足区分日期的目标，不采用。

## 3. 兼容性方案

接口字段不变，历史数据空值不报错。上线时前后端没有强绑定顺序要求，但建议只发布前端即可。

## 4. 验证方案

- 单元测试：运行日期展示辅助函数测试。
- 构建验证：在 `workhub-web` 运行 `npm run build`。
- 页面验证：启动前端后进入需求管理列表，检查：
  - 列名为“测试日期 / 验收日期 / 上线日期”。
  - 测试日期列能同时展示提测和完成。
  - 验收日期与上线日期不再混在同一列。

## 5. 回滚方案

回滚前端文件改动即可恢复原列表展示。由于不涉及接口、库表和历史数据，回滚不需要执行数据脚本。
