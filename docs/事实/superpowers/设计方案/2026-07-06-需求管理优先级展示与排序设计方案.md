# 开发方案：需求管理优先级展示与排序

## 1. 需求理解

- 业务目标：需求管理列表能直观看到需求优先级，并支持人工维护优先级，便于同阶段需求按紧急程度排布。
- 本次交付：优先级支持 `高`、`中`、`低`；需求录入后默认优先级为 `中`；列表在“需求”列后展示优先级；操作列提供“修改优先级”；列表在现有排序基础上追加优先级权重排序。
- 用户场景：用户进入需求管理列表，查看需求后面的优先级；需要调整时从操作列修改，保存后列表刷新，并在同一需求状态排序组内按高、中、低排序。
- 不包含范围：不新增数据库字段，不刷历史数据，不新增查询条件，不改变需求状态流转，不迁移历史结构化 JSON。
- 需求类型：老系统迭代，涉及后端接口、服务排序、前端页面和接口文档，不涉及数据库结构变更。

## 2. 功能清单和研发任务

- 功能点 1：后端列表响应增加优先级并追加排序权重。
  - 交付内容：`IntakeSummaryResponse` 返回 `priority`；`IntakeService.list` 保持现有识别状态、需求状态排序，再按优先级 `高 > 中 > 低 > 空值/其他` 排序。
  - 验收标准：同识别状态、同需求状态下，高优先级排在中、低之前；不同识别状态或需求状态仍按原排序优先级排列。
  - 建议研发任务禅道标题：`【需求管理】列表增加优先级响应和排序权重`
- 功能点 1.1：需求录入默认优先级为中。
  - 交付内容：创建待整理需求主记录时，如果结构化抽取未提供优先级，则默认写入 `中`。
  - 验收标准：通过需求录入创建的新需求，未指定优先级时列表显示为 `中`。
  - 建议研发任务禅道标题：`【需求管理】需求录入默认优先级为中`
- 功能点 2：后端支持修改优先级。
  - 交付内容：新增 `POST /api/intake/{id}/priority`，请求体包含 `priority`，只允许 `高`、`中`、`低`，更新主表 `pm_intake_record.priority` 并记录修改历史。
  - 验收标准：合法优先级可保存并留痕；非法值返回业务错误；重复保存相同值不重复写历史。
  - 建议研发任务禅道标题：`【需求管理】增加需求优先级维护接口`
- 功能点 3：前端列表展示和修改优先级。
  - 交付内容：需求列后新增优先级列；操作下拉增加“修改优先级”；弹窗提供高、中、低选项并调用后端保存。
  - 验收标准：列位置正确；空值显示 `-`；保存后列表刷新并展示最新优先级。
  - 建议研发任务禅道标题：`【需求管理】列表页增加优先级展示和修改入口`

### 2.1 涉及系统

- 前端系统：`../workhub-web` 需求管理页面。
- 后端系统：`workhub-server` 需求管理接口、服务、模型。
- 数据库：复用 `pm_intake_record.priority`，不改表。
- 外部系统或供应商：不涉及。
- 定时任务、批处理或数据脚本：不涉及。
- 上线系统清单：后端服务、前端静态资源。

### 2.2 现状分析

- 主表 `pm_intake_record` 已有 `priority` 字段，DAO 查询和正式字段更新逻辑已读写该字段。
- `IntakeSummaryResponse` 当前未返回 `priority`，需求管理列表无法展示。
- `IntakeService.list` 当前排序为识别状态、需求状态、接收时间倒序、ID 倒序。
- 前端 `IntakeListView.vue` 当前需求列后直接是提出人、需求状态等列，操作下拉已有多种单条操作入口。
- 现有修改业务线已具备弹窗和历史记录模式，可参考其写法实现优先级维护。

### 2.3 数据库与数据方案

- 表结构 ER 图：不涉及新增表或关系。
- DDL：不需要，复用 `pm_intake_record.priority`。
- DML：不需要，不刷历史数据。
- Flyway 脚本：不涉及。
- Java 启动补丁：不涉及，不新增自动补字段或刷数逻辑。
- 历史数据兼容：历史 `priority` 为空时列表展示 `-`，排序靠后。
- 索引：不调整。当前列表排序和过滤已在 Service 层完成，本次只追加一个内存排序权重。
- 备份和回滚：不涉及数据批量变更；回滚代码后已保存的优先级值仍保留在既有字段中。

### 2.4 页面方案

- 页面入口：需求管理列表页。
- 交互变化：列表“需求”列后新增“优先级”列；操作下拉新增“修改优先级”；点击后打开弹窗选择高、中、低。
- 表单字段：`priority`，必填，选项 `高`、`中`、`低`。
- 列表字段：`priority`，空值显示 `-`；高/中/低使用不同 tag 类型区分。
- 按钮、弹窗、筛选、分页、排序：不新增筛选；分页沿用现有分页；排序由后端在现有排序基础上追加优先级权重。
- 权限控制：沿用需求管理页面权限，不新增权限点。
- 加载、空态、错误态：弹窗保存按钮展示 loading；失败沿用 `resolveErrorMessage` 提示；空值列显示 `-`。
- 接口对应：`updateIntakePriority(id, { priority })` 调用 `POST /api/intake/{id}/priority`。
- 可交互 demo：不提供。原因是低风险列表列和单字段弹窗改造，复用现有 Element Plus 表格、下拉和弹窗；替代验证为本地构建和页面手工检查。

### 2.5 接口方案

- 修改接口：`GET /api/intake`
  - 返回字段新增：`priority`，字符串，可空。
  - 兼容性：旧前端忽略新增字段，不破坏响应。
- 新增接口：`POST /api/intake/{id}/priority`
  - 请求体：`{"priority":"高|中|低"}`
  - 返回：更新后的需求详情。
  - 默认值和空值：空值或非法值返回业务错误，不清空优先级。
  - 错误处理：需求不存在、优先级非法时抛出业务异常。
  - 验证方式：Controller 测试校验接口调用；Service 测试校验保存、留痕和非法值。

### 2.6 业务逻辑方案

核心方案：复用主表 `priority` 字段，列表响应直接返回该字段；保存优先级只更新主表字段和修改历史，不改 AI 结构化数据。

原排序：

```mermaid
flowchart LR
  A["列表记录"] --> B["识别状态排序"]
  B --> C["需求状态排序"]
  C --> D["接收时间倒序"]
  D --> E["ID 倒序"]
```

新排序：

```mermaid
flowchart LR
  A["列表记录"] --> B["识别状态排序"]
  B --> C["需求状态排序"]
  C --> D["新增：优先级高/中/低排序"]
  D --> E["接收时间倒序"]
  E --> F["ID 倒序"]
```

- 主流程：需求录入时无优先级则默认写入 `中`；用户修改优先级时，后端校验并保存，记录历史；再次加载列表时按原排序基础追加优先级权重。
- 分支流程：保存相同优先级时直接返回详情，不重复写历史；历史空值参与排序时排在高、中、低后面。
- 边界条件：只允许 `高`、`中`、`低`；前后空格归一化。
- 幂等性：相同值重复保存无额外副作用。
- 是否影响统计：不影响工作台统计口径，只影响需求管理列表排序。

## 3. 兼容性方案

- 旧前端：忽略新增 `priority` 字段，不受影响。
- 旧数据：空优先级继续可展示和查询，排序在高、中、低之后。
- 已有排序：识别状态和需求状态优先级不变，只在其后追加优先级权重。

## 4. 验证方案

- 后端单测：覆盖优先级排序、合法保存、非法值拒绝、Controller 接口。
- 后端编译：执行 `mvn -q -DskipTests compile`。
- 前端构建：执行 `cd ../workhub-web && npm run build`。
- 手工验证：打开需求管理页，确认列位置、优先级 tag、修改弹窗和保存刷新。

## 5. 风险评估

- 风险：排序变化可能改变同状态需求的列表相对位置。
  - 规避：仅在现有识别状态和需求状态排序后追加优先级，满足用户要求。
  - 验证：单测构造不同需求状态和优先级组合确认顺序。
- 风险：历史数据优先级为空。
  - 规避：空值显示 `-`，排序靠后，不做数据回填。
- 风险：非法值写入导致排序不稳定。
  - 规避：接口只允许 `高`、`中`、`低`，前端也只提供固定选项。
