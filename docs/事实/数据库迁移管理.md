# 数据库迁移管理

## 1. 当前边界

- WorkHub 使用 Spring Boot 托管的 Flyway 11，唯一自动扫描目录为 `workhub-bootstrap/src/main/resources/db/schema/mysql/`。
- `V1` 至 `V20` 是已经形成执行历史的数字版本，保持文件名和内容不变。
- 从 `V20260720_153544` 开始，新迁移统一使用时间戳版本：

  ```text
  VYYYYMMDD_HHMMSS__brief_desc.sql
  ```

- `baseline-on-migrate` 固定为 `false`。新库从 V1 顺序初始化；已有但未纳入 Flyway 的存量库只能在完成结构审计后人工 baseline。
- Java 启动逻辑、定时任务和手工散落 SQL 不得替代 Flyway 管理结构或必需系统数据。

## 2. 新增迁移

1. 在研发方案中说明 DDL、DML、历史数据兼容、索引影响、执行校验和失败恢复。
2. 使用当前时间生成全局唯一版本，描述使用小写英文和下划线。
3. 必需字典和系统配置可以纳入 Flyway；长耗时回填、环境专项修复和运营数据处理应使用经过评审的独立手工脚本。
4. 已在任何持久环境成功执行的迁移禁止修改、重命名或删除；修复使用新的更高版本。失败迁移只能在核对部分提交的 DDL、清理现场并评审 `repair` 后修正重试。
5. 高风险删除优先使用 expand-contract：先扩展并兼容读写，确认旧版本退出后再通过后续迁移收缩。

## 3. 配置行为

应用启动时自动执行严格的 `validate + migrate`：

- 校验迁移文件命名和 checksum；
- 迁移目录缺失、重复版本、SQL 失败或数据库连接失败时阻止应用启动；
- 禁止自动 baseline、out-of-order、placeholder 替换和数据库 clean；
- `FLYWAY_ENABLED=false` 仅用于紧急代码回滚或受控诊断，不得作为长期跳过迁移的方式；
- Flyway 使用独立 JDBC 连接参数，默认复用业务数据源地址和账号；生产可通过 Spring 配置注入专用迁移账号。

当前环境按单实例启动迁移设计。未来如果改为多实例并行发布，需要重新评审迁移锁、超时和独立迁移任务。

## 4. 本地和发布校验

发布必须使用 clean 构建，防止 `target/classes` 或 jar 中残留已删除、改名的迁移：

```bash
mvn -q -DskipTests clean package
jar tf workhub-bootstrap/target/workhub-bootstrap-0.1.0-SNAPSHOT.jar \
  | grep 'BOOT-INF/classes/db/schema/mysql/'
```

Flyway Maven 插件用于发布前检查和受控执行：

```bash
mvn -pl workhub-bootstrap flyway:info
mvn -pl workhub-bootstrap flyway:validate
mvn -pl workhub-bootstrap flyway:migrate
```

插件连接信息必须通过本地 Maven settings、环境变量或受保护的 CI/CD secret 注入，不得写入 POM、命令记录、日志或文档。执行前必须确认目标 JDBC URL 对应的环境和 schema。
本地可使用 Flyway 标准环境变量 `FLYWAY_URL`、`FLYWAY_USER`、`FLYWAY_PASSWORD`；生产流水线应使用受保护且不回显的 secret。

标准发布顺序：

1. 确认目标环境、schema、备份和变更窗口；
2. 审计 `flyway_schema_history`，要求不存在失败、Missing、Future 或非预期 pending；
3. 执行 `clean package` 并检查 jar 内迁移清单；
4. 启动单个应用实例，由 Flyway 自动完成 `validate + migrate`；
5. 查询 history、表结构和关键数据，要求新版本 `success=1`、0 pending；
6. 完成应用健康检查和核心接口验证后再继续发布其他实例。

## 5. 失败与恢复

- MySQL DDL 可能隐式提交，迁移失败不代表结构自动完整回滚。
- 失败后立即停止发布，保留现场并核对 history、表、列、索引、约束和实际数据。
- 优先新增更高版本向前修复，不直接修改已经成功执行的脚本。
- `repair` 只能在明确 history 与实际结构关系并完成人工评审后使用，禁止用来掩盖 checksum 变化或缺失脚本。
- 持久环境禁止执行 `clean`。
- 中止条件包括：错库风险、备份失败、history 未审计、checksum 不一致、重复版本、迁移失败或非预期锁等待。

## 6. 已知兼容性

当前开发库为 MySQL 8.4，WorkHub 使用的 Flyway 11.14.1 启动时提示其最新验证版本为 MySQL 8.1。开发库已完成真实迁移、`validate`、`info`、二次空 migrate 和应用随机端口启动烟测；生产发布前仍需对目标 MySQL 版本单独执行同样校验。
