# WorkHub 项目宪章

## 1. 项目定位

WorkHub 是一个面向内部团队的项目与工作项管理系统。第一阶段重点解决企业微信等渠道来的需求、缺陷、运维事项、临时任务无法集中登记、缺少统一跟踪、状态不透明、历史留痕不足的问题。

## 2. 业务目标

1. 建立统一收口。
来自企业微信回调和需求截图/附件录入的事项都进入统一待整理箱。

2. 建立统一工作项模型。
需求、缺陷、运维、任务采用统一字段体系和流转规则，避免多个台账并存。

3. 建立全生命周期跟踪。
从登记、澄清、评估、排期、开发、测试、发布到完成，全程留痕。

4. 提高整理效率。
对企微原始消息和需求截图/附件提供结构化增强能力，但必须人工确认后入正式工作项。

5. 提高研发拆解效率。
对研发类需求可基于业务线 GitLab 命名空间下全部微服务仓库生成代码影响分析、工作项草稿、改地点、工时和负责人建议；研发任务涉及系统必须从业务线系统清单或全局中台系统清单选择，需求侧从任务自动汇总“改了哪些系统”；当前任务评估只强制确认评估工时和测试工时，任务拆解为辅助项，正式工作项仍需人工确认。

6. 提高项目透明度。
通过项目、迭代、版本、工作项列表与看板，实现进度可见、责任人明确、历史可追。

7. 沉淀支付接入配置。
统一管理支付渠道、多商户、项目绑定、用途路由、生产参数、敏感凭据和秘钥版本，减少多项目重复维护与误配风险。

## 3. 第一阶段范围

范围内：

- 本地账号密码登录
- 项目管理
- 迭代管理
- 版本管理
- 工作项管理
- 跟踪记录
- 状态流转日志
- 附件关联
- 企业微信入站收件箱
- 企业微信群机器人出站通知
- 需求截图/附件结构化增强
- 数据提取/运维类需求的 SQL 草稿生成
- 研发需求 GitLab 代码影响分析与工作项草稿生成
- 业务线涉及系统清单和全局中台系统清单
- GitLab 仓库地址和 Access Token 系统配置
- 需求本地文件夹基础目录系统配置
- 禅道同步预留接口
- 支付渠道/商户/项目绑定配置管理
- 可选 ELK 错误日志监控，用于运维观测，不参与业务数据写入或状态流转
- 运维系统预警关注子系统和本地错误事件查询
- 列表、筛选、详情、看板

范围外：

- 企业微信单点登录
- 复杂权限模型和组织架构同步
- 自动审批流引擎
- 自动创建正式需求且不经人工确认
- 多租户
- 工时、成本核算
- 真实支付交易下发、资金路由执行、清结算计算
- 系统直连业务库执行数据导出 SQL
- 未经人工确认直接创建研发工作项
- 真实禅道同步写入

## 4. 统一对象模型

核心对象：

- 项目
- 迭代
- 版本
- 工作项
- 工作项跟踪记录
- 工作项状态流转日志
- 企微收件箱记录
- 需求待办
- 附件
- 用户
- 系统配置项
- 支付渠道
- 支付商户
- 项目支付绑定
- 支付参数、敏感凭据与秘钥版本

工作项类型：

- 需求
- 缺陷
- 运维
- 任务

规则：

- 每个工作项必须归属一个项目。
- 运维事项也必须归属项目，默认通过“公共运维项目”或具体业务项目承载。
- 每个工作项至少包含创建人、负责人、跟进人。
- AI 只能生成草稿，不能跳过人工确认直接入正式台账。
- 数据提取/运维类需求可以由 AI 生成 SQL 草稿，但系统不得连接业务库或执行 SQL，必须由人工确认后自行执行。
- 研发需求进入澄清阶段时可选择是否启用 AI 辅助澄清；启用后由 AI 基于需求材料、代码和知识库列出逐项待确认项、风险项，作为人工澄清辅助参考，不阻塞澄清完成；澄清完成后自动触发 AI 任务评估。
- 研发需求可以由 AI 基于代码和澄清结果生成工作项草稿、工时和负责人建议；任务评估和需求只关联业务线及对应系统，不依赖正式项目；人工可确认总预估工时和测试工时推进阶段；存在任务项时必须从系统清单选择涉及系统。
- 研发任务确认后需求进入待排期；只有草稿已关联正式项目 ID 时才创建正式工作项，并保留需求与正式任务的可查询关联。任务负责人录入后进入全局候选用户，后续研发任务评估可继续选择。
- GitLab Access Token 等敏感系统配置必须加密落库、脱敏展示。
- 禅道同步在真实配置和验收完成前只保留接口，不执行外部写入。
- 支付商户是可复用资源，不直接归属于单一项目；商户号先维护支持用途集合，项目通过“项目 + 商户支持用途子集 + 商户”的绑定关系消费商户配置。
- 同一个商户号可以被多个项目共享；同一个项目也可以按不同用途绑定多个商户，同一条绑定可以在该商户支持范围内选择多个用途。
- 共享协议、正常分账、代偿回购、子商户、被分账商户、退款主户等关系需要作为结构化关联关系维护。
- 支付秘钥、敏感参数和账户/交易/接口凭据不得明文回显给前端，至少需要加密落库、脱敏展示和操作留痕。
- 系统预警只做运维观测，关注子系统单独维护；当前先查询本地错误事件数据，后续 ELK 仅作为数据来源，不直接写工作项或推动业务生命周期。

## 5. 生命周期基线

标准状态：

`待整理 -> 待澄清 -> 待评估 -> 待排期 -> 开发中 -> 测试中 -> 待发布 -> 已完成`

补充终态：

- 已拒绝
- 已挂起

补充非终态：

- 已暂停

状态使用原则：

- `待整理` 只用于收件箱和待转化草稿，不用于正式已确认工作项。
- 正式工作项从 `待澄清` 开始流转。
- 任何状态变更都必须生成流转日志。
- 暂停状态必须填写暂停原因和暂停日期，并保存暂停前状态。
- 暂停工作项恢复时只能恢复到暂停前状态，不能借恢复动作跳转到其他状态。
- 关闭类状态必须填写结论说明。

需求管理侧补充生命周期：

- 识别前状态不进入需求业务生命周期，只通过 `enrichmentStatus` 展示系统处理进度。
- 识别成功后，需求按类型进入对应业务生命周期：
  - 研发需求：`已收录 -> 待澄清 -> 待评估 -> 待排期 -> 待设计 -> 开发中 -> 测试中 -> 待上线 -> 待验收 -> 已完成`
  - 数据提取/运维：`已收录 -> 待澄清 -> 待处理 -> 处理中 -> 待验收 -> 已完成`
- 需求侧异常终态统一为 `终止关闭`；任一非终态需求均可填写关闭原因后关闭，关闭原因必须写入修改历史。
- 需求侧可暂停任一非终态需求，暂停状态为 `已暂停`；暂停时必须填写暂停原因和暂停日期，并保存暂停前状态；恢复时只能回到暂停前状态，暂停和恢复均写入修改历史。
- 需求待办独立于需求主生命周期；同一需求可录入多条待办，待办状态为 `待处理/处理中/已完成/已取消`，待办完成时必须维护处理结果并写入修改历史。
- 需求录入时必须填写研发负责人，并单独落库到 `pm_intake_record.development_owner_user_name`；该字段不再存放于 `structured_data_json`。
- 研发需求的 AI 任务评估属于后台异步动作；评估完成后补齐草稿与建议信息，但需求主状态仍按人工阶段动作推进，不再额外持久化 `评估中/已评估，待确认` 这类过渡状态。

## 6. 成功标准

1. 任一来自企微或截图/附件录入的事项都能在系统中找到源记录。
2. 任一正式工作项都能查到负责人、当前状态、所属项目、最近跟进记录。
3. 任一状态变更都能回溯操作者、时间和原因。
4. 项目维度可以看到迭代、版本、工作项分布和当前阻塞项。
5. 结构化增强结果能减少人工整理时间，但不会直接污染正式数据。
6. 研发需求拆解结果能辅助形成工作项草稿，工时确认可独立推进，创建正式工作项前必须人工确认具体任务项。
7. 支付接入配置可以明确回答“某项目在某用途下当前使用哪个商户和哪套生产参数/秘钥版本”。

## 7. 开发原则

1. 先做稳定台账，再做自动化增强。
2. 先确保留痕与追踪，再做智能推荐。
3. 前后端契约优先，避免页面先跑、接口后补。
4. 文档先行，需求扩展先更新项目宪章和实施路线。
5. 能复用统一对象模型时，不为单一场景单独造表。

## 8. 防飘逸约束

以下事项必须先更新文档再开发：

- 引入新的工作项类型
- 改变生命周期主状态
- 让 AI 直接写正式数据
- 新增审批流、权限流、组织流
- 引入新的基础设施，例如消息队列、搜索引擎、对象存储
