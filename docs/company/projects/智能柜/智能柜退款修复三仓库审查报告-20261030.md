## 5. 未修复问题与建议

### 5.1 R2：并发同步静默漏写，P2

**归类**：原报告所述既有并发问题仍可触发；新增原支付单锁没有完全解决事务边界及更新失败处理。

**代码证据**：

- [S3:99][S3-99]：在 Spring `afterCommit` 中调用设备流水同步。
- [S1:644][S1-644]：`update(flow, updateWrapper)` 返回值被忽略。
- [S1:650][S1-650]：方法结束即释放原支付单锁，未覆盖回调线程连接后续清理。
- [S7:37][S7-37]：实体带 `@Version`。本次亦核对本地公共依赖中存在乐观锁配置，隔离测试使用真实 MyBatis-Plus 乐观锁拦截器；这不等于核验生产部署配置。
- [S4:85][S4-85]：已终态退款重复回调直接返回，不能依赖重复回调再次同步流水。

**复现一：回调与补偿并发。** 原支付 260；R1 退 1、R2 退 259。回调事务完成主单提交，在 `afterCommit` 中同步 R1。原单锁释放后，补偿线程取得锁并读到旧流水版本；回调连接后续清理完成写入，补偿的旧版本更新影响 0 行。最终只记录 R1，收入退款为 0、押金退款为 1，R2 未写入。该结果发生在 Spring/MyBatis-Plus/H2 隔离环境，不是生产故障记录。

**复现二：其他写入抢先修改版本。** 读取流水后，另一写入先更新版本；退款更新返回 0，方法仍正常结束，退款单号与金额未落库。对照测试中，无外层事务的两个退款线程在同一互斥锁下可以正确累计，说明不能简单表述为“锁始终无效”。

**影响**：退款主单已成功，但流水金额、单号、状态缺失；任务正常返回或成功计数不能证明同步落库成功。R2 还会削弱 R3 的并发时间保证。

**修复建议**：

1. 将锁边界与事务提交边界对齐。对 `afterCommit` 中的流水写入，使用经 Spring 代理调用的独立事务，例如在锁内调用 `REQUIRES_NEW` 的持久化服务，提交完成后再解锁；仅增加同类内部调用注解不能保证事务生效。
2. 检查更新行数或布尔结果。冲突时重新读取最新值并有界重试，超过上限明确失败并进入可补偿路径。
3. 支付、分账、退款尽量只更新各自负责字段，并保留版本 CAS；直接改为无实体的 wrapper 更新可能绕过现有版本保护，需要验证生成 SQL。
4. 验收回调与补偿、两笔退款、退款与支付/分账交错三类并发；最终金额、状态、单号集合必须与成功退款事实一致。

### 5.4 U2：补偿仍按原支付流水创建时间筛选

**影响**：旧支付订单的新退款一旦实时同步失败，不能指望当前默认任务兜底。此项是既有窗口限制，不计作本次新增缺陷。

**修复建议**：让候选集合覆盖近期成功退款及尚未同步的退款事实，并明确失败重试保留范围；若采用时间窗口，应选择退款事实的时间锚点，避免仍被原支付创建时间限制。人工指定订单时，应明确日期约束是否保留，并对不命中原因给出可见结果。

### 5.5 U3：增量去重不能替代历史纠错

**代码位置**：设备流水 [S1:605][S1-605] 在退款单号已存在时直接返回；任务 SQL [S6:301][S6-301] 排除已记录退款；xxt-pay [P2:120][P2-120] 与 SAPS [S4:85][S4-85] 对已终态订单跳过重复更新。

测试预置两笔退款已经记入，金额被污染为业务款 518、押金 2、状态仍为部分退款、时间为 1970 年；重放已记录退款后，错误字段仍保持原值。另一测试预置金额已正确累计全退但状态仍为部分退款，重放也不会纠正状态。

**结论**：发布本次代码或简单重跑通知、补偿任务不能证明历史问题已恢复。生产是否执行过其他修复，需要独立核验，见 V1。

**修复建议**：依据有效成功退款主单及明细重建金额、状态、退款单号集合；时间优先使用可信渠道结果或可追溯日志恢复。先生成带目标主键、旧值、重算值及版本的清单，再按明确截止点和并发保护分批处理。无法恢复真实时间的记录单列待核验。需更正对外通知时另核对协议与幂等。
