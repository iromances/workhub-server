# 系统预警“删除&过滤”研发方案

## 1. 需求理解

在系统预警“删除”按钮旁新增“删除&过滤”按钮。用户输入“错误消息”关键词后，可一次提交删除当前筛选条件下所有消息模糊匹配的历史预警，同时新增并启用全局消息忽略规则。该操作不限制匹配条数，采用持久化异步任务和分批提交，避免前端 15 秒、MyBatis 30 秒及网关长连接超时造成结果不确定。

本次交付包含页面按钮、确认交互、异步任务接口、任务状态查询、后台分批删除、过滤规则创建、关联站内通知清理和操作审计。不会删除 Elasticsearch 原始日志，不修改 ELK 采集游标，不自动启动或重启应用。需求类型为前后端、数据库和异步批处理混合迭代。

## 2. 功能清单和研发任务

建议禅道标题：`【系统预警】新增删除并过滤异步任务以清理消息噪音`。

| 功能 | 交付内容 | 验收标准 |
| --- | --- | --- |
| 页面入口 | “删除”旁新增“删除&过滤” | 仅有相应权限且消息关键词非空时可操作 |
| 二次确认 | 展示关键词、当前筛选范围、查询结果数量和全局规则影响提示 | 用户可在提交前明确删除范围及过滤范围 |
| 异步任务 | 每次提交立即返回独立任务 ID，状态接口返回进度和结果 | 长任务不依赖单次 HTTP 长连接，运行期间可继续提交其他任务 |
| 过滤规则 | 创建或复用启用的 `IGNORE/MESSAGE/ANY` 精确关键词规则 | 后续采集消息命中关键词时被忽略 |
| 历史清理 | 按当前业务线、环境、服务、级别、事件分类、时间及消息关键词删除 | 不限制总条数，按批处理，不一次加载全量 ID |
| 通知联动 | 按事件源 ID 精确删除同业务线、同环境的 `ELK_ERROR` 站内通知 | 不按文案宽泛删除通知，不跨环境误删 |
| 审计与恢复 | 持久化任务状态、累计数量、失败原因并写操作审计 | 失败可看到已完成进度，按钮恢复可重试 |

### 2.1 涉及系统

- 前端：`workhub-web` 系统预警页面、API、类型。
- 后端：`workhub-controller`、`workhub-service`、`workhub-dao`、`workhub-model`。
- 数据库：新增任务表；读取和删除 `ops_system_alert_event`、`sys_notification`；读取或新增 `ops_system_alert_rule`、`ops_system_alert_rule_keyword`；新增 `sys_operation_log`。
- Elasticsearch：不删除原始日志，不修改同步游标。
- 外部供应商：不涉及。

### 2.2 现状分析

- 当前 `POST /api/ops/system-alerts/events/batch-delete` 只按选中事件 ID 删除，前端当前页最多选择 1000 条。
- 查询已有 `messageKeyword` 模糊条件，展示口径为 `message -> title -> errorType`。
- 前端 Axios 全局超时为 15 秒，MyBatis 默认语句超时为 30 秒；同步执行全量模糊删除存在超时和结果未知风险。
- 现有删除已改为先查事件引用和通知候选，再在内存精确匹配通知主键，能够避免 `dedupe_key` 后缀函数联表删除超时。
- 现有过滤规则为全局规则，不支持业务线、环境或服务范围。因此确认框必须明确：历史删除遵循当前筛选条件，新增规则对所有业务线和环境生效。
- 当前工作区已有未提交的系统预警和关注业务线改动，本需求只在相关文件上增量修改，不覆盖既有改动。

### 2.3 数据库与数据方案

新增 Flyway 脚本 `V20260825_000100__add_system_alert_cleanup_task.sql`，创建 `ops_system_alert_cleanup_task`：

```text
ops_system_alert_cleanup_task
├─ id BIGINT PK AUTO_INCREMENT
├─ task_no VARCHAR(64) UNIQUE
├─ message_keyword VARCHAR(200)
├─ business_line_code/environment_code/service_name/log_level/event_category（可空筛选快照）
├─ start_time/end_time（可空筛选快照）
├─ status VARCHAR(32)                    PENDING/RUNNING/SUCCESS/FAILED
├─ rule_id BIGINT NULL                   创建或复用的规则 ID
├─ max_event_id/processed_event_id       固定任务上界和断点游标
├─ deleted_event_count/deleted_notification_count
├─ operator_user_name/request_ip/error_message
└─ created_at/started_at/finished_at/updated_at
```

关系图：

```text
ops_system_alert_cleanup_task --记录条件/进度--> 后台清理执行器
后台清理执行器 --创建或复用--> ops_system_alert_rule
ops_system_alert_rule --1:N--> ops_system_alert_rule_keyword
后台清理执行器 --按500条主键批量删除--> ops_system_alert_event
ops_system_alert_event --source_event_id精确定位--> sys_notification
后台清理执行器 --完成后写入--> sys_operation_log
Elasticsearch --不操作--> 原始日志保留
```

- DDL：仅新增任务表及任务状态、任务号索引，不修改历史表字段。
- DML：无发布期历史刷数；业务操作运行时产生任务、规则、审计并删除匹配历史数据。
- 批次：每批最多 500 个事件主键；每批独立事务提交并累计任务进度，避免一个超长事务长期持锁或回滚量过大。
- 上界：规则启用后记录当前匹配范围的最大事件 ID，仅处理 `id <= max_event_id`，保证任务可结束；任务期间新采集数据由已启用规则拦截。
- SQL 超时：任务提交和状态查询保持短请求；后台批次查询单独配置较长语句超时，不依赖全局 30 秒；前端无需把普通接口全局改成无限超时。
- 幂等与并发：同一任务只由 `PENDING -> RUNNING` 条件更新成功的执行器处理；同一关键词已有启用的 `IGNORE/MESSAGE/ANY` 规则时复用，不重复创建。多个任务允许并行，删除主键重叠时以实际受影响行数累计，不因记录已被其他任务删除而失败。
- 失败恢复：已提交批次不回滚，任务记录最后处理 ID、累计删除数和失败原因；用户重新提交相同条件时，从当前剩余数据重新扫描，不会恢复已删数据或重复规则。
- 备份和回滚：发布不刷数据，无数据备份步骤；用户确认后的物理删除不可从 WorkHub 直接恢复，但 ELK 原始日志保留。代码/DDL 可停止使用任务表，生产已执行的删除不能通过代码回滚恢复。
- Flyway 校验：上线后核对 `flyway_schema_history` 中版本、`success=1` 和执行时间；禁止 Java 启动逻辑补表。

### 2.4 页面方案

- 入口：运维监测 -> 系统预警 -> 系统异常/慢 SQL。
- 布局：“查询”“删除”“删除&过滤”三个按钮同级；不改变现有“删除”行为。
- 启用条件：消息关键词去空格后非空，且用户同时具有系统预警删除、过滤规则创建/更新权限或管理权限。
- 操作范围：历史删除完整使用当前查询条件（业务线、环境、服务、级别、事件分类、消息关键词、开始和结束时间），不依赖当前页勾选，也不限制 `dashboard.totalCount`。
- 确认弹框：显示当前查询返回数量，明确数量只是在提交时的预估；提示“过滤规则是全局规则，将影响所有业务线和环境；ELK 原始日志不会删除”。
- 任务状态：提交成功后分别轮询每个任务；成功提示实际删除事件数、通知数和规则 ID，随后刷新当前查询；失败提示已删除数量与失败原因。
- 连续操作：已有任务处于 `PENDING/RUNNING` 时不禁用“删除&过滤”按钮，允许继续按当前或新筛选条件提交其他任务；按钮只在消息关键词为空或无权限时不可用。
- 页面刷新或切页不会中断后端任务；本期不新增任务历史列表，任务结果以按钮状态和消息提示呈现，数据库保留完整记录。
- 不单独制作交互 Demo：页面仅在既有筛选区增加一个同级按钮和标准确认框，替代验证为组件类型检查、生产构建及已登录浏览器路径验证。

### 2.5 接口方案

1. `POST /api/ops/system-alerts/events/delete-and-filter-tasks`
   - 请求：`messageKeyword`（必填，1~200）、业务线、环境、服务、级别、事件分类、开始/结束时间。
   - 返回：任务 ID、任务号、状态、筛选快照、累计删除数量。
   - 权限：`manage`，或同时具有删除、规则创建和规则更新权限。
   - 行为：只创建持久化任务并投递后台执行，快速返回。
2. `GET /api/ops/system-alerts/events/delete-and-filter-tasks/{id}`
   - 返回：状态、规则 ID、处理上界/游标、实际删除事件数、通知数、错误信息及时间。
   - 权限：系统预警查看权限；普通用户只能查询自己提交的任务，管理权限可查询全部。

旧查询和旧批量删除接口保持不变，前后端可分步上线。

### 2.6 业务逻辑方案

原流程：

```text
勾选当前页事件 -> 二次确认 -> 同步按ID删除 -> 等待响应 -> 刷新列表
```

新流程（`[新增]` 为本次改动）：

```text
输入消息关键词并查询
  -> [新增] 点击“删除&过滤”
  -> [新增] 确认当前筛选删除范围和全局过滤影响
  -> [新增] 创建PENDING任务并立即返回任务ID
  -> [新增] 后台启用/复用全局IGNORE规则
  -> [新增] 固定最大事件ID
  -> [新增] 按500条循环：查匹配事件 -> 精确定位通知 -> 分别按主键删除 -> 提交进度
  -> [新增] 标记SUCCESS并写审计；异常则标记FAILED并保留已完成进度
  -> [新增] 页面轮询结果并刷新列表
```

核心规则：

- 必须提供消息关键词，禁止空关键词触发全表删除。
- 模糊匹配与页面查询一致，使用参数化 `LIKE`，不拼接用户输入。
- 历史删除使用当前全部筛选条件；新增过滤规则仅使用消息关键词，因为现有规则模型为全局规则。
- 过滤规则动作固定 `IGNORE`、范围固定 `MESSAGE`、模式固定 `ANY`、启用状态固定为启用；精确关键词相同的兼容规则优先复用。
- 通知仅按事件的业务线、环境、`source_event_id` 精确关联后按主键删除。
- 不把数万或更多事件 ID 一次性传到前端或加载到 JVM；只保留当前 500 条。

备选方案是同步接口配合 Axios `timeout: 0` 和放宽 SQL 超时。该方案仍受反向代理、负载均衡和连接中断影响，客户端无法判断后台最终结果，因此不采用。

## 3. 兼容性方案

旧接口和字段全部保留。后端先上线时旧页面无感；前端先上线而后端未上线时新按钮请求失败但原查询和删除仍可使用。任务表是新增表，历史数据无需迁移。过滤规则继续由现有规则页面可见、可编辑和删除。

## 4. 前置条件

- 方案经用户确认后才能改代码。
- 数据库账号具备 Flyway 建表和业务表读写权限。
- 后台执行器线程池可用；队列满时任务必须标记失败而不是静默丢失。
- 应用启动、重启和发布由用户或发布流程执行，AI 不自行启动。

## 5. 风险评估

| 风险 | 触发条件与影响 | 规避与验证 |
| --- | --- | --- |
| 误删 | 关键词过短或筛选项为空，范围过大 | 关键词必填、确认框展示条件和预估数、权限校验、审计；测试空关键词和全局条件 |
| 全局过滤 | 历史删除有限定范围，但规则全局生效 | 确认框醒目标注；规则页可查；测试其他业务线后续事件被忽略 |
| 长任务 | 数据量大、模糊匹配慢 | 异步持久化任务、500条分批、最大ID上界、较长批次SQL超时；大数据量测试 |
| 部分成功 | 中途数据库或应用异常 | 分批提交并保存游标/数量，失败状态明确；重复提交只清剩余数据 |
| 重复与并发执行 | 同一任务重复投递，或多个任务范围重叠 | 单任务状态条件抢占、主键删除幂等、规则精确关键词复用；并发测试。按钮不因其他任务运行而禁用 |
| 通知误删 | 不同环境 source ID 相同 | 同业务线、同环境、源事件 ID 三者匹配；跨环境测试 |
| 上线兼容 | 前后端版本不一致 | 保留旧接口，新增能力独立；分别验证先后上线 |

## 6. 实施步骤

1. 方案确认后新增 Flyway 任务表脚本和模型。
2. 实现任务 Mapper、事件 keyset 批次查询和规则复用查询。
3. 实现专用线程池、任务提交、分批执行、失败状态和审计。
4. 新增 Controller 提交/状态接口和权限校验。
5. 前端接入按钮、确认、任务轮询、成功/失败状态。
6. 更新事实文档与测试结果。
7. 执行定向测试、全仓编译、前端类型检查、构建和差异检查。

## 8. 上线步骤

1. 上线前完成 `clean package` 并核对迁移脚本唯一版本。
2. 先发布数据库迁移和后端，再发布前端。
3. 核对 `flyway_schema_history`、任务线程池日志和新接口权限。
4. 使用小范围关键词完成一次人工验证，再开放大范围操作。
5. 无需停机；若迁移失败、任务表不可用或权限异常则中止后端发布。

## 9. 回滚方案

- 前端和后端代码可回滚，新任务表可保留，不影响旧功能。
- 正在执行的任务应先等待当前 500 条批次结束，再停止实例；不强制中断数据库事务。
- 已创建规则可在过滤规则页停用或删除。
- 已删除 WorkHub 事件和通知不可直接回滚；必要时依据 ELK 原始日志和采集策略重新导入。
- 不建议回滚删除任务表；如必须删除，需先确认无运行任务并另行评审 SQL。
