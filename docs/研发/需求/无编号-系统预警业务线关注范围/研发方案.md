# 系统预警业务线关注范围研发方案

## 1. 需求理解

系统预警的关注配置由“逐个关注子系统”调整为“按业务线和环境维护关注范围”。关注模式为 `ALL` 时采集整条业务线，模式为 `SELECTED` 时只采集已添加且启用的子系统；没有业务线关注配置时不采集。历史事件仍保留服务维度用于查询、汇总和通知。

本次属于前端、后端、数据库、ELK 定时采集混合改造。不改变过滤规则、慢 SQL 分类、站内通知接收人规则和权限编码，不回溯采集历史日志。

## 2. 功能清单和研发任务

建议禅道标题：`【系统预警】支持按业务线配置全部或指定子系统关注范围`。

- 新增业务线关注范围及子系统、索引、同步状态数据模型。
- 新增关注范围查询和维护接口。
- ELK 采集按关注模式生成查询，事件继续记录实际服务名。
- 系统预警页面将“关注子系统”改为“关注业务线”。
- 迁移旧关注子系统配置，默认迁移为 `SELECTED`，避免上线后扩大采集范围。

### 2.1 涉及系统

- 前端：`workhub-web` 系统预警页面、API 和类型定义。
- 后端：controller、model、dao、service、ELK 日志客户端与采集器。
- 数据库：MySQL Flyway 新增表及历史配置迁移。
- 外部系统：Elasticsearch 查询条件发生变化，不新增外部依赖。
- 定时任务：沿用现有 ELK 系统预警定时入口。

### 2.2 现状分析

当前 `ops_system_alert_subsystem` 一行代表一个业务线、环境和服务，采集器逐行创建 PIT，并强制添加服务精确过滤。同步游标按子系统保存；关注子系统不存在时不会采集。前端在独立页签逐条维护子系统及索引模式。

### 2.3 数据库与数据方案

新增：

- `ops_system_alert_scope`：业务线、环境、关注模式、启停和备注；业务线与环境唯一。
- `ops_system_alert_scope_service`：范围下的子系统名称、服务名和启停状态；范围与服务名唯一。
- `ops_system_alert_scope_index`：范围下的日志索引模式。
- `ops_system_alert_scope_sync_state`：范围级增量游标和最近采集状态。

迁移脚本位于 `workhub-bootstrap/src/main/resources/db/schema/mysql/`。旧配置按业务线和环境聚合，关注模式固定迁移为 `SELECTED`；子系统、启停和备注保留，索引取并集去重；范围启用状态取旧记录最大值；游标取启用子系统最早的成功时间以防漏数。旧表不删除，便于代码回滚。迁移使用 `INSERT ... SELECT` 和唯一约束防止重复数据。

发布前备份四张旧系统预警配置和同步状态表。执行后检查 `flyway_schema_history`、新范围数量、子系统数量、索引数量及重复键。代码回滚时旧版本继续读取旧表；新表暂不删除。

### 2.4 页面方案

入口保持“运维监测 -> 系统预警”。页签改为“关注业务线”，列表展示业务线、环境、关注范围、子系统、索引、状态和备注。新增/编辑抽屉增加 `ALL/SELECTED` 单选；`SELECTED` 下至少保留一个启用子系统。删除最后一个子系统不会自动扩大范围，而是阻止保存。

权限继续复用 `ops:system-alert:create/update/delete/manage`。加载和保存失败沿用 Element Plus 消息提示，删除保留二次确认。交互原型已在方案审核阶段确认。

### 2.5 接口方案

- `GET /api/ops/system-alerts/scopes`
- `POST /api/ops/system-alerts/scopes`
- `PUT /api/ops/system-alerts/scopes/{id}`
- `DELETE /api/ops/system-alerts/scopes/{id}`

保存请求包含 `businessLineCode`、`environmentCode`、`watchMode`、`services`、`indexPatterns`、`enabled` 和 `remark`。`ALL` 允许空服务列表；`SELECTED` 至少包含一个启用服务。旧 `/subsystems` 接口保留但标记兼容，不再作为新页面入口。

### 2.6 业务逻辑方案

- `ALL`：按索引、环境、错误级别和时间查询，不添加服务过滤。
- `SELECTED`：在上述条件上增加服务名 `terms` 过滤。
- 服务名始终从日志源字段读取；缺少服务名的日志不入库并记录采集摘要。
- 一个关注范围使用一个 PIT 和一个游标，首次入库事件按实际服务分组通知。
- 配置内容发生变化时清除范围游标，下一轮从系统配置的初始回看窗口重新采集；事件唯一键保证幂等。
- 整条业务线模式要求索引模式天然按业务线隔离；共享索引在没有可靠业务线字段过滤时不得配置为 `ALL`。

### 2.7 模块与文件计划

- `workhub-model`：关注范围、子系统请求响应和枚举。
- `workhub-dao`：范围 CRUD、采集查询、事件写入和同步状态。
- `workhub-service`：范围校验、事务保存、ELK 查询和采集通知。
- `workhub-controller`：关注范围 REST 接口。
- `workhub-bootstrap`：Flyway 表结构和历史数据迁移。
- `workhub-web/src/types`、`src/api`、`src/views/ops`：类型、接口和页面交互。
- `docs/事实`：架构、接口和 ELK 监控说明。

### 2.8 影响面清单

- 前端页面、API 类型、表单和列表：涉及。
- Controller、DTO、Service、Mapper：涉及。
- 表、索引、迁移数据：涉及。
- 权限编码：不变；显示名称调整。
- 定时采集、ELK 查询、通知汇总：涉及。
- 缓存、消息队列、文件和支付能力：不涉及。
- 历史事件统计：数据不改，读取兼容。

## 3. 兼容性方案

旧表和旧接口暂时保留，前后端同步发布。历史事件继续按原字段读取。新配置不反向写入旧表，因此回滚后使用发布前的旧关注配置；新表数据保留供重新上线使用。稳定一个发布周期后再单独评审旧表和接口收缩。

## 4. 前置条件

- `ALL` 范围使用的日志索引必须只包含目标业务线，或后续补充可靠业务线字段过滤。
- 发布前确认 Elasticsearch 服务字段、环境字段和索引模式。
- 发布前备份旧配置表并审计 Flyway 历史。
- 前后端需要同步上线。

## 5. 风险评估

- 业务风险：错误切换到 `ALL` 会扩大采集范围；通过显式模式、确认提示和索引隔离要求规避。
- 数据风险：游标合并可能重复读取；通过事件唯一键幂等。
- 性能风险：整条业务线单次日志量增大；继续受 `pageSize` 和 `maxEventsPerRun` 限制。
- 兼容风险：新旧接口模型不同；采用新接口并同步发布，旧接口暂留。
- 外部依赖风险：共享索引无法准确区分业务线；不满足隔离前置条件时禁止启用 `ALL`。
- 回滚风险：新配置不回写旧表；回滚使用发布前旧配置并保留新表数据。

## 6. 验收标准

- 未创建业务线范围时不采集。
- `ALL` 无子系统配置时可以保存并采集索引内多个服务。
- `SELECTED` 只采集指定启用服务，空服务列表保存失败。
- 关注模式、索引和子系统变更后从初始回看窗口继续采集且不重复入库。
- 页面按业务线维护范围，事件页仍能按服务查询。
- 系统异常通知、慢 SQL 不通知和过滤规则行为保持不变。
