# 系统预警事件查询与批量删除研发方案

## 1. 需求理解

在系统预警的系统异常和慢 SQL 事件列表中，增加错误消息模糊查询、当前页复选与全选、批量物理删除能力。删除 WorkHub 本地 `ops_system_alert_event` 时，通过事件 `source_event_id` 精确删除关联的 `ELK_ERROR` 站内通知；不删除 Elasticsearch 原始日志。需求类型为前后端混合迭代，不涉及数据库结构变更。

## 2. 功能清单和研发任务

建议研发任务标题：`【系统预警】支持错误消息模糊查询和事件批量删除`。

- 查询：按列表“错误消息”的展示口径模糊匹配，`message` 为空时依次匹配 `title`、`errorType`。
- 列表：有删除权限的用户显示复选框，表头全选仅作用于当前页。
- 删除：后端不设置批量条数上限；前端可选择当前页全部事件，支持每页 20、50、100、500、1000 条，二次确认后物理删除并刷新列表、总数和汇总。
- 留痕：删除与系统操作日志在同一事务写入。

### 2.1 涉及系统

- 前端：`workhub-web` 系统预警页面、API 和类型。
- 后端：系统预警 Controller、Service、Mapper 和请求响应模型。
- 数据库：读取和删除 `ops_system_alert_event`，新增 `sys_operation_log` 审计记录。
- Elasticsearch、定时任务、外部供应商：不改动。

### 2.2 现状分析

现有 `GET /api/ops/system-alerts` 支持业务线、环境、服务、级别、事件分类和时间分页查询，总数、汇总、明细共用一组条件。事件列表无消息条件和删除入口。系统已有 `ops:system-alert:delete` 权限以及系统操作日志能力，可以直接复用。

### 2.3 数据库与数据方案

- 不新增 DDL，不新增 Flyway 脚本，不刷历史数据。
- 批量删除按主键 ID 参数化执行，后端不设置业务条数上限；前端单次最多提交当前页 1000 个 ID。
- 删除事件前，先按事件 ID 查询 `source_event_id`、业务线和环境，再从同业务线、同环境的 `ELK_ERROR` 通知候选集中在内存精确匹配源事件 ID，最后按通知主键批量删除。不再在删除 SQL 中使用 `RIGHT(dedupe_key, ...)` 与多个事件联表；没有源事件 ID 的事件不做消息文案宽泛匹配。
- 通知和事件写操作都按主键分别批量删除，单批最多 500 个主键，但全部批次、两张表和审计日志仍位于同一事务。
- 操作日志记录操作者、权限、动作、选中 ID、实际删除数量和 IP。
- 删除失败时事务回滚，审计日志不单独提交。
- 回滚方式：代码回滚可撤销功能，但已物理删除的事件无法从 WorkHub 数据库恢复；ELK 原始日志仍保留，可在符合采集时间窗口和游标条件时重新采集。

数据关系：

```text
ops_system_alert_event  --按 source_event_id 定位--> sys_notification 关联通知
sys_notification        --先物理删除-------------> 删除
ops_system_alert_event  --再批量物理删除---------> 删除
sys_operation_log       --同事务新增------> 操作审计
Elasticsearch           --不操作--------> 原始日志保留
```

### 2.4 页面方案

- 入口：运维监测 -> 系统预警 -> 系统异常/慢 SQL。
- 首次进入页面时只加载业务线下拉选项，不自动查询系统异常、慢 SQL、关注业务线或过滤规则数据；用户点击查询、按 Enter、切换对应页签或刷新时再加载。
- 筛选区新增“错误消息”，最长 200 字；查询时回到第一页。
- 明细表首列增加复选框，表头支持当前页全选。
- 每页条数增加 500、1000 选项。
- 筛选表单操作区在“查询”按钮同级增加“删除”按钮，按钮不显示选中数量，选中数量只在二次确认弹框中展示。无选择时禁用，无权限时不显示；系统异常汇总页签不显示删除按钮。后端删除失败时恢复提交前的选中 ID 和表格勾选，重新启用删除按钮。
- 删除确认明确提示同时删除可精确关联的站内通知，但不删除 ELK。
- 删除后若当前页已空且不是第一页，自动回到上一页。
- 加载、删除失败继续使用 Element Plus 消息提示。

### 2.5 接口方案

- 修改 `GET /api/ops/system-alerts`：新增可选参数 `messageKeyword`，总数、汇总和明细使用相同条件。
- 新增 `POST /api/ops/system-alerts/events/batch-delete`：请求体 `ids` 不能为空、ID 必须为正数，后端不限制最大条数；返回 `deletedCount` 和 `deletedNotificationCount`。
- 删除接口需要 `ops:system-alert:delete` 或兼容权限 `ops:system-alert:manage`。
- 旧查询调用方不传 `messageKeyword` 时行为不变。

### 2.6 业务逻辑方案

原流程：筛选 -> 查询事件 -> 分页查看。

新流程：筛选（新增消息关键词） -> 查询事件 -> 勾选当前页事件 -> 二次确认 -> **查询关联通知主键 -> 事务内按主键分别批量删除通知和事件 -> 写审计** -> 刷新总数、汇总和明细。

消息模糊查询使用参数化 `LIKE '%keyword%'`，不拼接用户输入。空白关键词按未传处理。重复 ID 在服务层去重；不存在的 ID 不报错，返回实际删除数量。通知候选查询只按业务线、环境和通知类型缩小范围，不在 SQL 中对 `dedupe_key` 执行后缀函数联表匹配。该删除不调整 ELK 采集游标。

### 2.7 模块与文件计划

- `workhub-model`：批量删除请求和响应。
- `workhub-dao`：统一消息条件和主键批量删除 SQL。
- `workhub-service`：参数归一、事务删除、审计。
- `workhub-controller`：查询参数和批量删除接口。
- `workhub-web/src/types`、`src/api`、`src/views/ops`：类型、接口和页面交互。
- `docs/事实`：接口和 ELK 监控行为说明。

### 2.8 影响面清单

- 前端页面、API、类型：涉及。
- Controller、DTO、Service、Mapper：涉及。
- 表字段、索引、Flyway、权限编码：不涉及。
- ELK 采集、同步状态、过滤规则、通知生成：不涉及；事件删除会联动删除可精确关联的历史通知。
- 历史数据兼容：保留；旧查询参数完全兼容。

## 3. 兼容性方案

查询参数可选，旧前端和其他调用方不受影响。删除接口为新增接口。前端先于后端上线时删除请求会失败但不影响查询；后端先上线不影响旧页面。无需灰度开关。

## 4. 前置条件

- 用户具有系统预警查看权限；删除按钮额外要求删除或兼容管理权限。
- 后端与前端发布后需要重新加载页面资源。
- 应用重启由用户或发布流程执行，AI 不自行启动应用。

## 5. 风险评估

- 数据风险：事件和关联通知物理删除后不可从 WorkHub 恢复；通过二次确认、权限、当前页选择和审计降低风险。
- 性能风险：前后通配模糊匹配不能使用普通索引；通过既有业务线、环境、服务、分类、时间筛选及分页控制范围。
- 采集风险：删除后重置采集游标可能重新采集 ELK 中的同一事件；页面明确说明 ELK 未删除。
- 通知一致性：站内通知按采集批次生成，只删除去重键可由所选事件 `source_event_id` 精确定位的通知；不使用消息内容模糊删除。
- 回滚风险：代码可回滚，已删除事件不可直接回滚。

## 6. 实施步骤

1. 扩展查询 DTO 调用链和 Mapper 条件。
2. 新增批量删除请求、接口、事务和操作审计。
3. 增加后端服务及控制器测试。
4. 接入前端查询字段、复选框、全选、删除确认和刷新逻辑。
5. 更新事实文档和测试记录。
6. 执行后端定向测试、编译、前端类型检查和生产构建。

## 7. 测试用例验证

测试计划和真实执行结果记录在同目录 `测试用例.md`。

## 8. 验收标准

- 输入错误消息片段后，总数、汇总和事件明细均只统计匹配事件。
- 当前页可以单选、全选，跨页不保留选择。
- 无删除权限不展示复选框和删除按钮。
- 空选择不能提交；空 ID、非正 ID 被后端拒绝；超过 100 条仍可删除。
- 删除成功返回实际数量，页面刷新且操作审计可查询。
- 可精确关联的站内通知与事件同事务删除，ELK 原始日志未删除。
