# WorkHub 后端实施路线

## 1. 实施目标

后端第一阶段要交付一套可供前端接入的稳定 API 和数据模型，先完成台账闭环，再接外部来源和结构化增强能力。

## 2. 里程碑

### M1. 工程基线

- 初始化 Spring Boot 4 工程
- 接入 MyBatis、Druid、MySQL
- 接入统一异常处理、统一响应、基础日志
- 建立用户登录和 JWT 骨架

### M2. 核心领域

- 用户表
- 项目表
- 迭代表
- 版本表
- 工作项表
- 跟踪记录表
- 状态流转日志表
- 附件表
- 支付渠道、商户、参数、敏感凭据、秘钥、项目绑定、多用途和关联商户关系表

### M3. 主业务 API

- 登录接口
- 项目管理接口
- 迭代管理接口
- 版本管理接口
- 工作项列表、详情、创建、编辑接口
- 跟踪记录接口
- 状态流转接口
- 支付渠道、商户、项目绑定、参数、敏感凭据、秘钥管理接口

### M4. 收件与整理

- 企微回调接入
- 待整理箱入库
- 审批型结构化字段抽取
- 需求截图/附件上传接口
- 异步 enrichment 状态查询
- 需求阶段动作接口
- 数据提取/运维类需求 SQL 草稿生成接口
- 系统配置接口
- 研发需求 GitLab 代码影响分析接口
- 研发需求项目知识库需求迭代 Markdown 沉淀与辅助检索
- 研发工作项草稿确认创建接口
- 禅道同步预留接口

### M5. 通知与稳定性

- 群机器人通知
- 到期提醒
- 幂等控制
- 日志补充
- 初始化脚本与部署说明
- 支付配置审计日志、敏感凭据维护和秘钥轮换留痕
- GitLab 仓库配置加密存储
- 研发拆解草稿与正式工作项创建留痕

## 3. 开发顺序约束

1. 先建领域表和核心 API，再接企业微信和结构化增强。
2. 先实现截图/附件录入闭环，再做自动收件。
3. 先保证正式工作项流程稳定，再扩展通知和提醒。
4. 任何外部集成失败都不能影响核心台账可用性。
5. 支付配置管理先交付静态配置与绑定闭环，再扩展真实支付网关校验与路由能力。
6. 研发需求任务评估先人工确认评估工时和测试工时，AI/人工任务拆解作为辅助；存在任务项时再经人工确认创建正式工作项，禁止 AI 跳过确认。
7. 禅道同步先保留接口和状态，真实写入需等禅道配置、字段映射和失败重试策略确认后再落地。

## 4. 验收基线

1. 用户可以登录并访问受保护接口。
2. 可以完整管理项目、迭代、版本、工作项。
3. 工作项可以写跟踪记录并做状态流转。
4. 企业微信回调内容可以落入待整理箱。
5. 结构化增强可以补齐审批型需求字段，且结果需人工确认后才能进入需求阶段流转。
6. 数据提取/运维类需求可以生成只读 SQL 草稿，但系统不连接业务库、不执行 SQL，执行前必须人工确认。
7. 研发需求可以按项目组读取 GitLab group 下全部仓库代码，生成工作项草稿、改动点、涉及系统标签、工时和负责人建议；至少可人工确认评估工时和测试工时推进到待排期，存在任务项时人工确认后创建正式工作项。
8. 状态变更和指派动作可以触发企微通知。
9. 可以按项目、用途查询当前生效的支付商户绑定，并查看脱敏后的参数、敏感凭据、秘钥版本和关联商户关系信息。
