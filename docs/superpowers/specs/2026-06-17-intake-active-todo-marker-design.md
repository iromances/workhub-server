# 需求管理待办明显标记设计

## 背景

需求管理已经支持在详情页维护需求待办，但列表页目前不能直接看出某条需求是否还有待处理事项。用户需要在需求管理列表扫描时快速发现“有待办”的需求，并在进入详情后看到一致的待办提醒。

## 范围

本次只增强需求管理中已有待办的可见性，不改变待办表结构、待办状态流转、需求阶段流转和现有增删改接口。

## 统计口径

明显标记只针对未完成待办：

- 纳入统计：`待处理`、`处理中`
- 不纳入统计：`已完成`、`已取消`

字段命名采用 `activeTodoCount`，表示当前仍需要跟进的待办数量。

## 后端设计

`GET /api/intake` 的列表摘要响应增加 `activeTodoCount` 字段。

数据来源为 `pm_intake_todo`，按 `intake_id` 关联需求记录，统计未删除且状态在 `待处理/处理中` 内的记录数。列表接口现有排序、筛选和分页语义不变。

后端需要调整：

- `IntakeRecordEntity` 增加 `activeTodoCount`
- `IntakeSummaryResponse` 增加 `activeTodoCount`
- `IntakeMapper` 列表查询增加待办数量子查询或聚合字段
- `IntakeService` 组装摘要时透传该字段
- 控制器或服务测试补充列表摘要待办数量断言

## 前端设计

前端 `IntakeSummary` 类型增加 `activeTodoCount`。

列表页同时做三类视觉增强：

1. 需求标题旁显示醒目标签 `待办 N`，仅 `activeTodoCount > 0` 时显示。
2. 需求 tooltip 增加“未完成待办 N”信息。
3. 有未完成待办的表格行增加浅色背景和左侧强调线，保证扫视时可见。

详情页做一致性增强：

- “需求待办”Tab 标题显示未完成数量。
- 待办表格中 `待处理/处理中` 的状态标签使用更醒目的样式。
- 明细仍展示全部待办，避免隐藏已完成历史。

## 样式原则

- 使用橙红色系作为待办提醒色，区别于需求状态标签和识别状态圆点。
- 行高亮保持浅背景，避免干扰表格阅读。
- 标记必须固定尺寸、文本短，不让需求标题列抖动。

## 验证计划

- 后端测试：列表摘要返回 `activeTodoCount`，只统计 `待处理/处理中`。
- 前端测试：补充待办数量辅助函数，验证未完成数量判断与 Tab 文案。
- 构建验证：运行前端构建或类型检查；必要时运行后端相关模块测试。
- 手工验证：打开需求管理列表，确认有未完成待办的行同时出现标签、tooltip 信息和行级高亮；进入详情确认 Tab 数量一致。

## 回滚方案

回滚本次后端摘要字段、前端类型和样式改动即可。数据库结构不变，无需数据回滚。
