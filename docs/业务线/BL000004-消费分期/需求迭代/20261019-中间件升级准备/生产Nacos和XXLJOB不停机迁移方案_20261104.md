# 消费分期生产 Nacos 和 XXL-JOB 不停机迁移方案

日期：2026-11-04。业务线：BL000004 消费分期，GitLab 组 asset-plateform。沿用需求编码 REQ-428dadce-1c72-4d7d-9eb7-d4233554e6c7，作为现有中间件升级需求的生产切换补充。

采用新旧两套应用并行部署：旧应用继续连接旧 Nacos 和旧 XXL-JOB，新应用连接新 Nacos 和新 XXL-JOB。新侧完整就绪后逐步切换在线流量，再交接 XXL-JOB 调度。用户已确认可以临时部署完整新版本，在线业务不停机，定时任务允许短暂延后、必须补齐；新旧应用使用同一套 MQ，沿用现有消息设施，不安排独立的 MQ 迁移或交接阶段。amp-wolease 不纳入迁移。

本次交付为可评审方案，尚未执行生产变更。实施前需填齐本文的实例、入口、依赖、任务和回退记录。历史方案的“暂停业务入口、统一切换全部应用”不适用于本次不停机目标；版本与已经完成的代码改造记录继续沿用。

## 并行期间的连接关系

| 链路 | 旧应用 | 新应用 |
| --- | --- | --- |
| 配置和服务发现 | 旧 Nacos | 新 Nacos |
| 执行器注册和结果回调 | 旧 XXL-JOB | 新 XXL-JOB |
| 在线请求 | 初始全部流量，逐步减少 | 初始无入口流量，逐步增加 |
| 定时任务 | 交接前继续执行 | 交接前全部停用，并限制人工/API 触发 |
| MQ 消费 | 继续消费现有队列 | 依赖就绪、并行消费兼容性验证后，按既有模型加入同一套 MQ |
| 其他后台工作 | 按现有机制运行 | 启动扫描、独占定时任务等遵循原有单实例或分布式互斥规则 |

两侧共用业务数据库、业务缓存、会话和原有幂等键；不按新旧环境拆分业务去重记录。实例工作目录、HTTP/执行器端口、PID、Nacos 客户端缓存和任务日志目录分开，不能让两个独立中心相同 logId 写进同一个执行器日志目录。

Nacos 的 serverAddr 多地址必须属于同一个集群。不能混填独立的新旧中心，也不能将旧中心域名直接切到新中心后，假定服务实例自动迁移。[Nacos 2.5 SDK 参数](https://nacos-group.github.io/docs/v2.5/manual/user/java-sdk/properties/)

XXL-JOB 注册和回调会遍历 admin 地址，成功后结束尝试，并非向两个独立中心双写。两个独立数据库中的 logId 不构成共同身份；新旧中心不得混填到一个执行器地址列表，也不能通过同一个入口随机转发到两套独立库。[2.5.0 注册实现](https://github.com/xuxueli/xxl-job/blob/2.5.0/xxl-job-core/src/main/java/com/xxl/job/core/thread/ExecutorRegistryThread.java)、[回调实现](https://github.com/xuxueli/xxl-job/blob/2.5.0/xxl-job-core/src/main/java/com/xxl/job/core/thread/TriggerCallbackThread.java)

## 新旧环境具体在哪里切换

用户已确认生产入口使用 Nginx/HAProxy 等反向代理，具体产品及版本尚未唯一确认。在线请求就在现有反向代理上切换。保持业务域名不变，准备两组后端：旧 amp-gateway/amp-op-gateway 与新 amp-gateway/amp-op-gateway。旧网关及旧应用始终使用旧 Nacos，新网关及新应用始终使用新 Nacos。将请求转给新网关后，该网关通过新 Nacos 发现并调用新服务；前提是相关路由和下游调用均已核实归属新侧，固定 URL 另行核对。

| 动作 | 入口上游调整 | 中间件及应用状态 |
| --- | --- | --- |
| 准备 | 业务请求继续指向旧网关，新网关单独验证 | 两套应用已启动，分别连接各自 Nacos；旧 XXL 调度、新 XXL 停用 |
| 灰度 | 增加指向新网关的路由或权重，先少量请求再逐步增加 | 两套保持运行，不修改旧应用的 Nacos 地址 |
| 完成在线切流 | 将全部目标新请求转到新网关，旧上游摘流 | 等待旧请求和长连接结束，保留旧应用及回切能力 |
| 交接调度 | 不需要再次调整网关入口 | 旧 XXL 停触发并收敛、隔离后，新 XXL 按清单启用 |
| 在线回退 | 将入口上游恢复为旧网关 | 使用仍在运行的旧应用和旧 Nacos；调度另按回退规则处理 |

若入口为 Nginx，实际操作是调整业务域名对应的 upstream/路由并校验后平滑 reload；旧 worker 继续处理已有客户端，新 worker 使用新配置。达到全量时从新配置中摘除旧上游或标为 down，不通过停止旧应用来强行切流。[Nginx 配置重载](https://nginx.org/en/docs/control.html)、[上游权重和 down](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)

以下以 Nginx 默认加权轮询、一个旧网关与一个新网关为示例。只说明后端状态变化，不能直接套用未知的现网配置；多个实例时按两组总权重分配，保留现有会话策略并以访问日志核对实际流量。

| 阶段 | 旧网关条目 | 新网关条目 | 执行动作 |
| --- | --- | --- | --- |
| 准备 | 启用 | down | 新环境单独验证，生产新请求仍走旧侧 |
| 小流量 | weight=95 | weight=5 | 校验配置后平滑 reload，观察新侧请求和业务结果 |
| 逐步放量 | 逐步降低权重 | 逐步提高权重 | 每档通过既定验收后再继续 |
| 全量 | down，或从新配置中移除 | 启用 | 平滑 reload，等待旧 worker、在途请求及长连接结束 |
| 回退 | 恢复启用 | down，或从新配置中移除 | 平滑 reload，将后续请求重新交给旧侧；仍需处理新侧在途请求 |

Nginx 的全量摘流用 down/移除表示，不使用 weight=0。两个网关及每个对外/内网域名的后端分别核对；有多个代理节点时逐台按同一目标状态发布，确保不会有遗漏节点持续送往旧侧。运维按正在运行的实例、二进制和配置路径执行语法校验及 reload，不重启整个代理服务。TLS、Host、路径和转发头沿用原入口契约。HAProxy 使用其对应的后端管理方式，不套用上表的 Nginx 指令。

落地操作清单只需登记：代理产品/版本及实例、业务域名、对应后端池、旧网关 IP/端口、新网关 IP/端口、原状态、目标状态、校验/重载方式、验证结果和回退负责人。配置正文仍不在本轮读取范围。

网关入口切流不会改变其他系统通过旧 Nacos 直接调用的目标，也不会控制共享 MQ 的消费分配。这两类路径分别按本文的跨业务线依赖和共用 MQ 检查处理。生产 Nacos 控制台没有一个能把所有请求统一从旧环境切到新环境的总开关。

## 第一阶段 准备新中间件

旧侧持续服务，仅冻结配置和任务定义变更，不冻结用户业务。必须发布的配置变更由负责人登记并同步两侧，分别校验；保留两侧有意不同的中间件地址、凭据和待命开关，不整份互相覆盖。

### Nacos

1. 按 2.5.4 目标结构准备独立数据库。保留 namespace ID、group、dataId、类型及业务含义；命名空间同名不等于 ID 相同。灰度、标签、权限等实际在用能力单独列入迁移范围。
2. 优先采用已验证的官方导入/发布流程。若沿用现有 SQL 脚本，在新中心未启动、尚未承载客户端时完成导入，再启动并确认全量 dump 成功。新中心已服务其他业务时，不采用停中心或在线直接写库的方式迁移本次配置。
3. 新应用启动前，由有权限的运维逐项比对必需配置键和内容摘要，再从实际 SDK 路径验证可读取；有多个节点时逐节点验证。列表和数据库条数正常不能替代实际拉取。仅留存键、摘要及成功/失败结果，不记录正文与凭据。
4. 核对每个应用到新 Nacos 的主端口及主端口加 1000 的 gRPC 通路，包括代理和映射；服务端内部通信按实际部署核对。鉴权在首次配置拉取前可用，生产凭据独立管理，不复用测试参数。[官方端口及兼容性说明](https://www.nacos.io/zh-cn/docs/upgrading/2.0.0-compatibility/)
5. 配置迁移不等于实例迁移。由新应用重新注册，验证地址、健康、分组、集群和路由所需元数据。

## 第二阶段 启动完整新应用并核对依赖

按实际调用图先准备被调用服务，再准备调用方和网关；循环依赖作为一组完整启动。新应用同时使用新 Nacos 客户端和新 XXL-JOB core，新中心任务保持停止，不依赖新版 core 混接旧中心。

待命验证包括配置拉取、需要注册的服务发现、只读调用、依赖连接、会话、鉴权、执行器注册、容量及日志。生产使用批准的只读冒烟，不通过真实扣款、放款、签约、通知或重放写请求验证连通性。任务参数、失败反馈、幂等和补跑在隔离测试中演练。

跨业务线按方向处理，在新侧承接相关流量前落实：

| 调用方向 | 过渡办法 | 退出条件 |
| --- | --- | --- |
| 新消费分期调用未迁移服务 | 固定生产 URL 保持可达；服务名依赖提供经验证的稳定代理入口，或经过兼容性演练的实例同步机制 | 新侧不再依赖旧应用；旧注册中心作为同步来源时仍需保留 |
| 其他业务线通过固定 URL 调用消费分期 | 域名、路径、TLS 和鉴权契约不变，由代理灰度切上游 | 旧上游无新增请求且在途完成 |
| 其他业务线通过旧 Nacos 服务名调用消费分期 | 初期保留旧应用；之后在旧注册中心接入通往新服务的稳定代理入口，验证后逐个摘除旧实例 | 旧消费者完成发现刷新，旧实例实际请求归零 |

桥接入口须有健康检查并保持服务身份及必要元数据；仅对已确认协议采用对应代理。不得将固定 IP 永久标为健康，不引入未经演练的双向同步形成回环。使用同步时须覆盖健康变化、删除事件、命名空间映射和原始实例来源。增加桥接入口可能立即引入流量，纳入灰度操作。完整新集群不能自动解决跨业务线的旧注册中心调用。

## 第三阶段 灰度切换在线流量

1. 在现有入口代理调整新旧网关或上游权重，保持外部域名和回调地址。候选梯度为 1% → 5% → 20% → 50% → 100%，按用户、租户或会话维持必要的稳定路由。低流量系统以覆盖真实关键路径为准。
2. 每档观察关键接口成功率、P95、业务状态、会话、注册发现、连接池和 MQ 积压。无现行标准时，供评审的初始阈值：错误率增加 0.5 个百分点或 P95 增长 20%，持续 5 分钟即停止放量并回退；每档至少 15 分钟且具备足够请求样本。正式阈值按现有 SLO 和业务量填写，上述不是已确认承诺。
3. 重复资金动作、串写、配置串环境、核心链路持续失败，立即停止放量并按范围隔离、回退，不等待观察时长。
4. 旧中心仍承担原调度；新旧应用可按验证过的既有消费模型使用同一套 MQ。HTTP 灰度权重不控制消息消费比例，新消费者接收消息前须确认其新 Nacos 调用依赖就绪。不镜像生产写请求，不因失败无条件重试资金请求。
5. 两个网关、直接服务调用、异步回调和内网接口分别验收。“网关 100%”不代表全部入口切完，不能据此关闭旧应用。

## 共用 MQ 的应用发布检查

用户已确认继续使用同一套 MQ。保持现有 vhost、队列、交换机/绑定及声明属性，消息不搬迁，不新增一套按新旧环境区分的队列。MQ 相关检查属于应用发布验证。

1. 若两套应用消费同一 vhost 下的同一普通队列，按既有竞争消费方式并行运行，消息由队列分发给消费者，无需专门停旧开新的 MQ 切换窗口。若应用各自创建不同队列或使用广播订阅，需确认符合原业务意图，不能仅凭连接同一 MQ 判断不会重复处理。[RabbitMQ 消费者分发](https://www.rabbitmq.com/docs/consumers)、[交换机路由](https://www.rabbitmq.com/docs/exchanges)
2. 核对新旧消息兼容性、业务幂等、顺序/独占要求、消费容量及 ACK。竞争消费不等于端到端恰好一次；手动确认模式下，连接关闭时未确认的消息可能重新入队并再次投递。[RabbitMQ 确认与重投](https://www.rabbitmq.com/docs/confirms)
3. 新消费者加入前保证新侧依赖完整可用；HTTP 灰度比例不能限制它从 MQ 获得的消息。旧应用退出时正常停止接收新消息，等待在途处理及 ACK，再关闭进程，由剩余消费者继续处理。
4. 公共消息重投任务若由 XXL-JOB 触发，随下述调度中心统一交接，始终只有一个中心负责；不另建 MQ 交接步骤。Spring 定时任务、启动扫描等按既有互斥规则验证。

## 第四阶段 交接 XXL-JOB 调度

以完整任务依赖链为切换单位。初次优先整体交接消费分期范围的相关链，不把父子任务拆到两个中心；没有跨组依赖的链才可分批。旧中心共用时仅操作本次确认范围。

| 顺序 | 操作 | 放行条件 |
| --- | --- | --- |
| J1 | 冻结最终定义和原启停快照，登记最后完成的业务批次、下一计划时间和冻结时点 Tf | 新旧映射一致，新侧无任务执行 |
| J2 | 限制人工/API 触发，停止旧侧新的计划触发 | 登记目标任务停止时间，旧中心继续收旧回调 |
| J3 | 等待预读/触发队列、执行器队列、在途任务、重试、父子链和回调收敛 | 无未决结果、待回调及后续重试/子任务，业务结果可核对 |
| J4 | 设置旧侧最终触发隔离 | 旧中心不能再有效执行本范围任务，新中心没有执行旧实例的路径 |
| J5 | 复核新执行器地址、handler、参数、凭据匹配和依赖，完成必要的前置批次补跑 | 旧侧已隔离，同一业务批次不重叠 |
| J6 | 按启停快照和依赖顺序恢复新侧任务，登记首个计划时点 Tn | 原 STOP 保持，子任务关系保留，执行与回调归属新侧 |
| J7 | 核对首轮业务结果和期间缺失批次 | 缺失批次已补齐、重复执行已排除、结果不明已查明并闭环，全部留证 |

J3 不能只等待固定 5 秒。旧 2.2.0 存在提前预读，失败监测还会发起重试，控制台停用不能证明这些工作消失。[旧版预读](https://github.com/xuxueli/xxl-job/blob/2.2.0/xxl-job-admin/src/main/java/com/xxl/job/admin/core/thread/JobScheduleHelper.java)、[旧版重试](https://github.com/xuxueli/xxl-job/blob/2.2.0/xxl-job-admin/src/main/java/com/xxl/job/admin/core/thread/JobFailMonitorHelper.java)

J4 在演练中落实具体手段：旧中心仅服务本范围时，可在回调全部完成后停止旧调度中心，旧业务应用继续服务；共用时采用仅针对目标执行器的网络/API 执行通路隔离，覆盖每个中心节点、手工及外部触发路径。隔离在 J3 完成后生效，不能阻断回调后假装结束。隔离不能证明有效时，不启新侧任务。

J3 超过本批允许延后预算，或存在资金结果不明的执行，不强杀后交接；停止推进，保留旧侧完成处理，必要时撤销交接并按台账恢复旧调度。用户同意短暂延后，具体分钟数依据最大耗时和演练结果确定。

历史清结算任务 13 与任务 8 的关系按最终 child_jobid 核实。任务 8 原为 STOP，并不代表不会被父任务触发；保留关系，不将所有子任务改为 Cron 启用。[2.5.0 父子任务处理](https://github.com/xuxueli/xxl-job/blob/2.5.0/xxl-job-admin/src/main/java/com/xxl/job/admin/core/complete/XxlJobCompleter.java)

## 漏跑任务补齐规则

逐任务按计划时间及业务批次核对，从最后已确认完成批次覆盖到新中心稳定接管。资金、通知、账务任务结合业务结果判断，不只看调度成功状态。结果不明先查明，不直接重发。

| 台账字段 | 内容 |
| --- | --- |
| 身份 | 执行器、任务 ID、handler、参数摘要、父子链、负责人 |
| 时间 | Cron/时区、计划时点、业务日期/账期、Tf、Tn |
| 已执行证据 | 旧/新中心各自日志 ID、业务批次号、结果和核对依据 |
| 差额处理 | 缺失/已完成/结果不明、是否补跑、显式业务日期或批次、前置条件 |
| 完成证明 | 执行方、结果、业务去重/对账结论及复核人 |

持续扫描未处理数据的任务，经验证可合并追平；按日、月或批次生成结果的任务按缺失期间补齐，并遵循依赖顺序。handler 若只使用当前时间、不能指定缺失日期，也不能自然追平，需先准备验证过的补偿方法，不能直接点击一次执行。原 STOP 独立任务不因迁移统一启用。

已有迁移映射使用 DO_NOTHING，不能期待自动补齐暂停期间的任务；即便 FIRE_ONCE_NOW，也不是重放所有缺失批次。启动任务会重新计算未来执行时间，仍须维护台账。[2.5.0 错过调度处理](https://github.com/xuxueli/xxl-job/blob/2.5.0/xxl-job-admin/src/main/java/com/xxl/job/admin/core/thread/JobScheduleHelper.java)、[任务启动](https://github.com/xuxueli/xxl-job/blob/2.5.0/xxl-job-admin/src/main/java/com/xxl/job/admin/service/impl/XxlJobServiceImpl.java)

依赖过去批次的任务先补前置再开放后续周期。补跑与正常调度使用相同业务锁和幂等键，不在两套中心分别补同一批。

## 回退步骤

| 时点 | 操作顺序 |
| --- | --- |
| 新侧未接流量 | 保持旧侧工作，新侧停止推进并修复，不改生产入口 |
| 已切流，新中心尚未调度 | 入口和桥接路由回旧应用，等待新侧在途完成，旧应用及旧中间件继续工作 |
| 新中心已调度 | 先限制新触发，等执行、重试、子任务和回调收敛，隔离新执行通路；核对新侧已完成和未决批次后，才恢复旧侧需要的任务 |

流量与任务可以分别回退：在线异常优先回旧入口，不自动同时启用旧中心。按已演练的混合运行兼容性处理。

新应用若已参与 MQ 消费，回退该应用时还需停止其接收新消息、处理完在途及确认，再退出进程；旧消费者继续使用同一队列。只回切 HTTP 流量不会自动停止新应用的 MQ 消费，不涉及 MQ 服务、队列或数据的回退。

回退使用保留的旧应用及原配置，不能只把新版 Nacos 客户端地址改回 1.3.2，2.x 客户端不能连接 1.x 服务端。[官方兼容性说明](https://www.nacos.io/zh-cn/docs/upgrading/2.0.0-compatibility/)

不回滚业务数据库，不撤销已发生的支付、账单或通知，不将新 XXL 日志覆盖旧库。回退期配置变更须能被旧版本理解，必要业务配置由负责人双侧维护。超出旧版本兼容范围的后续开发在回退期结束后发布。

## 观察与旧环境退出

建议至少观察 24 小时，并覆盖实际日切、对账及关键周期。未发生的月度任务保留验证安排，不表述为已经生产实跑。最终观察时长以业务周期及验收结果为准。

旧应用退出同时满足：全部入口及跨业务线调用已迁移，旧侧请求及在途归零，旧实例已停止接收 MQ 新消息且在途确认完成，其他后台工作收敛，旧执行器无运行、重试、回调，新侧承载及业务结果稳定。摘除实例后等待实际发现缓存刷新和连接收敛，再停止实例；MQ 服务与队列继续保留。

旧中间件退出与旧应用退出分别决定。旧 Nacos 仍被其他业务或桥接机制使用时保留；旧 XXL 共用时保留其他业务任务。回退期保留旧制品、启动参数、入口回切能力及容量，旧中心不再产生本范围执行。最终释放资源前完成回退能力确认及业务验收。
