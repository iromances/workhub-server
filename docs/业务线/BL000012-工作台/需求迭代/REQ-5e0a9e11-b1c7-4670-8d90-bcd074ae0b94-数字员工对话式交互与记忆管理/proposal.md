## 1. Why：背景与问题

- 当前问题及证据：
  1. 交互是批处理，不是对话。页面路径是员工列表 →「任务成果」弹框 →「开始新一轮」→ 手动刷新 → 读报告（workhub-web `src/views/agent/AgentWorkbenchView.vue` L121–L138、L200–L210、L244–L283）。与员工沟通的唯一方式是给某一轮运行“补充指令”（`POST /api/agent-tasks/{id}/messages`，写入 `HUMAN_INPUT` 事件）。每轮运行新建一个临时目录和一个 CLI 会话，结束即删除（`AgentNativeCliAdapter.java` L111、L205；`ZCodeCliClient.prepareAgent` L25–L39），没有多轮上下文。
  2. 输出被固定报告契约绑死。任务轮次每次都追加报告展示规范和 Schema v2 全文（`AgentApiExecutionAdapter.prompt()` L138–L140、`AgentNativeCliAdapter.prompt()` L221–L224、`ZCodeAgentCliProtocol.prepare` L23）；结果不合规时再调模型“整理纠正”并改写成 ELI5（`AgentResultFormatter.java` L62–L68、L91–L92）。日常问答和追问也要按“检查、发现、证据、行动”成文。
  3. 没有记忆。临时目录用完即删，员工不记得此前会话里交代过的事；职责是唯一的长期信息。
  4. 没有服务端推送。两个仓库都没有 SSE 或 WebSocket（server 无 `SseEmitter`，web 无 `EventSource`）；11-22 起任务成果只能手动刷新（REQ-a473b3fe，原因是 5 秒轮询在运行结束后仍然空转）。对话需要只在该轮执行期间推送。
- 受影响用户/角色：数字员工使用者（`agent:view`、`agent:task:view`、`agent:task:operate`、`agent:manage`）。
- 不解决的后果：员工只能按“一轮一报告”使用，追问要重新交代背景；11-22 建立的固定报告结构继续主导每次输出，提示词越叠越厚，和“配置好职责、直接对话”的使用方式背离。

## 2. What：目标与范围

### 本期目标

1. 对话优先。进入某位员工就是对话框：发一条消息，员工执行一轮运行，回复在会话里流式出现，过程可展开；同一会话内多轮上下文延续；关闭页面或重启服务后会话仍在。
2. 子菜单管理。员工页内左侧子导航：「对话」（会话列表与对话内容，默认页）、「历史」（做过的事：历次运行与报告，含巡检轮次、需求开发、问题修复和对话轮次）、「记忆」（员工记住的内容）、「配置」（身份、岗位、职责、授权、模型、执行设置）。
3. 其余保留。巡检轮次（手动与周期）、固定报告、预警推送、需求自动开发、问题修复的链路、提示词模板和契约不变，统一归入「历史」。
4. 提示词回到对话本身。对话轮次的输入是员工配置生成的工位指引加用户消息，不再拼接报告 Schema、展示规范和整理纠正指令。
5. 企业视角下的个人员工。每个人都可以创建自己的数字员工（持有 `agent:view` 即可，页面入口随之放开），员工仅归属人与管理员（`agent:manage`）可见；本期不做共享机制，需要类似能力时各自创建。
6. 对话驱动闭环。在会话里用自然语言设定或取消本员工的定时执行（写入职责执行任务的 CRON 调度，由平台调度器到点派发）；职责执行任务的任务轮次完成后，报告摘要回贴到归属人的会话；在会话里要求把问题立为工单时经 MCP 工具创建，并可查询工单。
7. 交付物通道。员工在会话里生成的文件（定制 HTML 报告、CSV/Excel 等）可经 MCP 工具 `submit_deliverable` 交付：校验（工位目录内、类型白名单、大小与数量上限）后存入数据库，会话消息与运行详情显示附件卡片，可下载，HTML 支持沙箱预览；与平台渲染的消息导出并存。

### 本期交付范围

1. workhub-server
   - 会话与消息的表和接口；对话轮次挂在员工的职责执行任务上，沿用排队、租约、取消、预算和审计。
   - 原生会话续接：ZCode `session/resume`、Codex `exec resume`；原生会话不可用时由平台回放对话历史；API 通道每轮单次调用并回放历史。
   - 每位员工一个固定私有工位目录（工作区、会话库、平台生成的 `AGENTS.md`）。
   - 平台级记忆：记忆文件存放于员工工位目录内（平台所有，Markdown + `MEMORY.md` 索引）；ZCode 通道把 CLI 记忆根指向该目录原生读写，Codex 通道经 WorkHub MCP 记忆工具读写，API 通道只读注入；记忆子菜单读写同一目录。
   - 员工归属与创建：员工列表按归属人过滤（管理员可见全部）、创建接口与页面入口对 `agent:view` 放开（归属创建人）；复用 `owner_name`，无新增字段。
   - 对话轮次的运行事件 SSE 推送。
   - 对话驱动闭环：MCP 工具 `update_duty_schedule`（对话设/取消定时）、`create_issue` 与 `list_issues`（对话建/查工单）；职责执行任务的任务轮次完成后把报告摘要回贴到归属人会话并渲染为报告卡片。
   - 交付物通道：`submit_deliverable` MCP 工具、`pm_agent_deliverable` 表与库内存储（MEDIUMBLOB + SHA-256）、下载接口、审计与上限校验。
   - 新增提示词场景 `agent.chat.context` 及其迁移。
2. workhub-web
   - 员工工作台与四个子页；员工列表入口调整。
   - 复用现有报告渲染器、运行面板、配置表单和执行设置表单。
   - 对话消息与会话的 HTML 导出（复用任务报告的渲染与打包逻辑，与「下载报告 (HTML)」同源）。
   - 交付物附件卡片（文件名、大小、说明、下载；HTML 沙箱预览）。
3. 文档：`现状.md`、`迭代日志.md`、`workhub-web/docs/frontend-architecture.md`。

### 明确不做

1. 不改任务轮次：巡检轮次、需求自动开发、问题修复的执行链路，`agent.api.step` 与 `agent.cli.step` 模板，固定报告契约、分表存储、预警推送和产物验收都保持原样。
2. 不引入 Mem0/Zep 类记忆中间件（向量库、知识图谱、事实抽取管线）；记忆规模超出目录可管理范围时的检索层另立需求。API 通道无工具调用，记忆只读注入、不写回。
3. 不做长驻 CLI 进程。每条消息仍启动一个 CLI 进程，结束即退出，靠会话续接保持上下文。
4. 不做多实例事件总线；跨实例时按 Design §4 的降级方式处理。
5. 不做会话重命名、置顶、搜索，标题取首条消息；不开放工位目录的自由浏览，文件仅经 `submit_deliverable` 校验后交付；平台渲染的消息导出并存。
6. 不新增权限码，不安装依赖。
7. 不做员工共享（指定人或全员）、跨员工的团队记忆与共享知识库；后续按需另立需求。

### 约束与依赖

- 依赖的代码和文档：REQ-7fecce00（职责执行任务、按员工列运行）、REQ-72ecd9bc（固定报告，仅任务轮次继续使用）、REQ-46a1aa8e（提示词配置化）、REQ-10c04b69（报告渲染器）。
- 既有系统/接口/数据约束：`pm_agent_run.task_id` 非空且参与触发唯一键，运行必须挂在任务上；系统提示词存于 `ai_use_case_config`，代码只组装变量。
- CLI 版本：ZCode CLI 0.18.0 的 app-server 有 `session/resume`；Codex CLI 0.80.0 有 `exec resume`。两者目前只核对了命令与方法名，行为在实施第一步实测（Tasks T-00）。
- 模型调用经公司 AI server 路由到智谱号池，按调用无状态分配额度；会话与记忆保存在运行 CLI 的 WorkHub 服务器本机，与号池无关。

## 4. 长期方向（非本期范围）

用户 2026-11-28 明确产品定位：对标 OpenAI Dots / Meta Muse 的常驻个人 agent——服务端常驻、有记忆、接企业能力、手机任意终端随时对话。本期 v1.3 即该形态的服务端内核（常驻工位、平台记忆、对话与任务双轮次、企业 MCP 能力与闭环工具、交付物通道）。后续迭代按序：

1. 移动触达（建议下一期）：响应式移动对话页；企业微信对话通道（自建应用收消息回调 → 对话轮次 → 主动回复；预警与回贴摘要已有出站基础）。App/小程序不做，企微即终端。
2. 主动工作（proactive）：定时轮次发现异常时经终端通道主动询问“是否处理”，从预警推送演进出主动建议。
3. 员工共享、跨员工团队知识库、记忆检索层（向量/图，规模超限后）。
