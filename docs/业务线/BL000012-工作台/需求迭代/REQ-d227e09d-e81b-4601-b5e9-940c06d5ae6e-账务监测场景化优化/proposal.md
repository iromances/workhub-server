# Proposal｜账务监测场景化优化

- 需求编码：REQ-d227e09d-e81b-4601-b5e9-940c06d5ae6e
- 需求名称：账务监测场景化优化
- 目录：`docs/业务线/BL000012-工作台/需求迭代/REQ-d227e09d-e81b-4601-b5e9-940c06d5ae6e-账务监测场景化优化/`
- 涉及仓库：workhub-server（本仓库）、workhub-web（前端）
- 日期：2026-11-18

## 背景

REQ-67108299 落地的账务监测按"业务线+环境+系统"配置，用 `SAPS_BILL_CHAIN` 14 条规则经生产 MCP 只读网关扫账单/缴费单/支付订单/结算明细/对账单/交易流水做数据一致性校验，并每日 06:30 自动对账。该方式存在两个问题：

1. 扫表一致性校验重、口径硬编码，发现的是数据质量问题而非业务流程异常，业务价值有限。
2. 每日自动扫生产库的调度方式不合适，应默认关闭、显式开启。

用户要求：删除通过生产 MCP 只读通道检查账单、对账单和交易数据的方式；监测改为按业务场景维度配置（批量代扣/代偿/回购/支付/清分结算），以代扣场景为例核对"每天什么时候扣、应发起多少笔账单扣款、实际扣多少"。

## 目标

1. 删除扫表对账执行链（`AccountingReconcileExecutor`/`AccountingRuleCatalog`/执行凭据服务/每日 Job/`OPS_ACC_*` 种子），历史运行数据保留只读。
2. 自动调度默认关闭：调度体系支持 Job 种子默认停用，场景核对 Job 与场景配置均默认 `enabled=0`。
3. 账务监测重构为场景维度配置：场景类型（批量代扣/代偿/回购/支付/清分结算）+ 预期发生时间 + 核对时间 + 预期/实际/成功笔数的 `func_call_sql` 场景 SQL 编码 + 容差 + 告警开关。
4. 代扣场景落地三段式核对：按时发起、应发起 vs 实际发起、发起 vs 成功；其余四场景框架就绪、SQL 口径待业务方提供后登记启用。

## 范围

- workhub-server：删除旧执行链与规则代码；`WorkhubJob` 支持 `defaultEnabled()`；新增场景配置表/场景核对执行器/场景核对 Job；`AccountingMonitorService`/Controller 按场景字段重写；Flyway 迁移（建新表、清旧配置、禁用 `OPS_ACC_*` 模板、删旧 Job 配置行、登记代扣占位模板）。
- workhub-web：`AccountingMonitorView.vue` 与 `api/accounting.ts` 按场景维度重构。

不在范围：代偿/回购/支付/清分结算四场景的真实 SQL 口径（待业务方提供后经 `func_call_sql` 页面登记启用）；`ops_account_reconcile_run/result/evidence` 历史数据的清理。

## 验收标准

1. 代码中不再存在扫表对账执行链（旧执行器/规则目录/凭据服务/每日 Job 及其测试删除），编译与相关测试通过。
2. 迁移执行后：`ops_account_scenario_monitor` 新表就绪；`ops_account_monitor_config`/`ops_account_rule_config` 清空；`func_call_sql` 中 `OPS_ACC_*` 全部 `enabled=0`；`sys_job_config` 无 `OPS_ACCOUNTING_RECONCILE` 行、种子出 `OPS_ACCOUNTING_SCENARIO_CHECK`（enabled=0）。
3. 页面可按场景维度维护配置；启用前校验 SQL 编码已登记且启用；手动触发代扣场景核对产出三条监测维度结果（按时发起/应发起 vs 实际/发起 vs 成功），结果写入既有 run/result 表。
4. 差异超出容差时按配置推送 WeCom 机器人告警（`alert_enabled` 控制）。
5. 调度默认关闭：新 Job 种子与场景配置默认停用，显式开启后才自动执行。
6. 前端 `npm run build` 与 `vue-tsc` 通过；后端相关模块测试全绿。

## 2026-11-19 补充规格 v2：叉车与智能柜单据及支付交叉核验（已确认）

3. 在账务监测中增加一致性核验入口，SQL 统一登记 FunctionCall；按批准窗口手动执行一次，记录每项覆盖基数、异常数、差额、异常样本、查询失败和未覆盖项。
