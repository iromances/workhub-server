## 3. 任务明细

### T-01：头像存储改造

- 描述与目标：头像内容写入 `pm_attachment`（业务类型 `USER_AVATAR`），上传和读取不再经过磁盘。
- 输入：design §2、§3。
- 输出：`AttachmentService`（新增 `saveUserAvatar`、`loadUserAvatar`、`deleteUserAvatar`，内部保存方法改为返回附件 ID）、`AuthService`（`uploadAvatar`、`loadAvatar` 改走数据库，去掉磁盘读写方法和本地存储配置依赖）。
- 允许修改范围：上述两个类。
- 明确不修改范围：`AuthController` 路径、安全配置、需求附件的保存与读取、前端。

验收条件：

- [x] 条件 1：上传后新增 `USER_AVATAR` 附件行，`storage_path` 为空，头像地址为 `/api/auth/avatars/{附件ID}`。
- [x] 条件 2：按 ID 读取返回内容和上传时的类型；ID 非法或类型不符时报“头像文件不存在”。
- [x] 条件 3：重复上传会删除上一行头像附件。
- [x] 条件 4：类型、扩展名、2 MB 上限的校验结果与改动前一致。

计划验证方式：新增头像存储单元测试。

状态及真实结果：已实施（2026-11-26）。四个条件由 `AuthServiceAvatarTest`（5 个用例）和 `AttachmentServiceTest` 新增的 4 个头像用例覆盖并通过。两点实现细节：

- 删除旧头像时只删业务类型为 `USER_AVATAR` 的记录，头像地址被手工填成其他附件的 ID 也不会误删需求附件。
- 上传、更新头像地址、删除旧头像在 `uploadAvatar` 的同一事务内完成；改动前写文件不在事务内。
