## 1. Why：背景与问题

- 当前问题及证据：
  1. 需求附件自 2026-09 起存入数据库，但仍有本地文件残留，仓库根目录的 `data/` 共 28 个文件、3.4 MB，最后一次写入是 2026-09-01。
  2. 用户头像仍存本地文件：`AuthService.uploadAvatar` 把文件写到 `storage.local-path` 下的 `avatars/`，所以只要有人上传头像，`data/` 就会重新出现。
  3. `pm_attachment` 中有 1 条记录只存了文件路径：附件 ID 355（需求 197 的截图），文件在 `data/uploads/intake/197/`，是唯一副本。
  4. `data/uploads/intake/` 下其余 27 个文件在库里都已有内容，逐个比对 SHA-256 与库内一致。
  5. 另有 294 条 2026-04 至 2026-08 的附件只存了路径（155 张截图、133 个附件、6 个阶段数据文件），对应文件已不存在，现在就无法打开。
- 受影响用户/角色：上传头像的用户、查看需求 197 附件的人。
- 不解决的后果：`data/` 会在上传头像时反复出现；附件 355 只存在于这台机器的文件里。

## 2. What：目标与范围

### 本期目标

1. 头像内容存入数据库，不再写本地文件。
2. 把仅存本地的 1 个附件内容写入数据库。
3. 删除 `data/` 目录和不再使用的本地存储配置。

### 本期交付范围

1. 代码：`AttachmentService` 增加头像业务类型的保存、读取、删除；`AuthService` 的上传和读取头像改走数据库；删除 `StorageProperties` 和 `application.yml` 中的 `workhub.storage.local-path`。
2. 数据：通过现有“替换附件”接口把附件 355 的文件写入数据库。
3. 清理：删除 `data/` 目录。
4. 测试与文档：新增头像存储测试；更新 `现状.md` 和迭代日志。

### 明确不做

1. 不恢复那 294 条文件已丢失的旧附件。
2. 不移除按 `storage_path` 读取历史文件的回退逻辑，不改 `pm_attachment` 表结构。
3. 不改前端；用户管理里手工填写的头像地址保持原样可用。
4. 不动“需求本地文件夹”（向桌面目录导出附件）和 `logs/`。
5. 不改 `.gitignore` 中的 `data/` 规则。

### 约束与依赖

- 依赖的代码和文档：`pm_attachment` 是按 `biz_type` 与 `biz_id` 区分业务的多业务表，头像复用它，没有数据库结构变更，也不需要迁移脚本。
- 业务/合规约束：仓库安全规范，未经授权不重启运行实例。
- 既有系统/接口/数据约束：`/api/auth/avatars/**` 当前匿名可访问，保持不变。
- 外部依赖与前置条件：代码生效需重新加载运行实例；删除 `data/` 须在附件 355 入库并核对之后。
