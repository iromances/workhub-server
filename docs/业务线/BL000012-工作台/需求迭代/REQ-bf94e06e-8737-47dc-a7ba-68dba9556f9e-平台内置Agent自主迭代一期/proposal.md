## 1. Why：当前问题

现有系统尚无可配置多个 Agent、分派通用任务并持续执行的工作台。已有能力能采集系统预警、发现 XXL-JOB 失败、运行账务核对，能识别和拆解录入需求，但尚未把这些信号串成持续分析、修复、获批发布和效果复查的流程。现有 AI 网关支持 API/CLI，研发分析场景仍限制 CLI；现有版本服务是记录管理，未接入实际 Jenkins 发布。

用户需要在工作台配置 Agent 并分派目标，由 Agent 主动运用 WorkHub 能力完成任务。巡检与修复是核心应用：主动发现并推进真实问题，让人审阅有证据的解决方案、代码和发布版本；此类任务的完成标志是问题经过验证解决，并能继续处理下一轮问题。其他任务按各自目标验收。

## 2. What：完整目标与范围

### Agent 工作台是主入口

1. **配置多个 Agent**：设置名称、职责/目标、系统 AI Provider/模型、可用工具、业务线/环境/仓库范围、执行预算与启停状态。工作台 Agent 是持久化的配置与管理对象，实际智能执行由绑定的 AI API 或 CLI 承担。
2. **分派任务**：选择 Agent，输入自然语言任务目标、必要上下文、期望产物/验收条件；支持立即执行和周期任务。巡检是内置任务模板之一，还能分派需求分析、代码审查、研发修复、资料/报告整理等其工具范围内的任务。
3. **主动计划和行动**：Agent 根据任务目标先制定检查/行动计划，主动选择并调用 WorkHub 的能力，观察结果后调整下一步；既能查询异常，也要检查正常、缺失和过期数据。不要求先出现告警事件才启动。
4. **连续推进与人工接入**：任务进度、工具记录和产物持久化；可查看、补充指令、取消、重试。信息不足时问人，发布时提交审核；其余授权内的任务步骤自主推进。
5. **多个 Agent 的隔离**：Agent 可以选择不同 AI、职责和范围；任务上下文和工作区独立。同一问题、分支或环境的并发操作由平台协调，不能互相覆盖或重复发布。多个 Agent 不意味着默认允许它们自行创建更多 Agent 或跨越彼此授权。

例如：“平台自检 Agent”周期检查 WorkHub 日志与巡检；“账务巡检 Agent”主动检查选定业务线的账务结果；“研发 Agent”可接收人工分派的需求分析或代码任务。名称和分工由用户配置，不硬编码这三种角色。

### 巡检与自主修复任务的内置流程

下列链路是 Agent 完成巡检/修复目标时可使用的任务模板和工具规则，不是所有 Agent 任务都必须经过的固定流程。

1. **主动巡检并建档**：Agent 按职责和任务主动查询 WorkHub 自身日志、Bug/巡检结果，以及各业务线业务监测、账务监测（用户称财务监测）、系统预警的状态、运行结果与新鲜度；异常事件也可唤醒巡检，但不是唯一触发条件。发现问题后保留原始来源与时间，合并同一问题的重复事件，避免重复需求和重复修复。
2. **自主分析**：识别业务线、系统、环境、仓库与分支，结合受控日志、只读数据、代码、业务资料追踪原因，说明证据、影响和不确定性。区分代码缺陷、配置问题、数据问题、监测故障、规则不适用和正常业务差异。
3. **方案与研发**：生成解决方案、验收与回退安排；对证据充分且在授权范围的代码问题，自动创建修复分支、实现、测试、修正失败并形成可审查变更。必要时支持多个仓库的关联变更；资料或业务口径不足才转人工澄清。
4. **人工审核后测试发布**：展示来源、诊断、方案、代码差异、实际测试、精确版本与 Jenkins 目标。人审核后由 WorkHub 调用现有 Jenkins Job，跟踪排队、构建和部署结果；发布前不再逐条要求人工确认 AI 的每一步分析或编辑。
5. **测试环境验证**：回归原问题、相关接口/业务规则和跨系统依赖；失败继续受限修复，新代码需重新审核后才能再次发布。Jenkins 构建成功与业务验证通过分别展示。
6. **审核上线与观察**：生产上线针对通过测试的明确版本单独取得人工审核，由 WorkHub 调 Jenkins 执行；上线后按原问题的监测/巡检与验收标准核实结果，未验证、数据未恢复或异常复发保持待处理，不自动写成已解决。
7. **持续运行**：问题、步骤、证据、审核和发布任务持久化，重启后继续；同一事件不重复触发，失败有界重试并说明原因，处理结果回到原监测入口和需求档案。

### AI 与平台分工

- Agent 是智能决策主体：围绕被分派的目标规划任务、选择工具、检查结果并决定继续、交付或请求人工输入。WorkHub 提供 Agent 配置/运行宿主、触发调度、工具能力、持久化、权限、审核和审计；调度器不替 Agent 写死巡检顺序。系统配置的 AI 为各 Agent 提供推理和生成能力。
- 每个 Agent 从现有 AI 配置选用 Provider/模型，覆盖 API 和 CLI；任务默认沿用该 Agent 的配置，明确配置的任务/阶段策略可选用其他有权访问的模型。系统不能只给 API 型 AI 写报告，却把实际编码固定交给 Codex。
- WorkHub 是企业与 Agent 的桥梁，统一管理任务、资源、进度、产物及审核，不强制所有执行端使用平台自建行动循环。现有模型 API 在适配层通过“模型提出动作—平台受控工具执行—结果回传”取得执行能力；CLI 可使用自身原生规划和执行能力，受相同资源与审核边界约束。已配置但尚不兼容的协议/输出模式属于待补适配项，显式展示并验证，不能默默换成 Codex 或把该模型从需求范围排除。
- 当前 Codex 的角色是建设此能力；最终持续运行由 WorkHub 调度，不依赖用户逐次打开聊天催促。

### 工作边界

- 人工审核针对明确环境、代码提交/构建产物和发布计划；不能由模型批准自己，也不能凭一次旧审核发布后续新版本。
- 日志与业务库核查沿用现有受控只读范围；发现历史数据/配置问题应提供可审核处置方案，代码发布授权不自动等于执行资金、数据修正或主机配置变更。
- 遵守用户现有“不擅自安装软件/依赖/脚本或修改配置”约束；缺工具、依赖或接入信息时准确记录并沟通。
- 保留现有人工需求流程。自主发现的问题有自己的执行记录，并关联既有需求/工作项与归档，不把普通待整理记录未经确认转换成人工正式工作项。
- 不重建 Jenkins 发布平台，不硬编码实例地址、Job、账号或环境。可用接入由管理配置明确绑定；此版规格不授权立即触发当前 Jenkins 作业或上线。

## 3. Done：验收标准

| 编号 | 可验证条件 | 证据 |
| --- | --- | --- |
| AC-01 | Agent 在没有异常推送时也能主动查询 WorkHub 自身及三类监测，检查结果与新鲜度并发现问题；重复事件合并、来源可追溯、漏采可恢复 | 主动查询的工具轨迹、无告警/过期数据用例、真实接入和去重测试 |
| AC-02 | 自动诊断绑定正确业务线/环境/代码；跨系统问题覆盖相关仓库；账务差异与监测失败/未执行不混淆；不足时给出具体问题 | 有因果证据的诊断、分类与归属测试 |
| AC-03 | 所有当前配置接入类型可经统一模型/工具循环完成分析和代码变更；每个启用 Provider 留存实际能力验证，API 不依赖 Codex 完成编码 | 协议测试、各 Provider 验证表、API/CLI 实测变更与日志 |
| AC-04 | 自动形成方案、修复分支、代码差异和实际测试结果；必要多仓库变更有共同版本清单；测试失败不伪装完成 | Git 提交、验证退出码/报告、失败修复记录 |
| AC-05 | 无有效人工审核不调用任何环境发布；审核绑定精确版本/环境/Job/参数；版本或配置变化使旧审核失效 | 权限、并发、审核失效与越权测试 |
| AC-06 | 审核通过后 WorkHub 真实调用现有 Jenkins 测试发布，跟踪队列/构建/部署；网络超时先对账，不重复发布 | Jenkins queue/build ID、版本与部署证据、故障恢复测试 |
| AC-07 | 测试发布后实际复现/回归原问题；失败继续修复并重新审核新版本，通过后才可进入生产审核 | 问题相关用例、跨系统验证、原规则/日志复查 |
| AC-08 | 生产审核后由 WorkHub 调 Jenkins 上线已验证版本；上线后按原监测规则证明问题解决，复发关联重开；未验证不关闭 | 生产批准、实际版本、观察窗口与业务结果 |
| AC-09 | 重启、超时、取消、重复调度、模型错误和 Jenkins 不确定结果不会丢任务、重复变更/发布或覆盖新状态；有预算、停止入口和审计 | 生命周期/幂等/恢复测试 |
| AC-10 | 工作台可创建/配置多个 Agent、分派和安排任务、查看计划/工具调用/产物；巡检修复任务贯通监测到发布观察，并可人工补充/驳回 | 前端构建与页面流程验证 |
| AC-11 | WorkHub 自身及全部目标业务线均有接入矩阵、明确仓库/环境/AI/Jenkins/验证绑定和运行状态；未接入项显式列出，不能以单一试点代替整体完成 | 实际系统清单、逐项接入与验收记录 |
| AC-12 | Agent 配置与任务为独立对象；多个 Agent 可绑定不同系统 AI、职责、工具和业务范围，启停/修改可审计，不能继承其他 Agent 的权限 | 配置/API/权限与隔离测试 |
| AC-13 | 人可分派非巡检任务并配置立即/周期执行；任务无需伪造告警/问题 ID，依据自身目标产出分析、审查或研发结果 | 非巡检任务端到端用例、调度/重启测试 |
| AC-14 | Agent 基于工具结果调整计划和下一步，任务可跨轮继续、补充与取消；通用任务状态不依赖修复问题的固定状态链 | 至少两种目标的不同工具轨迹、恢复/补充测试 |
| AC-15 | 多 Agent 可并发处理各自任务，同一问题/分支/环境冲突时不重复修复或发布；证据、上下文、工作区互不串用 | 多 Agent 并发、共享资源和越权测试 |

可先用 WorkHub 自身和三类监测的典型问题验证完整流程，再逐条业务线推广；先后顺序不缩小最终验收范围。真实运行前还需核实 Jenkins 实例/Job/精确版本参数，以及在线业务线和 Provider 清单。
