日期：2026-11-12。业务线：BL000012-工作台。分支 `codex/development-20261102`，工作区 `/Users/aslight/Documents/workspace/IDEAWorkspace/workhub-server`。沿用已确认 v4 范围内的缺陷修复，规格见 Design「系统预警采集窗口边界容差与失败升级（2026-11-12）」。

## 缺陷背景

本地采集实例每 ~10 秒刷 WARN「ELK系统预警采集未完成…ELK返回日志超出采集区间」。只读核查（MCP `run_readonly_query`，目标 `bl000012-prod-db-10-10-116-32-3306`）：scope 8（BL000001/PROD）与 scope 10（BL000003/PROD）自 2026-11-09 起 `status=ERROR`、`position_json=NULL`、`page_number=0`，窗口边界为微秒精度（如 `09:35:00.287476`→`09:37:00.075717` UTC），首页确定性失败被无限重试，两条业务线 PROD 错误预警漏采 3 天。机制：ES 毫秒级 date 字段对 range 边界按包含方向取整（gte 向下、lte 向上），边界毫秒上的真实文档被合法返回，而读侧/提交侧全精度严格校验整页失败；`fail(restart=false)` 保留窗口，`claim()` 仅在定义变更或 COMPLETE 时重开，形成死循环。

## 已实现

- `claim()` 产生或推进窗口时 `from_time`/`to_time` 一律截断到整毫秒（fresh、coveredUntil 回退、legacy 同步时间三条推导路径全覆盖），新窗口不再产生亚毫秒边界。
- `readErrorPage` 与 `commit()` 的区间校验放宽 ±1ms（常量 `SystemAlertLogSource.BOUNDARY_TOLERANCE_MS`），接受 ES 毫秒字段取整的合法边界偏差并继续入库；超出 1ms 仍整页硬失败保留异常防护。
- `ops_system_alert_collection_state` 新增 `consecutive_failures`、`last_failure_message`（迁移 `V20261112_140809__add_system_alert_collection_failure_escalation.sql`，仅加列）；`fail()` 递增计数（含 RestartRequired 路径），`commit()` 成功清零；`claim()` 发现 `ERROR` 且连续失败 ≥5 次按 fresh 路径重开窗口（重算毫秒对齐边界、新 windowId、清位置与计数）。
- **记录字段序与物理列序对齐**：MyBatis 对记录按位置做构造器自动映射，而 `ALTER TABLE ADD COLUMN`（H2 与 MySQL 一致）将新列追加在表尾，`SystemAlertCollectionState` 的新字段必须放在 `version/updatedAt` 之后；已在记录注释中固化该约束。开发过程中曾因字段序错位出现 `version` 读到 `consecutive_failures` 值的旋转错位，以特征值插入回读诊断确认后修正。
