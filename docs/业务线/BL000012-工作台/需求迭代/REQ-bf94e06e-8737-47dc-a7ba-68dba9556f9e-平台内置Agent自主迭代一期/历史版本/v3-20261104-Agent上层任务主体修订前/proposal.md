## 1. Why：当前问题

现有系统能采集系统预警、发现 XXL-JOB 失败、运行账务核对，能识别和拆解录入需求，但尚未把这些信号串成持续分析、修复、获批发布和效果复查的流程。现有 AI 网关支持 API/CLI，研发分析场景仍限制 CLI；现有版本服务是记录管理，未接入实际 Jenkins 发布。

用户需要系统主动发现并推进真实问题，让人主要审阅有证据的解决方案、代码和发布版本。完成标志是问题经过验证解决，并能继续处理下一轮问题；不是生成一份报告、创建一个 MR 或某次构建显示绿色。

## 2. What：完整目标与范围

### 必须形成的流程

1. **发现并建档**：持续接收 WorkHub 自身日志、Bug/巡检结果，以及各业务线业务监测、账务监测（用户称财务监测）、系统预警的异常；保留原始来源与时间，合并同一问题的重复事件，避免重复需求和重复修复。
2. **自主分析**：识别业务线、系统、环境、仓库与分支，结合受控日志、只读数据、代码、业务资料追踪原因，说明证据、影响和不确定性。区分代码缺陷、配置问题、数据问题、监测故障、规则不适用和正常业务差异。
3. **方案与研发**：生成解决方案、验收与回退安排；对证据充分且在授权范围的代码问题，自动创建修复分支、实现、测试、修正失败并形成可审查变更。必要时支持多个仓库的关联变更；资料或业务口径不足才转人工澄清。
4. **人工审核后测试发布**：展示来源、诊断、方案、代码差异、实际测试、精确版本与 Jenkins 目标。人审核后由 WorkHub 调用现有 Jenkins Job，跟踪排队、构建和部署结果；发布前不再逐条要求人工确认 AI 的每一步分析或编辑。
5. **测试环境验证**：回归原问题、相关接口/业务规则和跨系统依赖；失败继续受限修复，新代码需重新审核后才能再次发布。Jenkins 构建成功与业务验证通过分别展示。
6. **审核上线与观察**：生产上线针对通过测试的明确版本单独取得人工审核，由 WorkHub 调 Jenkins 执行；上线后按原问题的监测/巡检与验收标准核实结果，未验证、数据未恢复或异常复发保持待处理，不自动写成已解决。
7. **持续运行**：问题、步骤、证据、审核和发布任务持久化，重启后继续；同一事件不重复触发，失败有界重试并说明原因，处理结果回到原监测入口和需求档案。

### AI 与平台分工

- WorkHub 负责持续调度、上下文、状态、受控工具、验收执行、人工审核、Git/Jenkins 操作和审计；系统配置的 AI 负责分析、规划、生成修改与解释结果。
- 分析、方案、代码、复核等阶段均从现有 AI 配置选用 Provider/模型，覆盖 API 和 CLI。系统不能只给 API 型 AI 写报告，却把实际编码固定交给 Codex。
- 各协议接入通过共同的“模型提出结构化动作—平台验证并执行—结果返回模型”循环获得工具能力。已配置但尚不兼容的协议/输出模式属于待补适配项，显式展示并验证，不能默默换成 Codex或把该模型从需求范围排除。
- 当前 Codex 的角色是建设此能力；最终持续运行由 WorkHub 调度，不依赖用户逐次打开聊天催促。

### 工作边界

- 人工审核针对明确环境、代码提交/构建产物和发布计划；不能由模型批准自己，也不能凭一次旧审核发布后续新版本。
- 日志与业务库核查沿用现有受控只读范围；发现历史数据/配置问题应提供可审核处置方案，代码发布授权不自动等于执行资金、数据修正或主机配置变更。
- 遵守用户现有“不擅自安装软件/依赖/脚本或修改配置”约束；缺工具、依赖或接入信息时准确记录并沟通。
- 保留现有人工需求流程。自主发现的问题有自己的执行记录，并关联既有需求/工作项与归档，不把普通待整理记录未经确认转换成人工正式工作项。
- 不重建 Jenkins 发布平台，不硬编码实例地址、Job、账号或环境。可用接入由管理配置明确绑定；此版规格不授权立即触发当前 Jenkins 作业或上线。

## 3. Done：验收标准

| 编号 | 可验证条件 | 证据 |
| --- | --- | --- |
| AC-01 | WorkHub 自身日志/Bug/巡检及业务监测、账务监测、系统预警均能进入自主问题流程；重复事件合并，来源可追溯，漏采/中断可恢复 | 各来源回放、真实接入记录、游标与去重测试 |
| AC-02 | 自动诊断绑定正确业务线/环境/代码；跨系统问题覆盖相关仓库；账务差异与监测失败/未执行不混淆；不足时给出具体问题 | 有因果证据的诊断、分类与归属测试 |
| AC-03 | 所有当前配置接入类型可经统一模型/工具循环完成分析和代码变更；每个启用 Provider 留存实际能力验证，API 不依赖 Codex 完成编码 | 协议测试、各 Provider 验证表、API/CLI 实测变更与日志 |
| AC-04 | 自动形成方案、修复分支、代码差异和实际测试结果；必要多仓库变更有共同版本清单；测试失败不伪装完成 | Git 提交、验证退出码/报告、失败修复记录 |
| AC-05 | 无有效人工审核不调用任何环境发布；审核绑定精确版本/环境/Job/参数；版本或配置变化使旧审核失效 | 权限、并发、审核失效与越权测试 |
| AC-06 | 审核通过后 WorkHub 真实调用现有 Jenkins 测试发布，跟踪队列/构建/部署；网络超时先对账，不重复发布 | Jenkins queue/build ID、版本与部署证据、故障恢复测试 |
| AC-07 | 测试发布后实际复现/回归原问题；失败继续修复并重新审核新版本，通过后才可进入生产审核 | 问题相关用例、跨系统验证、原规则/日志复查 |
| AC-08 | 生产审核后由 WorkHub 调 Jenkins 上线已验证版本；上线后按原监测规则证明问题解决，复发关联重开；未验证不关闭 | 生产批准、实际版本、观察窗口与业务结果 |
| AC-09 | 重启、超时、取消、重复调度、模型错误和 Jenkins 不确定结果不会丢任务、重复变更/发布或覆盖新状态；有预算、停止入口和审计 | 生命周期/幂等/恢复测试 |
| AC-10 | 页面贯通发现、分析、分支、验证、审核、Jenkins、上线观察，各阶段可查看原始证据并人工补充/驳回 | 前端构建与页面流程验证 |
| AC-11 | WorkHub 自身及全部目标业务线均有接入矩阵、明确仓库/环境/AI/Jenkins/验证绑定和运行状态；未接入项显式列出，不能以单一试点代替整体完成 | 实际系统清单、逐项接入与验收记录 |

可先用 WorkHub 自身和三类监测的典型问题验证完整流程，再逐条业务线推广；先后顺序不缩小最终验收范围。真实运行前还需核实 Jenkins 实例/Job/精确版本参数，以及在线业务线和 Provider 清单。
