## 3. 任务明细

### T-01：问题、策略与信号来源

- 输入：Design §3.1/3.6、现有 ELK/XXL-JOB/账务监测、需求入口、MCP 资源约束；修改前读取现行数据库规范。
- 输出/允许范围：autonomy 的 model/dao/service/controller/job、新增迁移与权限定义、监测服务中的受控联动点；WorkHub 自身日志/Bug/巡检适配和游标。
- 不修改：真实业务库、监测原始业务判断、主机路径白名单或角色实际授权。
- 建议研发任务标题：监测异常自动形成可追溯问题。
- [ ] 全部目标来源支持回放与增量接入；事件唯一/问题聚合不漏重复、不丢复发；事务失败不前移游标。
- [ ] 账务差异、执行失败和未执行分别处理；未实现的监测能力显式未就绪；自身自治日志不会引起无限自触发。
- [ ] 工作台与业务线数据按真实配置定位；跨业务线/共享系统信息不丢失；原人工需求流程回归。
- 验证计划：来源桩、分类、去重、游标与事务测试；真实 MySQL 约束/迁移需已授权隔离环境，不启动业务应用代替迁移验证。

### T-02：支持系统配置的全部 AI

- 输入：Design §3.2、AiGateway/Provider/UseCase、实际已配置 Provider 清单与各接入协议。
- 输出/允许范围：ai/autonomy 共同 AgentStep、协议适配、阶段场景、工具结果回读、预算与能力检查、Provider 验证表。
- 不修改：用户当前 Provider 密钥或选择、模型实际权限；不把 API 任务暗中转给 Codex。
- 建议研发任务标题：多 AI 共用诊断与代码工具循环。
- [ ] 每阶段允许 API/CLI；模型、协议、动作与工具回执可追溯，不硬编码 Codex/GLM 为唯一执行方。
- [ ] 正常结果、动作格式错误、未知工具、越权参数、上下文超限、模型超时均有确定处理；格式纠正有上限。
- [ ] API 型 AI 可直接通过平台工具读文件、生成补丁、检查测试失败并修正；没有 CLI 时仍可完成流程。
- [ ] 每个启用 Provider 的真实能力单独验证；CLI 不同协议按实际适配，不通用套用 Codex 参数；不兼容项纳入实现缺口，不伪称通过。
- 验证计划：协议/结构化动作/回执恢复/权限测试，模拟各通道；真实小型临时仓库任务在已配置可用账号和明确验证范围下执行，记录模型与实际结果。

### T-03：代码迭代与独立验证

- 输入：Design §3.3、仓库/业务线映射、诊断方案、已安装工具和缓存。
- 输出/允许范围：受控文件/查询/构建测试工具、隔离工作区、Git 交付、多仓库变更清单、实际验证证据。
- 不修改：用户未提交目录、默认/受保护分支、业务数据、运行主机配置；不下载或安装缺失依赖。
- 建议研发任务标题：自主产出经过验证的修复分支。
- [ ] 指定正确仓库/base SHA，不存在时失败可见；补丁越界/软链接拒绝；交付凭据不进入模型环境或工作区。
- [ ] 平台实际执行测试并保存退出码；模型自述成功无效；失败在预算内修复、无验证不交付。
- [ ] 必需跨仓库变更共享方案/版本清单和依赖；局部成功不冒充整体就绪；重试不重复创建分支/MR。
- [ ] 取消/超时回收进程树、旧回调不覆盖新状态；隔离条件不成立时不能降级为无沙箱。
- 验证计划：真实临时 Git 仓库、工具边界、失败测试修复、并发/取消与跨仓库依赖测试；外部 GitLab 用客户端桩，真实写入在试点授权内执行。

### T-04：持续编排与人工审核

- 输入：Design §3.4–3.6、现有身份/项目/业务线权限、T-01–03。
- 输出/允许范围：阶段编排、持久化任务/步骤、澄清回复、审核 API 与不可变快照、出站发布请求、停止/重试和审计。
- 不修改：模型不能审核自身；不复活旧 v2 的“逐条确认设计才可编码”门槛；不改变普通人工需求语义。
- 建议研发任务标题：贯通自动研发与人工发布审核。
- [ ] 明确问题自动分析/研发，只有信息不足、范围越界或发布审核才等待人；问题/步骤均可恢复。
- [ ] 审核绑定准确的 caseVersion/manifestHash/环境/Job 绑定版本/参数；代码或绑定改变使批准失效。
- [ ] 无权限/跨业务线换 ID/重复审核/并发领取拒绝或幂等；审核与发布请求同事务，不依赖丢失的内存回调。
- 验证计划：状态机、权限、幂等、重启、审核失效、任务预算与取消竞态测试。

### T-05：Jenkins 审核后发布

- 输入：Design §3.4；用户已确认 WorkHub/业务线测试生产均为 Jenkins；实际实例/Job/参数/凭据引用和回执待接入核实。
- 输出/允许范围：Jenkins HTTP 客户端、只读探针、环境 Job 映射、发布请求执行/查询/恢复、构建与部署结果模型/API。
- 不修改：不新建发布平台、不擅改 Job/插件/认证、不关闭 CSRF；开发测试不触发真实 Jenkins。
- 建议研发任务标题：审核通过后由 WorkHub 调用 Jenkins 发布。
- [ ] 只读探针不触发构建；受控目标/凭据/参数验证，拒绝模型自定义 URL、跨环境/Job 替换及未批准调用。
- [ ] Job 可锁定准确提交或产物；队列/build/实际 SHA 与审批一致；不能通过构建最新分支头替换批准版本。
- [ ] 触发超时/返回丢失/队列过期/长构建/重启均先查既有句柄与关联信息；未知状态不盲重发。
- [ ] 测试和生产分别审核；多服务部分失败真实展示；WorkHub 自身重启后继续跟踪 Jenkins 原构建。
- 验证计划：本地 HTTP 桩覆盖构建、crumb/session 或 token 认证、异步状态、异常与幂等；真实接入只读预检后在具体人工审核下触发试点发布。

### T-06：回归、观察与问题关闭

- 输入：Design §3.5、原异常/规则/样本、变更清单、测试/生产实际发布结果。
- 输出/允许范围：验证任务、原监测结果关联、观察窗口、复发重开、数据处置待办与验收报告。
- 不修改：不以降低监测标准掩盖问题；不自动执行未授权数据修正或回滚。
- 建议研发任务标题：用原问题证据验证测试和上线结果。
- [ ] Jenkins 成功但业务回归失败、数据缺失、监测执行失败均不能关闭问题。
- [ ] 测试失败回到修复，新版本重新审核；生产只接受已验证的同一版本。
- [ ] 观察使用新鲜证据与批准标准；历史数据仍待处理时显示部分修复；复发关联旧证据重开。
- 验证计划：日志/规则/回归回放与新鲜度测试，跨系统一致性验证；真实数据仅在已确认环境通过受控只读工具复核。

### T-07：前端完整体验

- 输入：新 API、前端 README/charter/architecture/roadmap 与现有监测页面。
- 输出/允许范围：api/types/视图/路由、监测入口关联问题、统一问题看板、澄清与审核、AI/Jenkins/执行策略配置、对应前端文档。
- 不修改：不在前端直连外部系统；不展示假状态或将实现细节混入正常审批内容。
- 建议研发任务标题：自主迭代问题、证据和审核工作台。
- [ ] 三类监测与自身问题均能定位到完整进度和证据；方案、分支、测试、Jenkins、上线观察一处可追踪。
- [ ] 审核准确显示环境/版本/影响/验证/回退；驳回和补充能继续原问题，失效审批明确提示。
- [ ] Provider 选择不限制 Codex；API 能力与实际验证状态可见；接入缺失给出具体缺项。
- [ ] 现有依赖下类型检查/构建通过，覆盖正常、失败、等待审核、版本变动和权限场景。
- 验证计划：前端类型检查、构建和页面验证；不执行 npm install，不提前更改实际运行策略。

### T-08：完整运行验收与交付

- 输入：全部实现、用户明确目标、当前实际业务线/AI/Jenkins/仓库/环境清单。
- 输出/允许范围：Provider 覆盖表、各业务线接入矩阵、真实端到端证据、现状/迭代日志/验收档案、发布与回退包。
- 不修改：不把小样本试点、mock 或“方案完成”当作整个自主迭代目标完成；不隐去未接入业务线/Provider。
- 建议研发任务标题：验证 WorkHub 与业务线持续自主迭代。
- [ ] WorkHub 自身及三类监测代表场景跑通发现→分析→分支→实测→人工审核→Jenkins 测试发布→业务验证→人工审核上线→效果复查。
- [ ] 每个目标业务线记录实际仓库/环境/监测/AI/Jenkins/验证绑定和验收；不可用项明确保留待完成，不默认为通过。
- [ ] 所有启用 Provider 有实际能力证据，至少涵盖无需 Codex 代做的 API 修复链路；每个尚未适配项继续处理。
- [ ] 多轮问题/复发可持续推进；平台重启和自发布不丢任务、不重复发布；回退方案已审阅，真实发布均有审核。
- 验证计划：先静态/隔离，再只读预检，最后具体人工审核下的真实测试/上线；完整记录未执行项目及原因。
