## 1. Why：背景与问题

WorkHub 已有需求录入、AI 识别、澄清、研发拆解和人工工作项流转，以及业务线代码与运维只读上下文。当前代码未注册实施场景，工作项无 Agent 执行计划，GitLab 服务只有发现仓库与 clone/fetch，无法从确认需求走到经过验证的代码交付。

v1 草案存在需要在实施前解决的缺口：

- CLI 的 `allowLocalTools=true` 实际关闭沙箱，工作目录和提示词不能提供文件或网络隔离。
- “需求进入开发中”没有绑定被确认的 SDD 内容、仓库、基线和验收命令，后续变更可能未经确认进入执行。
- 只按应用查询判断重复任务、只靠 afterCommit 入队，分别存在并发重复和提交后丢失任务的路径。
- 没有独立验证模型自述的构建/测试结果，也未定义取消与交付竞争、推送成功但 MR 超时的恢复语义。

上述为本地代码与草案核查结论，不代表生产事故。在线 MCP 数据库连接失败，真实业务线资源与部署状态暂未验证。

## 2. What：目标与范围

### 目标路线与完成判定

| 阶段 | 产出 | 完成证据 |
| --- | --- | --- |
| M0：执行能力 | 平台内置执行引擎、确认界面、隔离工作区、独立验证、分支/MR 交付及失败恢复 | 代码、离线自动化验证、前端构建与受影响页面验证 |
| M1：平台试点 | 一条真实 WorkHub 需求在确认后完成实施与交付 | 规格版本、基线 SHA、执行记录、测试输出、MR、人工交付结论 |
| M2：业务线验证 | 至少一条经用户选定并核实业务线配置的真实需求复用同一机制 | 同 M1；包含业务线/仓库/环境/分支映射证据 |
| 后续候选：主动提出改进 | 从告警、失败任务与反馈形成去重的候选需求，由人决定是否立项 | 长期范围已向用户询问，尚待答复；不据此默认增加本期功能或定时任务 |

本期完成要求 M0、M1、M2 均有真实证据。仅完成文档、单测或 MR 创建，不能宣布“自主迭代目标已完成”。后续推广还需逐条登记目标业务线的仓库、环境、工具链、授权与验收状态；一条业务线试点成功不等于所有业务线已接入。持续运行的目标和主动发现范围在用户回复后补充；分期不替代总目标。

### 本期交付范围

1. **两个业务确认点**。规格确认时展示需求、工作项、Proposal/Design/Tasks 内容与哈希、目标仓库、环境、基线分支与 SHA、MR 目标、验收命令；确认后才可执行。交付确认由人审阅 MR、合并并推进既有业务阶段。常规编码、测试和范围内修复无需逐步询问。
2. **工作项级执行计划**。人工选择 HUMAN/AGENT；每个 AGENT 工作项明确一个仓库，记录目标业务环境与实际本地执行位置。多仓库需求拆分，不凭标题推断仓库、不默认全业务线开启。
3. **执行引擎**。持久化队列、受限并发、超时、取消、异常恢复、幂等交付；任务输出和阻塞原因可在页面查看。需求暂停、取消、规格变更或权限失效时停止领取，并在交付前复核。
4. **受限执行**。只在专用克隆目录内修改代码；新场景保留沙箱，禁用外部工具接入和命令网络访问，工具与依赖使用预备缓存。缺依赖记录阻塞，不自行安装软件、下载依赖、修改主机配置或放宽权限。
5. **独立验证和有限修复**。平台按确认的离线验收命令收集退出码与日志，记录执行时提交/内容摘要；模型报告仅作解释。失败允许最多 2 轮范围内修复并重新验证，受单任务总时限约束，仍不通过则失败等待处理。
6. **受控交付**。平台在模型进程退出后保存变更、构建测试、创建提交，只推执行分支并创建 MR；默认与受保护分支不接受 Agent 推送。交付凭据不进入 Agent 工作区、提示词、进程环境或报告。交付超时先核对远端结果，再决定重试。
7. **参数与证据**。模型、强度、超时沿用 AI 场景配置；启停、并发、保留期在独立执行设置中管理，变更只作用于后续执行或后续领取，不篡改进行中记录。报告保留原始证据，人工修订以新版本追加。
8. **前端入口**。需求/工作项页配置执行计划、预览与确认规格、查看执行状态、失败原因、验证证据、分支和 MR，支持取消、按阶段重试和报告备注；配置页区分模型参数与执行器设置。

### 本期边界

- 不自动合并、部署或改变测试/验收/上线终态；MR 创建仅表示待人工交付确认。
- Agent 不访问或修改业务数据库与生产资源。WorkHub 后端为执行记录、权限和状态正常写自身数据库，不属于 Agent 业务库写入授权。
- 不新增无人值守的候选需求发现任务；内部队列调度只处理已确认计划。
- 不进行跨仓库依赖编排；有跨工作项依赖时须先拆解、排序并满足前置交付，不能把几个独立 MR 宣称为完整需求交付。
- 不触碰用户现有 IDEA 工作区，不使用其未提交改动作为默认执行基线；试点选择已同步的基线。
- 不改变 MCP 的只读契约、不修改知识库 SDD 规范。已有分析场景的沙箱问题单独记录，新增实施场景不沿用关闭沙箱路径。

### 约束与前置条件

- 已安装并可用的 Git、Codex CLI、JDK/构建工具与离线缓存；执行账户、读写边界和网络隔离必须通过预检。不具备时功能保持关闭，缺项报告给用户。
- GitLab 仓库必须来自 WorkHub 的业务线配置；WorkHub 自身仓库也需核对实际 remote、GitLab 项目 ID 和访问能力，不从目录名推断。
- 确认规格不等于授权修改当前运行配置、执行数据库迁移、部署应用或触发真实试点；这些操作在对应具体产物与目标可审阅后按已有授权处理。
- 本轮不安装依赖、运行迁移或修改配置。缺少的真实环境信息不阻止完成本地实现规格，但阻止真实执行与验收。

## 3. Done：成功标准

以下均为 v2 提议验收标准，尚待用户统一确认。

| 编号 | 可观察的验收条件 | 核对方式 |
| --- | --- | --- |
| AC-01 | 规格确认与入队同事务；重复点击/并发发起只产生一个活动执行。未确认、规格已变化或需求暂停时不能执行 | 服务、并发与事务故障测试 |
| AC-02 | 只能写专用工作区；越界写、命令网络与外部工具调用受阻；不能读取平台凭据；缺少隔离能力时拒绝启动；用户工作区保持原样 | 参数测试 + 执行主机隔离探针 |
| AC-03 | 只向已确认仓库的执行分支提交，默认/受保护分支拒绝推送；一次交付一个 MR；超时重试不重复推送/建 MR | 仓库边界与远端不确定结果测试 |
| AC-04 | 模型/强度/超时和执行器设置有明确入口、权限与范围；执行记录保存实际生效值 | 服务测试 + 页面验证 |
| AC-05 | 排队可取消；运行中先停止进程树再终结；取消不与推送竞争；失败、阻塞、已交付有独立可见原因 | 并发与进程生命周期测试 |
| AC-06 | 重启可恢复已提交队列；不误杀其他实例任务；未确认旧进程已退出不重跑；远端副作用先对账再恢复 | 恢复与租约失效测试 |
| AC-07 | 报告关联规格/基线/结果 SHA、实际验收退出码及日志、MR、风险；人工修订保留历史，不能覆盖原始结果 | 归档与版本测试 |
| AC-08 | M1 与 M2 各有一条真实需求完整证据；合并由人工进行；真实通过和未验证明确区分 | 授权后的运行验收 |
| AC-09 | 后端相关测试、前端类型检查/构建与受影响页面验证通过；缺环境/依赖时记录未通过或未验证 | 测试记录 |
| AC-10 | 不以模型自述作为通过依据；必需验收缺失/失败阻止交付；范围内最多修复 2 轮且不超总时限 | 假成功、失败与超时测试 |
| AC-11 | 服务端验证操作者与需求/项目/工作项/业务线/仓库的关系，不能换 ID 越权操作；规格或目标变化重新确认 | 权限与一致性测试 |

设计与执行任务见 [design.md](design.md)、[tasks.md](tasks.md)。
