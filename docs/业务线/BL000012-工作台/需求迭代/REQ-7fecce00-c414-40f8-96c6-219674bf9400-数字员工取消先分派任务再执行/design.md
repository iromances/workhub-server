## 2. 系统架构

- 总体方案和设计目标：把“执行单元”从任务上移到数字员工。每个员工有且只有一个**职责执行任务**作为常设执行配置，页面经它直接执行；历史运行按员工聚合。任务表、运行链路和系统建任务的流程都不动。
- 职责执行任务的标识：保留请求标识 `request_key = 'duty'`，复用既有唯一键，不加表、不加列。
- 主要流程：
  1. 打开「任务成果」：`GET /api/agents/{id}/duty-task` 与 `GET /api/agents/{id}/runs` 并行。前者在员工还没有职责执行任务时补建或认领（见 §3）。
  2. 「开始新一轮」：沿用 `POST /api/agent-tasks/{dutyId}/run`，以职责执行任务的当前版本和规格快照入队。
  3. 「执行设置」：沿用 `PUT /api/agent-tasks/{dutyId}`，可一并调整执行方式，所以不再需要独立的「调整周期」。
  4. 历史运行的详情、停止、重试、补充、验收、对账、删除：前端用运行行自带的 `taskId` 调既有任务级接口，后端不变。
- 前端页面、交互：
  - 员工列表「操作」列：「任务成果 / 配置 / 停用或启用 / 删除」。
  - 任务成果弹框：标题 `任务成果 · {员工名}`；其下是常设配置的工作目标（为空显示“按员工职责执行”）和两行截断的职责（超过 60 字可展开收起）；期望产物、增量分析标签与验收、本次完成目标两行保留；工具栏为「查看历史运行（窄屏）/ 刷新 / 执行设置 / 开始新一轮」。历史运行侧栏与阅读区不变。
  - 运行面板：当该轮的目标与常设配置的工作目标不同时，显示「本轮目标：…」，用于区分需求开发、问题修复等系统任务的运行。
  - 执行设置抽屉：原编辑任务表单去掉“立即执行”，字段为工作目标、补充资料、期望产物、数据范围、执行范围、预警 webhook、本次完成目标、业务监测、执行方式。

## 3. 契约与数据模型

- API/事件提供方与消费者：后端提供，数字员工页面消费。
- 新增契约（权威文件：`AgentController.java`）：

| 接口 | 权限 | 返回 | 说明 |
| --- | --- | --- | --- |
| `GET /api/agents/{id}/duty-task` | `agent:task:view` 且为员工归属人或持有 `agent:manage` | `AgentTaskResponse`（同 `GET /api/agent-tasks/{id}`） | 返回职责执行任务；不存在时在同一事务内认领或补建后返回，重复调用幂等 |
| `GET /api/agents/{id}/runs?page=1&pageSize=20` | 同上 | `AgentPage<AgentRunResponse>`（同任务级运行列表） | 员工名下全部运行，`ORDER BY created_at DESC, id`，`pageSize` 取 1–100 |

- 既有契约的校验变化：
  - `POST /api/agents/{id}/tasks`：`requestKey` 为 `duty` 时拒绝，提示“请求标识为系统保留值，请更换”。需求自动开发和问题修复的标识前缀不受影响。
  - `DELETE /api/agent-tasks/{id}`：目标为职责执行任务时拒绝，提示“职责执行任务随数字员工管理，不能单独删除”。`DELETE /api/agents/{id}` 仍级联清除。
- 认领与补建规则（只在员工还没有 `request_key='duty'` 的任务时执行一次）：
  1. 先无锁查询；缺失时对员工行 `FOR UPDATE` 加锁后复查，唯一键兜底并发。
  2. 认领：在员工名下排除 `intake-dev-%`（需求开发）和 `fix-%`（问题修复）的任务中，取运行次数最多者，同数取创建最早，再按 ID 升序。只把它的 `request_key` 改为 `duty`，规格、周期、版本、运行都不动；写审计 `TASK/{taskId}/ADOPT_DUTY`，记录原请求标识。
  3. 补建：没有可认领的任务时新建，请求标识 `duty`，分派人为员工归属人，手动模式。默认规格：工作目标、验收为空，期望产物为分析报告，全量分析，读取已有核验结果，无预警 webhook。执行范围取员工的授权范围；员工未限定范围时取当前全部启用业务线及其已配置环境，与配置页“留空允许所有已启用业务线及其环境”同义。
- 幂等、并发、重试和重复执行行为：「开始新一轮」沿用任务级请求标识与版本校验；认领与补建幂等，回滚再上线不会重复执行。
- 数据归属、关键约束、迁移及历史兼容：没有数据库结构变更与数据迁移。运行按 `agent_id` 聚合，不改写任何快照。被认领任务的原请求标识只在该任务创建时用于幂等，页面任务与脚本任务的标识此后不会再被复用。
- 后端提示文案：
  - “单次运行的补充指令已达上限，请分派后续任务”改为“…，请开始新一轮运行”。
  - “发布或效果验收任务须明确选择本次完成目标环境；旧任务请重新分派”改为“…；请在执行设置中选择完成目标环境”。

## 4. 非功能约束

- 安全与权限、授权边界：不新增权限码；两个新接口都做员工归属校验；预警 webhook 仍按原方式加密存储与脱敏。`agent:task:assign`（分派 Agent 任务）不再被页面使用，后端流程继续沿用。
- 性能、容量和时效：按员工列运行走既有索引 `idx_agent_run_agent(agent_id, status)` 过滤后排序，单员工运行量为百级。认领查询只在首次打开时执行，范围为单个员工的少量任务。
- 失败处理、降级与补偿：「执行设置」读取失败时历史运行照常显示，只是隐藏「执行设置」和「开始新一轮」并提示；其余失败口径不变。
- 日志、监控、告警与审计：认领写 `ADOPT_DUTY` 审计，补建写 `TASK CREATE` 审计；执行链路日志不变。

## 5. 交付与回滚

- 影响系统和前后端/数据库发布顺序：后端先发，前端后发。新后端保留全部旧接口，旧前端可继续使用任务列表。
- 灰度或开关：无。
- 数据备份与前后校验：无结构变更，不需要备份。上线后只读核对 `pm_agent_task WHERE request_key='duty'`，应与 §1 基线的“处理”列一致（已打开过任务成果的员工才会出现）。
- 回滚条件、步骤与不可逆部分：还原两端提交即可。已认领任务的请求标识变更和已补建的默认任务不回退；旧版页面把它们当普通任务显示在任务列表里，仍可编辑和执行，没有数据损失。
- 生效并核实后需要更新的目标项目系统设计、迭代日志、需求及专项文档内容与证据：`现状.md`“数字员工与执行桥接”下新增小节；`迭代日志.md` 新增条目；workhub-web `docs/frontend-architecture.md` 数字员工小节更新页面结构与接口说明。

## 6. 一致性与待确认

- Proposal 每项目标的设计承接位置：目标 1 → §2 流程 2、3 与 §3 契约；目标 2 → §3 按员工列运行；目标 3 → §2 执行设置抽屉。
- 明确非范围是否被保持：任务表、任务接口、系统建任务流程和执行链路均未改动。
- 待确认问题及影响：
  1. 智能柜认领 131 轮的巡检任务；“业务监测 v4 一次性验收”任务此后不能单独发起运行，只能查看历史或调整执行设置后重跑。如需保留该能力，要另加“按历史运行再跑一轮”入口，属于新增范围。
  2. 「开始新一轮」不加二次确认，与现状一致。任何员工（含研发工程师）都能按常设配置直接执行，这与现在留空目标分派任务的能力相同。
  3. 新建或未限定范围员工的默认执行范围取全部启用业务线及其环境（§3 补建规则 3），而不是沿用页面新建任务时的“不选范围”。不选范围会让该员工按职责执行时无法访问任何业务线。
  4. 页面走查需要运行实例加载新代码。默认不重启运行实例，走查记为待部署；需要本次会话走查请另行授权重启。
- 契约、ADR 及 Tasks 的关联链接：[proposal.md](proposal.md)、[tasks.md](tasks.md)；无独立契约文件与 ADR。
