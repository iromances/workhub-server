## 1. 关键决策记录（2026-11-05 用户确认）

1. AI 启动开发触发时机：**设计完成后**（待设计 → 设计完成进入开发中时触发）。
2. 禅道：**本次接真实禅道 API**（地址与 Token 由用户配置到系统配置后联调）。
3. Jenkins：**确认解除暂缓并接入**（测试环境发布，人确认环境）。
4. 实施节奏：**一次全做**（评估改造、AI 分支开发、提测审核三期全部实施）。

## 2. 背景

当前“AI任务评估”与“任务评估”是同一份研发分析草稿（`pm_intake_development_analysis.draft_json`）的两个页签：前者只读展示 AI 参考，后者人工编辑并在“评估完成”确认后创建正式工作项、推进待排期。两者重复展示、交互割裂。评估提示词不定向读取知识库 SDD 流程，任务负责人由 AI 从候选池猜测填充。设计完成后的开发、提测均为纯人工动作，禅道同步仅 RESERVED，无 AI 审核与自动化发布。

## 3. 目标与范围

1. 需求录入增加“研发规范”选择（默认 SDD，可选常规）；旧数据视为常规。
2. 需求澄清阶段可选择审核员；选中后任务负责人默认全为审核员，支持按任务分别指派。
3. “AI任务评估”与“任务评估”两个页签合并为一个“任务评估”页签（AI 状态与摘要只读区 + 人工编辑区），列表“去评估”弹窗同步。
4. SDD 模式评估：定向读取知识库 SDD 流程规范做设计评估，产出 SDD 三件套内容；任务拆解从 SDD tasks 摘要（任务项、改动点、工时、改动系统），负责人默认不填；确认时发布三件套到需求迭代目录。
5. 设计完成后自动在研发分支启动 AI 开发（复用平台 Agent 基础设施），失败可重试。
6. 提交测试先 AI 审核：有缺陷返回审核不通过并停留开发中，人工确认后可强制提测；确认提测后调用真实禅道 API 创建测试单，并用 Jenkins 发布所选测试环境；测试单与构建回执入库展示。
7. 测试通过及以后阶段流程不变；非 SDD 模式评估行为保持现状。

### 明确不做

- 不改测试通过之后的阶段流转与既有业务规则（暂停/关闭/验收等）。
- 不做生产环境 Jenkins 发布（沿用既有边界：仅测试环境）。
- 不迁移历史数据研发规范（NULL 按常规处理）；不回填历史需求审核员。
- 不在代码中硬编码禅道/Jenkins 凭据；未配置时明确报错，不伪装成功。

## 4. 验收标准

| 编号 | 可观察的验收条件 | 核对方式 |
| --- | --- | --- |
| AC-01 | 录入弹窗可选研发规范且默认 SDD，提交后入库并可回读；旧数据默认常规 | Service/Controller 测试 + 页面联调 |
| AC-02 | 澄清页签可选/修改审核员（活跃账号），保存后详情与评估页签可见 | Service 测试 + 页面联调 |
| AC-03 | 详情仅一个“任务评估”页签，含 AI 状态/摘要只读区与编辑区；“AI任务评估”页签移除；列表“去评估”弹窗同步 | 前端构建 + 页面联调 |
| AC-04 | SDD 模式：评估生成读取知识库 SDD 流程规范，产出三件套内容；任务拆解含任务项/改动点/工时/改动系统且负责人为空 | Service 测试（知识库读取、生成变量） |
| AC-05 | 确认时任务负责人规则：指派>审核员默认；无两者时 SDD 模式拦截；三件套发布到需求迭代目录 | Service 测试 + 归档产物核对 |
| AC-06 | 设计完成后自动创建并启动 Agent 开发任务（分支=研发分支），状态可查、失败可重试 | Service 测试（stub Agent） |
| AC-07 | 提交测试先 AI 审核：有缺陷停留开发中并展示缺陷；人工确认强制提测记录确认人；通过路径直接提测 | Service/Controller 测试 |
| AC-08 | 确认提测：禅道建单（真实 API，未配置明确报错）+ Jenkins 触发所选测试环境构建；回执与测试单信息入库展示 | 本地桩测试 + 用户配置后联调 |
| AC-09 | 非 SDD 模式评估、测试通过后流程与现状一致 | 回归测试 |

约束：不安装软件；真实外部调用（禅道/Jenkins/GitLab 发布）仅在用户配置就绪并授权后联调；遵循代码风格与既有权限模型。
