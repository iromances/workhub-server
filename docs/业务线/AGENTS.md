# 业务线文档指引

本目录按 WorkHub 的业务线与需求归档文档。先核实业务线，再读取该业务线的 `系统现状.md`；处理具体需求时，再进入相应需求目录。

## 目录与系统字段

```text
docs/业务线/{业务线编号}-{业务线名称}/
├── 系统现状.md
└── {需求编号}-{需求名称}/
    ├── 研发方案.md、测试用例.md       # 选择原有流程时
    └── SDD/                         # 选择 SDD 流程时
        ├── proposal.md
        ├── design.md
        ├── tasks.md
        └── 验证记录.md               # 其他契约、ADR 按该流程按需生成
```

以上两套产物按本次选定流程生成，不要求同时创建。

| 目录部分 | 权威来源 | 约束 |
| --- | --- | --- |
| 业务线编号 | `businessLineCode` | 系统生成的稳定编号，如 `BL000001`；不能使用数据库 `id` 或 GitLab 组名 |
| 业务线名称 | `businessLineName` | 使用系统当前名称，不能自取简称 |
| 需求编号 | `approvalCode` | 使用需求/审批编号；`intakeId` 仅用于查询，不能代替归档编号 |
| 需求名称 | `requirementName`，为空时取 `approvalTitle` | 使用系统记录，不能凭文档标题猜测 |

业务线通过 `get_business_line_context`、`list_mcp_targets` 或 WorkHub 业务线接口核实；需求通过 `get_requirement_test_context`、`get_intake_detail` 等受控工具定位，同时核对所属业务线。上下文没有完整字段时继续读取需求详情，不虚构名称、编号或归属，也不创建“无编号”需求目录。

文件名中的 `/`、反斜杠和控制字符统一替换为 `_`，去除首尾空白；只处理文件系统无法安全表达的字符，文档内保留系统原始名称及编号。按稳定编号查找已有目录；名称变化时重命名并同步引用，不重复建档。

## 系统现状与需求文档

- `系统现状.md` 是业务线长期入口，至少说明系统范围、环境、分支、提交、核验时间、证据来源和待核实事项；按实际资料逐步补充业务流程、架构、接口、数据模型及运行配置。
- 历史资料迁入时保留原日期、代码版本和证据边界。目录整理时间不等于系统重新核验时间；旧资料不能单独证明当前环境的实现。
- 需求目标、方案、任务、审批、测试与交付记录归入需求目录。未实施或未核验的内容不得写成已上线现状；历史资料中保留的建议须明确标为历史参考。
- 业务线级原始附件可与 `系统现状.md` 同目录存放并在现状中链接；需求附件放入对应需求目录。不得凭附件或专题名称编造需求归属。
- 开发前进入[研发规范入口](../研发规范/AGENTS.md)，由用户在本次任务选择原有流程或 SDD 流程。已明确的选择不重复询问；仅整理目录、修正路径和维护工作指引无需选择。
- 跨业务线需求以 WorkHub 记录的归属业务线建立唯一主目录，相关业务线的 `系统现状.md` 链接该目录并说明影响；不能复制为多个独立需求。归属不明确时先确认。
- 交付后仅将实际验证的变化同步到 `系统现状.md` 并关联需求文档，保留规格审批和验证证据在需求目录中。

业务定位、环境与分支解析、知识库和生产资源访问遵守[业务运维分析方法](../研发规范/业务运维分析方法.md)。外部知识库的 `raw/`、`wiki/` 结构仍以 WorkHub 配置为准，与本目录分别管理。
