# 智能柜生产功能梳理与缺陷审查

## 1. 总体结论

智能柜主业务链路较完整，覆盖项目配置、客户进件、签约交付、设备资产、账单还款、清结算、渠道收益及运营财务。

资金功能已覆盖主要业务场景，但异常恢复、并发保护、金额累计、状态推进和事务边界在不同入口之间不一致。

## 2. 功能清单与核心流程

### 2.1 业务场景与产品模式

代码覆盖三类业务场景：

- 智能零售柜。
- 二轮车换电。
- 货车驻车电池。

### 3.1 FIN-01／P1：提现请求超时被当作确定失败，并解冻资金

**触发条件：** 支付系统已经受理提现，但返回过程中发生网络超时或其他 Feign 异常，业务系统未收到确定结果。

**现有行为：** 提现请求发出前保存商户请求号及处理中状态；捕获异常后却直接调用失败处理，将提现标记为失败并退回可用余额。后续查询遇到本地失败状态直接返回，不再向支付系统确认结果。

**影响：** 客户可能再次提现，而第一笔提现仍可能打款，导致本地余额与外部付款结果不一致。

**修复方向：** 将请求超时等不确定结果保留为“结果未知／处理中”，保持资金冻结，通过原请求号查询或补偿确认终态后，再决定扣减或解冻。

### 3.2 FIN-02／P1：同一账户的不同提现单并发处理，可能覆盖余额

**触发条件：** 同一账户的不同提现单并发更新结果，或提现结果处理与其他账户资金变动并发执行。

**现有行为：** 提现成功／失败处理只锁提现单，普通查询账户后直接计算并覆盖余额，没有锁住共用账户。申请提现时虽有账户行锁，但结果处理没有使用相同保护。

**影响：** 两个处理过程可能基于同一旧余额更新，后写入的值覆盖前一笔结果。例如冻结 300 元，两笔 100 元、200 元提现同时成功，最终冻结余额可能留下 100 元或 200 元，而不是 0 元。

**修复方向：** 所有账户资金变动统一使用账户行锁或原子余额更新，并保持一致的加锁顺序；单据锁不能替代账户维度的并发保护。

### 3.3 FIN-03／P1：批扣展开客户账单时丢失项目限制

**触发条件：** 同一客户同时有项目 A、B 的到期未结清账单，项目 A 允许当前节点代扣，项目 B 不允许。

**现有行为：** 第一阶段筛出允许当前节点代扣的项目及客户，第二阶段却只按客户、结清状态和到期日期查询账单，没有继续限制项目范围。

**影响：** 项目 A 将客户带入批扣后，项目 B 的账单也可能被加入扣款任务，违反项目级代扣规则。

**修复方向：** 将已筛选出的项目范围贯穿客户筛选、账单查询和扣款前校验，确保最终扣款对象仍属于本次允许代扣的项目。

### 3.4 FIN-04／P1：已有支付处理中订单时，批扣仍继续发起

**触发条件：** 账单已有线上支付处于处理中，批扣任务又扫描到该账单。

**现有行为：** 检测到处理中交易后执行的 `continue` 只跳过内部交易记录循环，没有跳过外层账单循环，后续仍创建新的扣款任务。批扣自行创建新支付订单，共享支付系统当前也未启用同一账单的处理中拦截。

**影响：** 原支付尚未结束时，同一账单可能再次发起扣款；新订单号的幂等保护无法阻止这种同账单重复请求。

**修复方向：** 检测到处理中订单后立即跳过整张账单，并补充账单维度的原子互斥保护，避免主动支付与批扣并发发起。

### 3.5 FIN-05／P1：支付回调“收到过”被当作“处理成功”

**触发条件：** 非银行转账的支付回调首次到达，通知日志已保存，随后在账单核销、账户更新等步骤发生运行时异常，业务事务回滚。

**证据链：** HTTP 回调先执行 `valiateRepeatPayNotify`，再执行有事务的 `receivePaymentResult`。去重方法使用 `NOT_SUPPORTED` 保存日志，按订单号统计通知次数，达到 2 次就拒绝；统计条件没有业务处理成功标记。第二次回调又插入一条日志，随即被拒绝，无法进入业务处理。

**影响：** 外部付款已成功，本地账单／交易可能继续停留在未完成状态，普通回调重试不能恢复。成功处理后的重复通知也会被异常拒绝。已有订单终态幂等判断位于后续处理内部，不能解决前置次数拦截。

**修复方向：** 以业务成功结果作为幂等依据；保留通知接收记录，并区分待处理、处理中、成功、失败。失败记录允许重放，业务入账与成功标记在同一事务内完成，并对同订单并发回调做原子保护。

### 3.6 FIN-06／P1：退款请求记录会随本地事务回滚消失

**触发条件：** 原路退款审批调用共享支付系统，对方已受理或创建退款订单，但本地等待响应超时、响应解析失败，或后续本地更新抛出异常。

**证据链：** `executeApproveItem` 在 `TransactionTemplate` 中执行审批；`approveOne` 在同一事务内更新审批状态、保存 `refund_payment_flow`，紧接着调用外部退款接口。请求异常向外抛出并回滚事务。保存请求流水的方法采用默认 `REQUIRED`，没有在外部调用前独立提交。再次审批会重新生成 `RR` 请求号。

**影响：** 共享支付系统的退款不会随 SAPS 数据库事务回滚；SAPS 却可能恢复待审批状态并丢失该次请求流水。退款回调按请求号查流水时找不到记录，主动查询补偿也失去关联；重新审批使用新请求号，增加重复请求风险。是否发生重复到账还取决于支付侧累计退款限制，不能据此断言必然超额退款。

**修复方向：** 先提交退款意图、固定请求号和处理中状态，再调用外部系统；超时保留未知／处理中，通过同一请求号查询、重试和回调收敛。数据库回滚不能被用来撤销已经发出的资金请求。

### 3.7 FIN-07／P1：缴费单超额回调没有给交易分配应核销金额

**触发条件：** 同一缴费单存在多笔在途付款，先到账的一笔降低未付金额，后到账的一笔超过此时剩余未付。默认缴费单策略允许部分付款，建交易时也明确跳过缴费单的“已有支付处理中”检查。

**示例：** 缴费单未付 100 元，先后创建 40 元和 100 元付款请求，均在未付仍为 100 元时通过校验。40 元先成功后，另一笔 100 元到账，正确处理应为核销剩余 60 元，并对超收 40 元形成明确的退款或待处理记录。

**现有行为：** 超额分支只增加订单的 `settleAmount`，设置订单与交易的 `rechargeAmount`，遗漏交易的 `settleAmount`。后续实际传给缴费单核销的却是交易 `settleAmount`。本轮生产表结构核实该字段默认值为 `0.00`，普通建单路径没有另行赋值，结果会以 0 元尝试核销，无法正确冲减剩余应收；不能把订单层记录的 60 元视为已经完成核销。

自动重复付款退款仅覆盖“首笔款缴费单已经成功且未付为 0”等条件，不覆盖上述仍有剩余应收的重叠付款。驻车电池策略也有相同漏赋值分支，但其部分付款限制不同，不能把示例直接套到所有项目。

**修复方向：** 明确分配 `本次核销额=min(实收额, 当前未付额)`，同时写入订单、交易及核销请求；超额款逐笔关联退款或待处理记录。补齐同一缴费单多笔在途支付、付款与线下核销交错的处理规则。

### 3.8 FIN-08／P1：支付接口的客户身份可由请求参数决定

**触发条件：** 已登录客户提交其他客户的编号、订单号等有效标识；取消支付还需目标订单处于允许取消的状态。

**证据链：** 客户端支付、取消支付、支付结果查询接口，只在请求的 `tenantCode`／`customerCode` 为空时才使用登录信息。取消请求 DTO 可接收这两个字段；业务层用请求中的客户编号查询订单，再与请求中的租户编号比较，没有与当前登录人绑定。网关认证后补充的是请求头，已检查的请求体过滤器原样返回请求体，不能覆盖 JSON 中的客户编号。

**影响：** 已查代码路径允许登录人指定其他客户身份，查询他人支付状态或进入他人支付订单的取消流程。取消仍受订单状态和支付渠道结果限制；本轮没有在生产发起越权请求，也没有证据认定已经发生越权扣款或数据泄露。

**修复方向：** 客户端接口的租户和客户身份必须由可信登录态派生，并在业务层校验订单归属。确有运营代客操作需求时，应使用独立权限入口并保留审计，不能复用可由客户端覆盖身份的普通客户接口。

### 3.9 FIN-09／P2：缴费单费用科目的累计已付金额被覆盖

**触发条件：** 使用允许部分付款的缴费单策略，同一费用科目被分两次或多次核销。

**现有行为：** `coresettle` 对科目明细执行 `setPaidAmount(settleAmount)`，保存的是本次金额；缴费单主表则执行“原已付＋本次金额”。

**示例与影响：** 单科目应付 100 元，先付 40 元、再付 60 元后，主表显示已付 100、未付 0；科目明细却显示已付 60、未付 0。累计已付口径错误，主单与科目不一致，影响依赖该字段的明细展示和财务核对。驻车电池等限制部分付款的项目不能直接套用此触发条件。

**修复方向：** 科目累计已付应增加本次金额；将“累计已付”和“本次付款明细”作为不同字段口径，验证主表、科目及付款记录之间的金额关系。

### 3.10 FIN-10／P2：渠道分润对账单部分核销后被直接结清

**触发条件：** 运营输入大于 0、但小于剩余未付的分润核销金额。前端金额可编辑，后端只拒绝超过未付的金额。

**现有行为：** 系统正常增加已付、减少未付，但不判断余款，直接将核销状态设为 `CHECK`、结算状态设为 `SETTLED`。后端下一次核销拒绝 `CHECK`，前端也隐藏已核销单据的核销按钮。

**示例与影响：** 应付 100 元，核销 30 元后仍有 70 元未付，却显示已结清；剩余款项无法通过正常入口继续核销。该问题限定于已追踪的渠道分润入口，不能泛化所有对账单类型。

**修复方向：** 有余款时保留部分核销／未结清状态；如果业务规定一次全额核销，前后端应明确校验核销金额等于未付金额，而非接受部分金额后直接关单。

### 3.11 FIN-11／P2：对账单核销没有覆盖完整业务操作的事务

存在两个已确认的事务边界问题：

1. **渠道分润核销：** 公开入口 `shareBenefitVerification` 无事务，同类直接调用带 `@Transactional` 的 `updateResource`，没有经过事务代理。主单更新后若费用明细更新异常或乐观锁失败，前一步主单更新不能随之撤销，可能出现主单已核销、明细未更新。
2. **普通对账单核销：** 公开入口无总事务，先调用另一服务的 `rollBackStatement`，再调用 `coreVerification`，两者各自使用 `REQUIRED`。存在付款日期之后的逾期费记录时，前一阶段会删除相应费用记录、修改应收及已付金额并提交；后一阶段失败不能回滚前阶段，留下已改金额但尚未完成正式核销的状态。

**影响：** 一次核销可能只完成部分持久化操作，造成主单、科目、付款明细或关联账单不一致。触发通常需要数据库异常、版本冲突等，因此本项定为 P2，而非仅因涉及资金自动定为 P1。

**修复方向：** 由通过代理调用的公开业务入口统一承载本地事务，覆盖金额、费用回滚、付款明细、关联账单和终态更新；跨系统通知在提交后可靠执行。保留正确的乐观锁与行数校验，不能仅补注解而不核对调用关系。
