# 业务运维分析方法

本文档统一维护业务线代码、知识库、数据库、服务器资源和禅道缺陷的定位、排查、安全约束和输出要求。

当用户询问某个业务线的问题时，先归类为：代码理解、需求/业务口径、数据库数据核查、服务器/日志排查或综合排查。不要凭记忆或推理猜测资源位置。

仓库内的文档以 `docs/业务线/{业务线编号}-{业务线名称}/系统现状.md` 为业务线入口；具体需求文档直接放在该业务线下的 `{需求编号}-{需求名称}/`，详见[业务线文档指引](../业务线/AGENTS.md)。业务线和需求编号均从 WorkHub 核实，不从目录名反推系统归属。

## 1. 识别业务线和环境

- 业务线定位必须以 WorkHub 配置为准，不得按本地代码目录、仓库名或历史经验反推。
- 如果用户没有明确业务线，先反问。
- 如果问题涉及数据、服务状态、日志或生产现象，必须同时明确环境，无法确认时先反问。
- 业务线标准来源是 WorkHub 中维护的业务线配置：`/api/projects/business-lines`、`pm_business_line` 或 MCP 的 `list_mcp_targets` 返回结果。

### 1.1 环境和分支解析

- 开始排查前必须确认目标环境，并按环境解析代码分支，方便使用 MCP 提供的对应环境 DB 或 SERVER 资源。
- 用户已指定需求（如需求 ID、审批编号或需求名称）时，必须先调用 MCP `get_requirement_test_context` 定位需求，获取需求关联的业务线、涉及系统、研发分支、测试环境资源和禅道地址。需求无法唯一定位时不得猜测，应请用户补充可唯一定位的信息。
- 在测试环境排查中，只要用户已指定需求，代码口径必须使用该需求对应的远程研发分支，其优先级高于测试环境当前发版分支。不得用本地当前分支、`master` 或同名历史分支代替需求研发分支。
- 用户明确给出需求研发分支时，以用户指定的分支为排查口径，并使用需求上下文补齐业务线和环境资源。如该分支与 WorkHub 需求中记录的研发分支不一致，应先明确报告差异，不得静默替换。
- 使用需求研发分支前，应安全刷新远程引用并确认 `origin/{developmentBranchName}` 存在，记录实际核对的远程提交 SHA。排查优先直接读取远程跟踪分支内容；不得为了排查强制切换、重置、清理或覆盖存在未提交改动的工作区。
- 用户未另行指定分支时，生产环境默认使用 `master`，无需重复确认分支。
- 需求涉及多个仓库或跨业务线时，必须分别确认每个相关仓库中对应的远程研发分支和提交；某仓库不存在该分支时，应将其标记为证据缺口，不得自动降级到 `master` 后继续得出该需求的实现结论。
- 完成环境和分支解析前，不得开始代码、配置、日志或数据库排查。
- 排查开始时必须先输出当前业务线、GitLab 项目组、环境、需求标识、解析后的远程分支、提交 SHA 及其来源，确保后续结论具有明确上下文。

### 1.3 消费分期与嘉泰消费分期跨业务线规则

消费分期业务线（`BL000004`，GitLab 组 `asset-plateform`）的部分项目采用再保理模式，嘉泰消费分期业务线（`BL000003`，GitLab 组 `th-jiatai-amp`）是相关再保理链路的资方侧，因此两条业务线之间存在订单、支付、核销、放款和状态同步等跨系统关联。

处理消费分期或嘉泰消费分期的问题分析、开发、需求梳理和测试任务时，必须先判断是否涉及再保理模式或上述跨系统链路；只要涉及，就必须同时纳入 `BL000004` 与 `BL000003` 两条业务线，分别解析两边的关联系统、GitLab 项目组、代码仓库、目标环境、开发分支、SERVER/DB 资源、服务入口、测试数据和上下游影响，不得只根据需求主业务线、主仓库或单侧接口得出结论。

跨业务线任务开始时必须明确输出两条业务线各自涉及的系统和资源边界。开发时应区分两边仓库的改动归属；需求梳理时应覆盖两边状态流转和接口契约；测试时应覆盖消费分期业务侧、嘉泰资方侧以及跨系统同步结果。只有在结合需求、代码和业务配置确认任务不涉及再保理或跨系统链路后，才可以限定为单业务线处理。

## 2. 找业务线代码

- 本仓库只代表 WorkHub 后端自身；用户问其他业务线系统代码时，不要默认当前仓库就是目标业务系统代码，也不要先扫 `workhub-*` 模块得出业务结论。
- 必须先解析业务线定位上下文，再检索代码。推荐顺序：
  1. 优先调用 MCP `get_business_line_context` 或 `list_mcp_targets`，确认业务线名称、`gitlabGroupName`、涉及系统和代码工作区路径。
  2. 如果 MCP 工具不可用，再使用 WorkHub HTTP 接口 `/api/projects/business-lines?keyword={业务线}` 查询；如果本地服务也不可用，应说明定位阻塞并请求启动/同步，不能直接扩大到全工作区猜测。
  3. 只有已经确认 `gitlabGroupName` 后，才进入对应 group 的代码范围检索。
- 业务线远端代码入口来自项目管理中的业务线 `gitlabGroupName`，配合系统配置 `gitlab.global.webApiUrl`、`gitlab.global.accessToken` 和 `gitlab.global.sshHost` 获取 GitLab group 及子组仓库。
- 业务代码统一位于 `/Users/aslight/IDEAWorkspace/{gitlabGroupName}`；其下每个仓库目录名沿用 GitLab project `path`，如果 `path` 为空则从仓库 URL 末段推断并去掉 `.git`。
- 需要补齐或刷新业务线代码时，使用 MCP 工具 `sync_gitlab_group_repositories`。工具以完整历史克隆缺失仓库；对已有完整仓库执行安全 fetch，对已有浅仓库先补全历史；随后将当前分支纯快进到同名远端分支。无冲突的本地未提交改动会保留；分支分叉或工作区覆盖冲突时不更新并报错。不创建 commit，不 stash、不变基、不强制重置、不清理、不切换分支，也不覆盖本地改动。
- 使用工作区前必须确认：
  - 已通过 WorkHub 配置确认 `gitlabGroupName`。
  - 仓库 `git remote -v` 指向该 GitLab group，例如 `...:{gitlabGroupName}/{repo}.git`。
  - 当前分支和提交符合目标环境或需求分支；回答中标明仓库、分支和提交。
- 嘉泰消费分期前端仓库需额外区分：`jiatai-amp-opadmin` 是当前运营后台前端，`jiatai-amp-admin` 是演示用旧系统。处理嘉泰消费分期业务前端需求时，除非用户明确点名 `jiatai-amp-admin`，不要把改动落到 `jiatai-amp-admin`。
- 不要因为仓库名、包名或关键词相似就分析其他业务线仓库。例如“设备金融”“叉车”“资产”等仓库中的命中，不能自动作为“智能柜”等其他业务线的证据。
- 没有找到业务线工作区或目标仓库时，应优先使用 `sync_gitlab_group_repositories` 补齐；无法同步或无法读取远端时，要明确说明缺口，不要用无关仓库替代。
- 回答代码问题时说明使用的工作区，并尽量标明仓库、分支、提交或文件路径。

### 2.1 业务线代码理解快速流程

当用户问“某业务线是否有某逻辑/接口/定时任务/配置”时，按以下顺序执行：

1. 识别业务线名称和业务关键词。若业务线已明确，先不追问；若业务线不明确，先反问。
2. 解析业务线配置，拿到 `gitlabGroupName` 和涉及系统。禁止跳过这步。
3. 定位仓库范围：使用 `/Users/aslight/IDEAWorkspace/{gitlabGroupName}`，仓库目录名使用 GitLab project `path` 或仓库 URL 推断名，并用 `git remote -v` 校验远端 group。
4. 只在已确认范围内检索关键词。关键词应同时覆盖中文业务词、英文标识、枚举和配置键，例如“回购”类问题可同时查 `回购`、`强制回购`、`buyback`、`repurchase`、`BUYBACK`、`BUY_BACK`、`needBuyback`。
5. 抽取证据链：业务线映射、仓库来源、项目/产品标识、枚举或配置、入口接口/定时任务、核心处理器或 SQL。
6. 结论必须区分“确认存在”“未在已确认范围内发现”“定位受阻”。如果需要确认生产是否启用某配置，再转入数据库只读核查流程。

## 3. 找知识库文档

- 项目知识库根目录必须通过 MCP 工具 `get_knowledge_context` 或 `list_mcp_targets` 读取项目配置中的 `projectVaultPath`，不要使用本地硬编码路径。
- MCP 工具 `get_knowledge_context` 只返回项目配置中的知识库根地址、业务线 raw/wiki 根目录和归档路径结构，不直接读取知识库文件正文。
- 定位知识库后按渐进披露顺序读取：先进入业务线 `index.md` 或现有业务线入口页，再按问题读取相关长期专题页；只有问题涉及接口字段、原始需求或历史依据时，才继续读取专题页链接的 `raw/` 原文。
- 业务规则和流程优先读业务线长期 wiki，系统实现问题再结合目标分支代码；接口文档是契约参考，不能单独证明目标环境已实现或启用。
- 检索知识库时必须先用业务线中文名圈定范围，再用项目名、系统名、审批编号、需求名称、业务关键词收敛范围。
- 优先读取相关 Markdown/TXT 文档、需求迭代文档和原始材料归档路径，不要无差别扫描整个知识库。
- 知识库内容只能作为业务口径和历史背景证据；如果文档与代码、数据库或用户当前描述冲突，要指出冲突并说明采用哪类证据。

## 4. 查数据库和服务器

- 先通过 MCP 工具 `list_mcp_targets` 查看已配置的业务线、环境、数据库目标和服务器目标，优先按 `businessLineCodes + systemNames + environmentCode + targetKey + profileKey` 选择最小范围；`systemNames` 为空的资源覆盖所绑定业务线下所有系统。
- 生产日志排查首选 MCP `search_business_logs`，按业务线、环境、服务、时间和级别实时查询受控 ES 范围；调用方不得提交索引或 Query DSL。涉及普通业务过程、上下游请求和响应时应显式包含 `INFO`，时间窗口先从告警前后 15 分钟开始收敛。
- 数据库访问只使用 MCP `run_readonly_query`，默认选择只读 profile，例如 `readonly`；禁止绕过 MCP 直连数据库、SSH 隧道、堡垒机或手工使用连接串。
- SQL 必须是本次问题所需的最小只读查询，禁止写入、DDL、多语句、导出、高风险函数和无边界全表扫描。
- 服务器访问只使用 MCP `get_service_status`、`read_service_logs` 和 `search_service_logs`，作为 ES 缺失、日志未采集、需要核对进程状态或原始历史文件时的补充；生产服务器需要堡垒机时由 WorkHub 服务端按资源配置建立受控隧道。只能读取受控服务状态、服务日志或在单个白名单日志文件中执行固定字符串检索；ZIP 历史日志检索不解压写盘，配置白名单时必须限制在白名单内，白名单为空表示对应维度不限制；禁止要求或执行任意 shell 命令。
- 不要在回答中暴露数据库密码、Access Token、SSH 密码、私钥、堡垒机凭据或本地 catalog 中的敏感字段。

## 5. 禅道查询和 Bug 提交

### 5.1 查询禅道

- 指定需求后，先从 MCP `get_requirement_test_context` 返回结果中获取已关联的 `zentaoUrl`、研发分支和测试上下文，不要凭需求名称在禅道中模糊猜测关联项。
- 查询禅道中的需求、Bug、任务、状态或历史时，优先使用 MCP 提供的专用查询能力；如当前没有专用工具，先用 `list_mcp_targets` 定位 `featureTags` 包含“禅道”的只读数据库资源，再通过 `run_readonly_query` 执行本次问题所需的最小只读查询。
- 禅道查询同样遵守 MCP 安全边界：不直连数据库，不执行写入 SQL，不绕过权限，不在回答中暴露账号、Token 或其他敏感信息。
- 提交 Bug 前必须先查询同一需求下是否已有相同或高度相似的未关闭 Bug，避免重复提交。

### 5.2 通过浏览器提交 Bug

- MCP 只读通道不承担禅道写入。用户明确要求“提 Bug”“创建 Bug”或授权提交时，使用用户已登录的浏览器打开需求对应的禅道项目并提交；不得要求或记录用户的禅道密码。
- “排查”“诊断”“查问题”只授权只读核查，不等于授权创建 Bug。未获得明确提交授权时，可以准备 Bug 草稿，但不得在禅道执行最终提交。
- Bug 内容至少应包含：简明标题、关联需求、测试环境、影响系统、核对的远程研发分支与提交 SHA、前置条件、复现步骤、实际结果、预期结果、发生时间，以及经脱敏的订单号、流水号、Trace ID、日志或截图等证据。
- Bug 归属的产品、项目、模块和关联需求应以 MCP 查询结果或需求的 `zentaoUrl` 为准；严重程度、优先级、指派人、截止日期等无可靠依据的字段不得臆测，应保留项目默认值或请用户确认。
- 提交前应在浏览器页面核对关键字段和证据摘要；提交成功后返回 Bug 编号、标题和可访问地址。如浏览器未登录、无权限或无法唯一确定项目，应停止提交并说明阻塞原因，不得改投其他项目。

## 6. 输出要求

- 先给结论，再列支撑依据。
- 区分“代码证据、知识库证据、数据库结果、服务器日志、推断”。
- 如果只查到部分资源，要说明缺口。
- 对生产问题，默认只做诊断和只读核查；任何修复、重启、数据修正、DDL/DML、配置变更都必须等用户明确确认。
- 没有证据时使用“推测”“需要确认”等表述，不要把 AI 生成内容包装成已确认事实。
- 已核实的长期业务规则和系统实现沉淀到对应业务线的 `系统现状.md`，注明环境、分支、提交、时间和证据；需求方案、任务及验证记录归入真实需求目录，依本次已选择的原有流程或 SDD 流程生成。
- 未实施的设计、未经核验的上线结论不写成系统现状。跨业务线问题分别说明各方影响，正式需求文档在系统归属业务线保留唯一主目录，其他业务线链接引用。
