# 代码审查方法

## 1. 适用范围与原则

用户要求 AI review、代码审查、分支审查或复查审查意见时，遵守本指引。适用于 WorkHub 自身及协作范围内的业务仓库；资源定位和访问继续遵守[业务运维分析方法](业务运维分析方法.md)，代码约定见[共用代码风格](代码风格.md)。

审查目标是找出本次改动引入、具有明确触发条件和影响的可操作问题。不能仅凭“理论上可能出错”形成确定缺陷，也不能因为生产暂时没有数据就认定新代码正确。

- 只读审查可直接进行，不因 review 本身要求新建 SDD 规格或等待审批。
- Review 不代表授权修改业务代码、执行数据库变更、部署、启动应用或安装软件。后续修复按仓库研发流程及用户授权执行。
- 保留现有工作区改动；默认直接读取目标提交，不为审查切换、重置或清理工作区。
- 不为凑数量列问题。优先报告行为错误、数据一致性、兼容性及明确的安全问题；风格偏好不能冒充功能缺陷。

## 2. 先固定审查对象

开始审查时核实并记录：

1. 业务线或共享系统、GitLab 项目组、实际仓库路径与 remote。按 WorkHub 配置和已核实的目录约定定位，不凭目录名推断业务归属。
2. 用户指定的分支、远程提交 SHA、比较基线及其来源。优先使用 MR 目标分支或用户指定基线；采用 `master` 等默认基线时明确说明依据。
3. 安全刷新相关远程引用，通过 merge-base 和三点 diff 确定本分支引入的变化。不能把基线已有问题直接列成本次新增缺陷。
4. 跨仓库调用涉及的各仓库提交。同名分支不一定在所有仓库存在；缺失时说明范围和证据缺口，不静默用其他分支代替。
5. 已指定的需求及规格；没有关联需求时如实说明，不自行编造业务验收标准。
6. 若判断涉及数据、配置或部署状态，确认目标环境。单纯静态审查不需要强行指定环境；静态结论不能写成生产事实。

区分“待发布分支”“本地当前分支”和“实际部署版本”。数据库已有表或字段，不能单独证明目标分支已经部署；远程分支 SHA 也不能当成生产版本。

## 3. 沿调用链核对行为

先读完整 diff，再围绕改动追踪必要的上下游、持久化和测试，形成“输入 → 转换 → 存储 → 查询/输出”的证据链。

| 变更类型 | 必须核对的行为 |
| --- | --- |
| DTO、字段及映射 | 字段真实业务含义、来源协议、序列化名称、上下游契约、读写是否完整；付款方/收款方、我方/对方、借方/贷方不能仅按变量名等同。 |
| 唯一键、幂等及流水 | 新旧唯一性口径、NULL 语义、重复回调、批内重复和并发路径；区分代码允许的重复与生产已有的重复。 |
| DDL、DML及迁移 | 当前表结构、受影响数据是否存在、迁移覆盖范围、执行顺序、滚动发布兼容性；脚本注释不能替代数据证据。 |
| 配置或业务键变更 | 哪些读写、定时任务和历史记录使用旧值，是否需要迁移；任务参数是否实际存在必须另行核实。 |
| 支付及状态推进 | 成功、失败、中间态、重试、通知、补偿、退款和对账链路，金额精度及事务边界。 |

不要机械地对每个改动执行全部检查。按实际影响范围选择验证，读取最小必要上下文；已有保护、上游校验或框架约束能够排除的问题不再列为缺陷。

优先使用可隔离的现有单测或最小复现验证关键路径。先确认测试不会连接真实依赖、启动受限应用或触发渠道交易；无法运行时明确说明。`git diff --check` 只能证明差异格式检查结果，不能替代编译、功能或数据库验证。

## 4. 涉及生产影响时核实前提

### 4.1 查询边界

- 按[业务运维分析方法](业务运维分析方法.md)定位环境和受控资源，只通过 MCP 只读查询数据或日志。
- 先核实表结构、字段和必要索引，再按应用、渠道、商户、主键或时间区间限定查询。优先用存在性查询或少量样本，不为 review 无边界统计或导出整表。
- 只读取支撑结论所需字段；账号、流水号、报文等证据脱敏，不回显凭据或完整敏感信息。
- 明确查询目标、过滤条件、核验时间、结果及是否截断。空结果只说明本次范围内没有命中，不能扩大为整个系统没有数据。
- 没有数据权限、环境未明确、查询失败或结果不足时，记录为“待核实”，不能把“未查到”写成“确认没有”。

### 4.2 存量数据与新行为分别判断

**存量迁移问题必须先证明存在需要迁移的对象。** 例如新增序号参与去重：先核实旧流水是否存在、序号能否从旧字段还原，以及发布后是否会重新拉取。不能仅看到新增列默认为 NULL 就认定本次生产发布一定造成重复流水。

**新代码的业务错误可以在没有生产错误数据时成立。** 例如入账场景中，把对方开户行写到收款方字段：可通过渠道契约、借贷方向和映射代码证明错误，但不能声称生产已经发生错配。生产表为空只能排除当时的存量影响，不能排除后续正常业务输入触发该错误。

**配置变更的影响必须逐项核实。** 更改商户号后，历史查询可能使用新值过滤，但只有旧值下实际存在历史记录，才能确认迁移影响；定时任务参数是另一项前提，不能由“配置里有旧值”推断“任务一定传旧值”。

数据库结果只代表核验时点。若发布前仍可能产生旧格式数据，应说明需在发布窗口复核，而不是继续把已排除的当前存量问题保留为阻断缺陷。

## 代码质量

- 异常捕获和处理是否规范，不能存在吞异常的情况
- 日志级别使用是否规范，确保异常被正确的打出error

## 5. 结论分类与输出

每条审查意见都应能回答：改动位置是什么、在什么输入或状态下触发、为什么现有实现无法处理、造成什么可观察影响、有什么证据。

| 分类 | 判定依据 | 输出要求 |
| --- | --- | --- |
| 已确认代码缺陷 | 在系统允许的场景下，代码、契约或隔离验证能够证明错误 | 明确触发条件和修复方向；生产未验证时直接说明，不要求先发生生产故障才报告。 |
| 已核实环境影响 | 已确认缺陷或迁移行为，且目标环境的数据、配置或日志证明相关前提存在 | 注明环境、范围、核验时间和脱敏证据；“具备触发条件”和“已经发生故障”仍需区分。 |
| 待核实风险 | 关键业务前提、数据、配置或调用路径尚未证实 | 单独列为待核实项，说明缺什么证据；不能作为确定 P1 或发布阻断结论。 |
| 当前不成立/撤回 | 证据排除了当前审查范围内的触发前提，或先前理解错误 | 明确撤回或修正原意见，不用其他未核实风险替代原结论。 |

优先级依据已证明的影响、触发范围和紧迫性确定。不能因为涉及支付、数据库或生产就自动定为 P1，也不能按措辞的严重程度代替证据。

建议输出结构：

1. 先列已确认问题，按优先级排列，每项给出目标提交中的文件位置、触发条件、影响及证据。
2. 单独列必要的待核实项或审查限制。没有确认问题时写“本次审查未发现已确认缺陷”，不等同于保证无问题。
3. 补充审查仓库、分支、SHA、基线、核验环境和日期，以及实际执行的验证。文件行号以审查提交为准；本地文件不是该提交时应说明。

精简描述，不贴完整敏感 SQL 结果或渠道报文，不把未执行的检查写成已通过。静态审查、生产只读核查、测试验证及发布批准是不同结论。

## 6. 用户质疑或要求复查时

直接说明先前究竟查过什么、没有查什么。围绕被质疑意见补齐证据，并明确给出“保留、调整优先级、改为待核实、撤回”中的结论；不为维护原判断扩大风险。

本指引提炼自 2026-09-29 支付中台分支 `feature/channel_account_flow_extend_202609290001` 的审查与复查：存量流水相关判断经生产空表查询后撤回；收款方银行映射仍可由代码证明，但没有生产错误记录证据。该例仅说明审查方法，历史查询结果不能替代后续任务的实时核验，也不能据此长期假设生产表为空。
