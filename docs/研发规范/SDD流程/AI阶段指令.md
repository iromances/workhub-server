# SDD 流程 AI 阶段指令

本文件是给 AI 的可复用工作指令，不是原书逐字 Prompt。使用时先读本目录 [AGENTS.md](AGENTS.md)、[SDD工作流](SDD工作流.md)；若目标需求已有 SDD 规格，再读取其当前版本。只执行当前阶段，不把整条研发链压缩成“请把需求做完”。

## 0. 每个阶段都要先建立上下文

AI 在开始时填写以下工作头；缺项可以标为“待确认”，但不得猜测：

```text
当前阶段：
业务线编号与名称（businessLineCode / businessLineName）：
需求编号与名称：
系统需求来源及业务线归属：
唯一需求主目录：
目标业务线/系统：
目标环境与分支/版本：
本阶段已批准输入及版本：
已核实的现状证据：
允许读取/修改的范围：
本阶段输出：
本阶段不做：
验证方式：
阻塞性待确认问题：
```

以下共同约束始终有效：将原始需求、运行事实、推断、待确认项分开；引用可追溯来源；不得扩大权限或伪造审批；需要人的业务、架构、兼容或风险决定时停止并提出选项。工作头是会话管理辅助，不要求额外创建同名文件。

正式产物根目录为 `docs/业务线/{业务线编号}-{业务线名称}/{需求编号}-{需求名称}/SDD/`，下文 `SDD/` 均相对此需求主目录。需求编号从系统 `approvalCode` 获取，名称取 `requirementName`，缺失时取 `approvalTitle`；具体归档规则见[通用约束](../通用约束.md)。缺少权威编号、名称或归属时可在工作头标为待确认，但不得生成占位正式目录。现状先读所属业务线 `系统现状.md`，再结合目标分支代码和环境证据核实。

## 1. 需求定义：起草 Proposal

**输入：**原始需求、需求管理记录、已确认的业务背景和约束；必要时只读核实当前事实。

**AI 应做：**

1. 将“为什么做、做什么、何时算完成”分开表达。
2. 明列本期范围、非范围、用户场景、可观察的成功标准与异常/边界场景。
3. 区分需求原文与 AI 的理解；对缺失的业务口径、范围或验收条件主动追问。
4. 检查术语和数字口径是否一致，不在本阶段决定技术实现。

**输出：**`SDD/proposal.md` 草案；可使用 [proposal 模板](模板/proposal.md)。

**暂停条件：**无法确定受益对象、目标、非范围或成功标准；不同需求材料相互矛盾。此时输出问题清单，不把推断写成定稿。

**人需确认：**业务意图、范围、非范围、优先级及验收口径。AI 结构化需求，不代替人作这些决策。

## 2. 架构设计：起草 Design 与 ADR

**输入：**已确认的 Proposal、目标环境/分支的代码与配置事实、现有架构和项目约束。

**AI 应做：**

1. 给出系统/模块职责，包括“不负责什么”，画清数据流和关键状态流。
2. 对关键方案列备选项、选择理由及代价；重大且难逆转的决定形成 ADR 草案。
3. 定义接口和数据模型所需的语义，列兼容、迁移、失败处理、幂等、权限、安全、性能、可观测性与回滚约束。
4. 逐条核对 Design 是否满足 Proposal，避免设计出非范围功能。
5. 把未核实的现状、假设和待确认的外部依赖明确列出。

**输出：**`SDD/design.md` 与必要的 ADR 草案；可使用 [design 模板](模板/design.md)。

**暂停条件：**方案必须改变已批准目标或范围；无法确认系统边界、数据归属、兼容承诺；关键风险需要人接受。

**人需确认：**架构、契约边界、选型与风险；AI 可以文档化和比较方案，不能自称架构已获批准。

## 3. 接口契约：让协作边界可检查

**输入：**已确认的 Proposal 与 Design、实际调用方/提供方、当前接口和数据模型。

**AI 应做：**列出新增/修改/废弃接口或事件，逐项说明请求、响应、字段语义、空值/默认值、状态与错误码、幂等键、版本与旧调用方兼容；需要机器校验时选择 OpenAPI YAML 或合适的 Schema。契约写在实际拥有该接口的仓库/位置，`SDD/design.md` 中给出影响与引用；不得在多个仓库维护相互独立的“权威副本”。

**暂停条件：**生产者不明、旧调用方范围不明、状态/金额语义冲突或兼容窗口未确认。

**人需确认：**对外承诺和兼容风险；AI 不得自行废弃现有接口。

## 4. 任务拆解：起草 Tasks

**输入：**已确认的 Proposal、Design、契约和可用执行资源。

**AI 应做：**

1. 将任务拆成可独立验证的交付物，而不是按文件或一句动词机械切分。
2. 每项写明描述、输入、输出、前置依赖、关联规格、可观察且可判定通过/失败的验收条件。
3. 用依赖关系确定执行顺序；只有不依赖彼此、且不会争写同一产物的任务才可并行。
4. 检查每项 Proposal 成功标准和 Design 契约都有实现与验证承接；不在任务阶段偷偷引入新架构决策。

**输出：**`SDD/tasks.md` 草案，可使用 [tasks 模板](模板/tasks.md)。

**暂停条件：**验收条件无法检查、依赖成环、一个任务大到无法在当前上下文中独立交付，或任务要求修改未批准范围。

**人需确认：**任务边界、优先级、依赖和本次 SDD 规格；规格审核通过前不得进入代码修改。

## 5. 实现：一次执行一个已获准任务

**输入至少三层：**全局目标（Proposal）、结构/契约（Design）、当前任务与前置任务已完成产物（Tasks）；同时核对目标分支的实际代码。

**AI 应做：**先重述当前任务与允许改动范围，再实现代码和相应测试；逐条比对任务验收、接口契约和非功能约束；记录实际改动与规格的任何差异。完成一个任务并验证后，再进入依赖它的下一项。

**禁止：**在 SDD 规格未审核时改代码；为让测试通过而弱化验收；擅自修改非范围系统、生产数据或外部服务；遇到规格错误时在代码里悄悄绕过。

**暂停条件：**代码现实与规格冲突、需要新增业务规则/架构决策/数据迁移、验证所需权限或环境未获准。应先报告并更新相应 SDD 规格，重新等待确认。

## 6. 验证与交付：用证据证明规格被满足

**输入：**Proposal 成功标准、Design 契约和非功能约束、Tasks 验收项、实际代码与测试环境。

**AI 应做：**

1. 将任务验收映射到局部/单元测试，Design 契约映射到集成或契约测试，Proposal 成功标准映射到端到端验证。
2. 区分“计划执行”“已执行通过”“已执行失败”“未执行/受阻”；保存命令、环境、时间、关键输出或可复核证据。
3. 核对核心、边界、异常、兼容、数据和非功能场景；未覆盖的部分说明原因、影响和替代验证。
4. 将真实结果回填 `SDD/验证记录.md`，并在交付说明中标明剩余风险与是否需要人接受。
5. 对已经生效且核实的系统变化，更新所属业务线 `系统现状.md` 的能力、接口、数据模型或运行方式，注明核对时间与证据；跨业务线影响关联同一需求主目录。

**禁止：**用代码审阅代替所有验证；把未运行的命令写成通过；在测试失败或关键风险未决时宣称交付完成。

**暂停条件：**预期和实际不符、环境不足以验证、出现重大安全/数据/兼容风险。先定位属于实现缺陷还是规格缺陷，再按[评审验证与变更](评审验证与变更.md)处理。
