# SDD 评审、验证与变更规则

本文件把 SDD 的“规格可审查、可执行、可版本化”落实为可检查的 AI 行为。它与两套流程的[通用约束](../通用约束.md)同时适用，不引用原有流程的专属方案格式。

## 1. 规格评审清单

### Proposal：检查要做什么

- 目标是否让未参与讨论的人能理解问题和预期结果？
- 范围、非范围、角色和术语是否明确且前后一致？
- 每条成功标准能否转换为观察或测试；性能指标需要量化时是否给出数值？
- 空数据、外部失败、权限差异等重要边界是否有预期行为？
- 哪些关键决定仍需人确认？AI 是否把推断误写成事实？

### Design 与契约：检查如何做及为何如此

- 模块的负责/不负责范围、数据流和状态流是否清晰，是否与 Proposal 一致？
- 关键技术决策是否列出备选方案、理由与代价；重要决策是否有 ADR？
- 接口及数据模型的字段、空值、错误、幂等、版本和兼容性是否可被消费者理解？
- 安全、性能、日志、监控、回滚和数据迁移是否按风险覆盖？
- 是否存在“设计默认值”掩盖尚未确认的业务/架构决策？

### Tasks：检查是否能执行和验收

- 每项任务是否产生一个可独立检查的交付物，描述、输入、输出和依赖齐全？
- 验收条件是否能判定通过/失败，而不是“功能基本正常”？
- 每项任务能否追溯到已确认的设计与需求；是否有需求无人负责或多任务重复写同一资源？
- 依赖是否无环；并行任务是否避免共享写入冲突？

这些检查是质量门槛，不把书中示例里的非目标数量、ADR 数量、代码行数或任务时长设成固定数值门槛。SDD 流程的正式产物是 `docs/业务线/{业务线编号}-{业务线名称}/{需求编号}-{需求名称}/SDD/` 中的规格，不套用原有流程的 11 节格式；评审时同时核对编号、名称和归属来自系统，跨业务线需求只维护一个主目录。

## 2. 验证追溯

| 规格层 | 验证层 | 最少应能回答 |
| --- | --- | --- |
| Tasks 的任务验收 | 单元/局部测试或可重复的局部检查 | 单项交付物是否按输入、输出和边界工作？ |
| Design 的接口、数据和结构约束 | 集成/契约测试、结构审查 | 模块协作是否符合已承诺的契约？ |
| Proposal 的成功标准 | 端到端/业务验收 | 用户目标是否真正达成，非范围是否未被误做？ |

将关键规格条款映射到测试用例或人工验证路径，并记录实际结果。测试不可自动化时，说明原因、替代证据及剩余风险。计划结果、执行结果与交付结论必须分别记录；失败和未执行不得合并为“通过”。

## 3. 变更从正确的层级开始

| 变更类型 | 首先检查/更新 | 后续受影响内容 |
| --- | --- | --- |
| 业务目标、范围或验收变化 | `SDD/proposal.md` | Design、契约、Tasks、代码、测试 |
| 架构、数据模型或接口决策变化 | `SDD/design.md` 和契约 | Tasks、代码、测试；必要时回查 Proposal |
| 任务拆分或依赖变化 | `SDD/tasks.md` | 实施顺序、代码与测试 |
| 纯实现缺陷 | 代码与测试 | 若暴露规格缺陷，再逆向修订 Design/Proposal |

实现中发现已确认的 SDD 规格不准确时，先更新相应规格并等待重新确认。重大新决策写新的 ADR，保留旧 ADR 的历史与替代关系，不覆盖原决策理由。规范与代码可同 PR/提交或先规范后代码；新功能优先让规格得到审查，不能把单一 Git 提交形式误当成书中唯一要求。

## 4. 给 AI 的输入与输出护栏

**输入侧：**确认请求来源、权限、目标环境/分支、受影响文件、已批准规格版本和允许副作用；拒绝越界、敏感信息暴露或未授权的生产/数据操作。

**输出侧：**检查产物是否符合范围、接口契约、测试和安全约束；列出未验证项、规格偏差与风险。AI 可以自查和提出修订，但不得自己批准业务决定、接受剩余风险或宣称未执行的验证已通过。

书中以 Hook 展示自动护栏，这是一种实现方式，不意味着所有项目必须安装脚本，也不意味着 AI 普遍禁止起草规格。是否增设 Hook/CI 由项目另行评审；本次目录只定义检查规则，不安装或启用任何工具。

## 5. 渐进式 CI 检查建议

1. **完整性：**检查本次 SDD 规格、验证记录、非范围和验收项是否存在。
2. **规格—代码一致性：**检查接口签名、数据类型、模块边界与代码是否相符；代码变而规格未变时给出提示，不一律失败，因为可能是纯缺陷修复。
3. **规格内部一致性：**检查需求范围、设计、契约和任务验收之间是否互相矛盾。

先从稳定的结构检查开始，再评估更复杂的语义检查。任何自动检查结果都应保留可解释的依据；涉及业务正确性和风险接受仍需要人审查。

## 6. 交付前自查

- 本次 SDD 规格已审查，且与最终实现一致；如发生偏差，已走重新确认流程。
- 任务和接口的验收项有真实执行证据或明确未覆盖风险。
- `SDD/验证记录.md` 回填了环境、命令/步骤、结果、失败原因和执行者/代理。
- 兼容、数据、上线和回滚风险已按变更类型处理；需人接受的风险没有被 AI 自动关闭。
- 需求已生效且核实后，将当前能力、接口、数据模型及运行方式更新到所属业务线 `系统现状.md`，注明核对时间、目标分支/环境和证据；尚未上线的设计与历史决策留在需求材料或 ADR 中。
