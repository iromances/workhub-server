# 研发规范入口

本目录并列维护「原有流程」与「SDD 流程」。两者共享[通用约束](通用约束.md)，但阶段、模板和需求产物互不替代。

## 开始开发前先选择

对于新的开发、修复、接口或数据库变更、正式方案编写、测试与交付任务，如果用户在**本次任务**中没有明确选定流程，先询问：“本次使用原有流程还是 SDD 流程？”得到答复前，只做必要的只读定位与分析，不起草该流程的正式产物，也不修改代码或执行有副作用的操作。不得因为仓库里已有某套文件、上次任务选过某套流程而默认选用；也不得混用两套模板和审批载体。

用户已明确指定时不重复询问。同一任务的后续实施可以沿用已确认的选择；开启新的开发任务时重新确认。单纯解释现状、只读诊断、回看资料，以及用户明确要求的文档整理、目录调整和 AI 指引维护，不需要选择流程；若转入开发需求的正式方案、代码实施或验证交付，再执行上述询问。文档维护不代表已批准任何业务变更，也不改变两套流程的审批门槛。

选定后，先读[通用约束](通用约束.md)，再只读所选流程入口：

| 选择 | 流程入口 | 本次需求产物 |
| --- | --- | --- |
| 原有流程 | [原有流程/AGENTS.md](原有流程/AGENTS.md) | `docs/业务线/{业务线编号}-{业务线名称}/{需求编号}-{需求名称}/` 下的 `研发方案.md`、`测试用例.md` |
| SDD 流程 | [SDD流程/AGENTS.md](SDD流程/AGENTS.md) | 同一需求目录的 `SDD/` 下的规格和验证记录 |

在需求产物的入口或说明中记录本次所选流程；已有需求的后续工作若要切换流程，先让用户确认，并说明既有产物如何保留或迁移。旧文件是历史资料，不因选择新流程而自动改写。

## 先定位业务线，再归档需求

业务线目录、需求编号来源、跨业务线归属和 `系统现状.md` 的维护统一遵守[通用约束](通用约束.md)的“文档定位与归档”。业务代码分析先按[业务运维分析方法](业务运维分析方法.md)确认目标业务线、仓库、环境和分支。需求文档直接位于所属业务线下，不额外建立“研发/需求”目录层级。
