# SDD 协作流程

本流程及同目录四份模板为本仓库研发规范。需求的具体产出保存在所属代码仓库；需求归档目录、项目字段与专项约束以本仓库指引为准。

新开发、修复、接口或数据库变更、正式方案编写、测试与交付任务先完成规格确认，再开始实施。只读解释、诊断、代码审查、资料回看、文档整理、目录调整、路径修正、AI 指引维护和研究复盘可直接进行；转入系统研发时再执行本流程。

## 执行流程

1. **建档**：先按编码和名称核对已有需求、历史来源与已确认的跨仓库归属，复用唯一目录；新需求按目标项目指引建档。无既有编码时生成 `REQ-{UUIDv4}`，在三份规格中固定记录名称、编码和涉及仓库，后续变更不重新编号。
2. **起草**：使用 [Proposal](proposal.md) 明确目标、范围和验收，[Design](design.md) 承接方案、契约、数据、验证和回滚，[Tasks](tasks.md) 编排实施任务；关键决策按需使用 [ADR](adr.md)。按项目指引补充元信息、专项设计项和任务字段。
3. **确认**：可连续起草完整规格，不逐份等待审批；规格达到本轮变更所需完整度后，由用户或有权人员在实施前统一确认。范围、规格版本、结论、确认人与日期记录在 Tasks；影响已确认范围、关键方案或验收标准的变更重新确认后实施。
4. **实施与验证**：按已确认规格和目标仓库约束实施，读取该项目适用的代码、审查和数据库规范。计划与实际结果分开记录，Tasks 保存证据、失败原因和剩余风险；跨仓库任务明确各侧职责、分支、接口和验收。
5. **交付**：核实并更新目标系统设计的受影响章节，在所属系统迭代日志记录实际进展；不影响系统现状时说明原因。保留既有产物、历史审批与验证结论，区分开发、验证和部署状态。

起草中遇到影响范围、关键方案或验收标准且无法从上下文确定的问题时询问用户，其他可独立完成的内容继续起草。已有任务的后续变更沿用本流程补充规格，记录任务来源和版本关系。

## 使用边界

- 正式产物为唯一需求目录下的 `proposal.md`、`design.md`、`tasks.md`，接口契约和 ADR 按需增加。
