# 代码风格

本文件适用于 AI 在本项目协作范围内新增或修改代码，包括 WorkHub 及目标业务系统代码。编写代码前必须读取，完成修改后必须按本文件自查。本文件不替代研发流程和授权要求。

## 1. 结合上下文，只写必要的代码

**必须基于已核实的代码上下文完成当前需求，禁止为假设场景堆叠无用的防御性代码。代码的每个新增分支、校验、兜底和抽象，都应有明确的业务或技术依据。**

- **先读上下文再写代码。** 核对相关调用方、接口契约、参数与返回值约定、已有校验、框架行为及异常处理方式，再决定需要补充什么；上下文不清楚时先定位核实，不用猜测性的判断和默认值掩盖不确定性。
- **不重复已经保证的条件。** 对已由可信入口校验、类型约束、数据库约束或明确调用契约保证的条件，不在内部调用链中反复判空、判类型或检查相同状态。省略校验前必须确认约束覆盖当前调用路径，不能仅凭方法名或习惯推断。
- **不添加无依据的兜底。** 没有明确需求或真实故障依据时，不新增多层 `if`、宽泛 `try-catch`、备用路径、重试或兼容分支。不得将应暴露的错误转换为成功、空集合、零值或其他默认值；异常处理沿用项目已有机制，只有当前层确实需要恢复、转换或补充必要上下文时才捕获。
- **不为未来假设扩展实现。** 优先复用现有能力，用清晰直接的实现解决当前问题；不为尚不存在的复用、扩展或兼容需求新增工具类、接口、配置项和通用框架，也不夹带无关重构。
- **保留有依据的必要保护。** 外部输入校验、权限校验、业务状态约束、数据完整性以及实际需要的事务、并发和幂等处理必须保留；外部依赖失败按已明确的契约处理。“避免防御性编程”不能成为删除必要校验或忽略真实异常的理由。
- **以清晰和正确为前提精简。** 优先让正常业务路径直接可读，去除重复逻辑和无效分支；不得为了减少行数压缩成难以理解的表达式，或改变既有业务语义。

## 2. 先处理退出条件和边界，再实现正常功能

**进入函数后，必须先完成当前函数职责内必要的参数校验、边界处理，以及无需继续执行的情况处理，再按照预期功能展开正常业务逻辑。**

- **优先提前退出。** 对无需处理、不满足处理条件或已得到结果的情况，按接口契约直接返回；非法参数或不允许的业务状态按既有异常机制终止，不能静默伪装成成功。各项判断顺序必须符合业务语义，不得因提前返回跳过必要校验。
- **让正常逻辑顺序展开。** 前置处理完成后，按业务步骤直接实现功能，避免把整个正常流程包在多层 `if` 或 `else` 中，也不要将可提前完成的校验散落在业务处理之后。
- **在条件具备时尽早判断。** 依赖查询结果或中间状态的边界，在获得必要数据后立即处理、进入后续操作前完成；不为形式上的“全部放在开头”重复查询、改变必要的执行顺序或增加无依据的防御性判断。已由上下文保证的条件仍遵守第 1 节，不重复校验。

## 3. 工程边界

- 工程结构与模块职责以目标分支代码为准；
- 前端负责交互、呈现、表单状态和轻量展示格式化；
- 后端负责业务逻辑、计算、数据聚合、状态、权限判定等应由后端接口统一输出。

## 4. 交付前自查

- 每个新增校验、分支、兜底和抽象，是否都能对应到当前需求、真实调用路径或明确约束？无法说明依据的应删除。
- 是否重复实现了上游或框架已有的保证，或用默认值、捕获异常掩盖了应修复的问题？
- 精简后是否仍保留必要的安全、业务和数据完整性约束，并保持约定的行为？
- 是否先处理了必要校验、边界和提前退出条件，再顺序展开正常功能，且没有因提前退出跳过必要操作？
