# 两套研发流程的通用约束

本文件只记录与流程选择无关的安全及工程要求。具体规格结构、评审载体、模板与需求目录分别由所选流程决定；本文件不意味着必须同时执行两套流程。

## AI 协作与授权

- 使用中文沟通和维护仓库文档；代码标识、命令、API 路径、产品名及既有固定目录可保留英文。
- 明确目标仓库、环境、分支、允许的修改范围和需要的授权。AI 不自行启动应用，不自行安装软件或脚本；涉及生产数据、外部系统或其他有副作用操作，遵守用户授权和仓库安全边界。
- 所选流程要求的规格/方案尚未获得有权人员确认前，不修改业务代码，也不执行会改变项目状态的命令。实施中发现已确认规格不准确或范围扩大，先更新相应规格并重新等待确认。
- 不将未执行的验证写成已验证；不将 AI 起草的内容写成已审批。不在方案、文档、日志或回答中暴露敏感配置、token、数据库密码。
- 关键写操作必须有日志或留痕，尤其是工作项状态流转、需求阶段动作、支付配置变更和跟踪记录。

## 文档定位与归档

- 业务线根目录统一为 `docs/业务线/{业务线编号}-{业务线名称}/`。编号与名称读取 WorkHub 的 `businessLineCode`、`businessLineName`，不能使用数据库主键、简称、GitLab 组名或 AI 自编编号替代。
- 业务线目录内并列放置 `系统现状.md` 和 `{需求编号}-{需求名称}/`。需求编号使用系统的 `approvalCode`，需求名称使用 `requirementName`，缺失时使用 `approvalTitle`；以系统需求记录及其业务线关联为准。未获取权威编号、名称或归属时，先查系统或向用户补齐，不创建“待编号”“无编号”等占位正式目录，也不自行编制编号。
- 每个需求只维护一个主目录。跨业务线需求按系统归属确定主目录，其他受影响业务线通过 `系统现状.md` 关联该目录；系统归属不明确时先确认，不能复制多份正式需求文档。
- 需求主目录记录所选流程及需求来源：原有流程维护 `研发方案.md`、`测试用例.md`；SDD 流程在 `SDD/` 下维护规格与验证记录。两套正式产物互不覆盖，不因目录迁移重写历史审批或验证结论。
- `系统现状.md` 只记录所属业务线已核实且当前生效的职责、仓库/分支、环境、架构、接口、数据模型、运行方式及限制，并注明核对时间和代码、配置、日志或只读数据来源。需求设计、待实施方案与历史决策放在需求目录，不作为当前事实；资料不足时明确待核实。
- 不再建立独立的事实文档层。先按[业务运维分析方法](业务运维分析方法.md)定位，结合目标分支代码与目标环境证据回答当前实现问题；长期生效的业务线事实归入对应 `系统现状.md`，通用方法和工程规则归入 `docs/研发规范/`。

目录命名、归属核实和现状维护的具体规则见[业务线文档入口](../业务线/AGENTS.md)。

## 工程边界

工程结构与模块职责以目标分支代码为准，并与所属业务线 `系统现状.md` 中的核实记录交叉检查。

- 前端负责交互、呈现、表单状态和轻量展示格式化；业务统计、数据聚合、状态口径、权限判定、跨页分页合并、业务线归并及金额/数量汇总等应由后端接口统一输出。统计页面不得由前端拉取大分页或全量列表自行聚合。展示计算一旦影响业务数量、分组、筛选、排序或权限，应后移到后端。
- 表结构变更同步更新初始化 SQL、模型、DAO、服务逻辑和需求文档。新增或变更接口在需求文档中记录设计和验证，生效并核实后同步更新所属业务线 `系统现状.md` 的接口说明；接口文档表格包含 `系统路径`。
- 数据库结构变更应说明 DDL、DML、默认值、历史数据兼容、索引影响和回滚方式。纯刷数据需求应说明数据范围、筛选 SQL、影响记录数、备份、幂等、试跑、回滚和前后校验；不得直接执行正式刷数。
- 禁止在 Java 启动代码、`ApplicationRunner`、`CommandLineRunner`、Bean 初始化或定时任务中硬编码 DDL/DML 自动补表、补字段或刷历史数据。
- 数据库结构和数据变更必须以 Flyway 版本脚本交付，放在 `workhub-bootstrap/src/main/resources/db/schema/mysql/`；`V1` 至 `V20` 保留为历史数字版本，后续新增脚本使用全局唯一的 `VYYYYMMDD_HHMMSS__brief_desc.sql`，描述为小写英文及下划线。
- 已在持久环境成功执行的 Flyway 脚本不得修改、重命名或删除；修复应新增更高版本。失败迁移须保留现场、核对部分提交的 DDL，清理与 `repair` 经人工评审后才能重试。发布前执行 `clean package`，避免构建目录残留迁移资源。
- Flyway 保持严格命名校验及 `validate + migrate`；禁止 out-of-order、自动 baseline、placeholder 替换和数据库 clean。校验或迁移失败应阻止应用启动。执行记录以 `flyway_schema_history` 为准；失败后核对实际结构及历史表，优先向前修复，不用 Java 启动逻辑绕过脚本管理。具体配置与脚本以目标分支代码为准，执行及恢复证据记录到本次需求文档。
- 可观测性基础设施作为旁路能力，采集失败不得影响核心台账 API。

## 验证与交付

- 验证覆盖核心、边界、异常场景；不适合自动化的场景说明原因和替代方式。计划与真实结果分开，记录环境、命令或步骤、时间、执行人或执行代理、失败原因和剩余风险。
- 交付前执行与风险相称的检查；后端较大改动至少执行 `mvn -q -DskipTests compile`。受影响接口进行基本手工验证，涉及前端调用时同时验证入口路径和响应字段。没有成体系测试代码也不能替代编译、接口及必要手工验证。
- 环境、依赖或外部服务阻碍验证时，说明原因、影响和后续建议；最终只声明实际执行成功的验证。需求的具体测试文件名与格式由所选流程规定。
- 已生效的系统能力、接口、数据模型或运行方式发生变化时，核实后更新所属业务线 `系统现状.md`；尚未上线或未核实的变更保留在需求产物中并标明状态。
