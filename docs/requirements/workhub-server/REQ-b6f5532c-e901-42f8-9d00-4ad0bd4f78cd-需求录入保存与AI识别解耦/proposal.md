## 1. Why：背景与问题

用户在导入需求后遇到 Codex CLI 启动错误（找不到 codex），要求保证需求保存独立于 AI 识别。

当前上传接口已经在一个事务中保存需求主记录和附件，AI 在事务提交后的回调中异步执行；AI 执行失败会记录 FAILED，并已有重试接口与页面入口。因此，提供的 Codex 异常本身不能证明需求未入库，本次未查询运行数据库或复现该次上传。

仍存在明确的代码边界：`IntakeEnrichmentService.scheduleUploadedEnrichment` 在 afterCommit 中直接提交任务，未处理执行器拒绝。任务提交失败可能在数据已提交后向接口传播异常，并留下 PENDING，使页面误报保存失败且没有重试入口。`enrichUploadedIntake` 的 RUNNING 初始化也在现有异常处理范围外。页面成功提示“需求已提交，AI 正在后台识别并归类”，未明确区分保存结果与识别结果。

## 2. What：目标与范围

### 本期目标与交付范围

1. 需求原文、录入元信息、截图和附件先完成保存；AI 的命令缺失、调用失败、超时或任务提交被拒绝不回滚已保存内容，也不把已保存结果呈现为保存失败。
2. 保留自动后台识别；任务提交失败或识别失败后记录 FAILED 与失败摘要，复用现有“重新识别”入口。
3. 重试使用既有需求 ID、原文及附件，不重复创建需求，失败后仍可再重试。
4. 页面明确提示“需求已保存”，解释识别失败可以重试；刷新列表失败只报告列表加载失败。
5. 增加验证事务提交与 AI 调用顺序、任务拒绝、AI 失败和重试的自动化用例。

### 明确不做

- 不安装软件，不启动或重启 WorkHub，不发起真实 AI 推理。
- 不新增消息队列、自动重试、进程重启后的任务恢复机制或数据库迁移。
- 不改变需求业务生命周期、正式工作项人工确认规则和已有重试权限。
- 原文或附件保存、必填校验、业务线校验、数据库提交自身失败仍按保存失败处理，不能伪装为成功。

### 约束与依赖

- 遵守根 AGENTS.md、docs/AGENTS.md、代码风格；完整规格确认后实施。
- 需求主表与附件元数据保存继续采用现有事务；业务数据库可用是记录失败状态的前提。
- 不覆盖工作区既有无关修改；本次唯一规格归档本目录。
