## 1. 背景

待整理需求的类型由录入时的识别逻辑（Codex 结构化提取，回退为关键词推断 `IntakeStructuredDataExtractor.inferRequirementType`）自动生成，值为“研发需求”或“数据提取/运维”。识别错误时（如 202610280001“即科医美项目还款及代偿回购分账功能”被识别为“研发需求”，实为数据提取/运维）没有人工修正入口。

详情页基本信息中“需求类型”为只读展示；同页“业务线”“优先级”已有“编辑 + 弹框 + 实时保存”模式，类型缺少同等能力。类型影响系统分支：数据提取/运维类走 SQL 草稿与运维阶段流，研发需求类走澄清/研发分析，且研发分支名仅对研发需求存在。

## 2. 目标与范围

1. 后端新增需求类型修改接口，校验类型值域（研发需求、数据提取/运维），保存结构化数据与正式字段，记录修改历史，返回最新详情。
2. 类型切换时研发分支名按现有语义联动：切为数据提取/运维清空研发分支名；切为研发需求保留现有分支名，缺失时按现有规则生成。联动结果一并记录历史。
3. 详情页基本信息“需求类型”增加编辑入口，弹框选择类型后即时保存，详情与列表实时刷新。
4. 权限沿用业务线/优先级修改权限（`intake:metadata:update` 或 `intake:record:update`）。
5. 不改变识别逻辑本身，不批量重算历史记录，不迁移数据；202610280001 的类型由用户在功能可用后通过详情页修正。

约束：不安装依赖，不自行启动 WorkHub 应用。

## 3. 验收标准

| 编号 | 可观察的验收条件 | 核对方式 |
| --- | --- | --- |
| AC-01 | `POST /api/intake/{id}/requirement-type` 以合法类型调用后保存结构化数据、正式字段并返回最新详情，权限不足被拒绝 | 控制器与服务测试 |
| AC-02 | 类型不在值域或为空时明确报错，不落库 | 服务测试 |
| AC-03 | 类型未变化时不重复落库、不写历史 | 服务测试 |
| AC-04 | 切为数据提取/运维后研发分支名清空；切为研发需求后保留或生成研发分支名；变更写入修改历史 | 服务测试 |
| AC-05 | 详情页“需求类型”可编辑并即时保存，保存后详情、列表与阶段展示按新类型刷新 | 前端构建与类型检查，页面联调待部署后进行 |
| AC-06 | 类型/分支名修改历史可追溯（操作人、前后值） | 服务测试 |
